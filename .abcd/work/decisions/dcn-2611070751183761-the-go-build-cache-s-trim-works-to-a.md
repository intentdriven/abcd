2026-11-07 — The Go build cache's trim works to a size limit in place of its two-day age, amending dcn-2611041338454498, and besides prune it runs when the build loop's worktree stage makes a lane, for a build and a drain alike, detached and at most once an hour across the account. Grounds: a lane is what fills the cache, every build and drain makes them, and a drive running for weeks makes them throughout, where prune can go days without running and the load gate only refuses; a verb start would miss a long drive, and a whole-run gate would miss work that runs no preflight. A walk took 115 to 437 seconds on a very large cache, so the lane starts it in its own session holding nothing of the caller's and does not wait; a marker in the abcd home paces it across processes, and since a detached run has no terminal, it saves its answer there and the next lane to claim says on stderr what it could not do. The age goes because a cache under its limit has no reason to lose entries and rebuild them, and Go's own five-day trim still runs. Four smaller calls: the keep allows Go's hour, so entries whose time is under 4 hours old stay, which is what keeping anything used in the last 3 hours requires; a limit that cannot be read or used deletes nothing, unlike load.preflights, which reads past, since a guessed size could delete what the person's value would have kept; size is each file's length, the measure the load gate already names; and the trim is also a verb of its own, ahoy worktree trim-cache, which is what the detached run needs and what the gate's refusal can now offer, since the two-day find it offered freed nothing on a busy machine. The key is load.go_cache_limit_gib, in GiB as the stopgap measured it.

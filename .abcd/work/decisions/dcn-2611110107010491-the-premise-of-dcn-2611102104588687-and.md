2026-11-11 — The premise of dcn-2611102104588687 and dcn-2611102203415224 that a lane's git worktree add runs the post-checkout hook of the commit it checks out is wrong: the add runs in the checkout, so with a relative core.hooksPath git runs the checkout's own working-tree copy of the hook, with the new worktree as its directory, for a new branch and an already-standing one alike, and that copy is the one the run's fingerprint already watches; a test through the real stage now holds it. The standing-branch check and the core.hooksPath named on the add's command line stay, as defensive measures: a lane whose hooks differ is refused before a worktree is made rather than after, and neither stops a hook from running. The add still reads objects as stored, so the lane holds the tree its commit stores. Grounds: the coordinator's experiment with git and the new test both show the checkout's copy runs. To reverse: nothing to undo in code; a git that ran the commit's own copy would make the standing-branch check load-bearing again.

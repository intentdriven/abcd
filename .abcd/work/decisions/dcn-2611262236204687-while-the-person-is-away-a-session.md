2026-11-26 — While the person is away, a session holding a scheduled wake whose prompt opens with a slash (a slash command) or with `<<` (a loop's sentinel, `<<autonomous-loop>>` or `<<autonomous-loop-dynamic>>`) has no prompt read as the person's, so no prompt opens its conversation window until a stop lists its wakes without one, as with a session listing more wakes than its state keeps. A stop whose payload lists an empty set of wakes clears the mark; one whose payload carries no wakes field (the host's task list not reached) leaves it. Grounds: a wake is told from the person typing only by its prompt's text matching what the stop listed; a plain-text wake arrives as it was set (checked on 2026-11-26 against 47 firings of a session's own wakes, every one equal after trimming), but a slash command reaches the prompt hook expanded, and the host's scheduling tool says a loop's sentinel is resolved back to the loop's instructions at fire time, so either firing would read as the person's and a frequent one would keep the session read as present for the whole away period. Failing closed costs the person only a window in such a session. Reverse by dropping the slash and sentinel tests from unmatchableWakes in internal/core/autonomy/conversation.go.

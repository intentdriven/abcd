2026-11-22 — Refusal codes are named for what the refusal means, not for the code path that raises it (spc-2610301431108175 steps 1 and 2, adr-2610301638558260). A verb's own refusal that means a usage refusal takes the usage code: capture's lone-word and mistyped sub-verb guards are usage/unknown-command, an empty issue text and explain's --input with no command are usage/missing-argument, capture list's filter choice and the --occasioned-by requirement are usage/missing-required-flag, two filters at once and --complete with other flags are usage/flag-conflict, and a closed-set value or a malformed --recurs token is usage/bad-flag-value. A verb gets a code of its own only for a refusal no usage code describes. The reason segment is spelled in US English, as code is (capture/not-characterized). A next command is a template whose only run-time part is the {command} slot, filled from the refused command's path; the word none marks a refusal no command gets past. Each entry names the commands that raise it, except a usage code, which every command raises. A refusal shared by many verbs (the peer-held refusal, the shared-main-checkout refusal) is left uncoded until the record verbs' step names it once for all of them, rather than one code per verb. exitError keeps its exported Code and Msg fields while the exemption list exists, because the listed files still build literals with them; they become unexported with the list's deletion.

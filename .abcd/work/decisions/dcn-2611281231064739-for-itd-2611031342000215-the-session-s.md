2026-11-28 — For itd-2611031342000215, the session's technical call on when the agents element reads stale (step 9 of spc-2611281205023617), answering the correctness review's finding that a 30-second bound marked every agent running past 30 seconds as stale data. While a launch it records is running, the launcher in RecordLaunch rewrites the session's rollup, rebuilt from the ledger, on a five-minute heartbeat as well as at the launch's start and end, so the rollup's written time is its running launches' last heartbeat. The agents element reads "as of" its written time only when the rollup counts a running launch and was written more than twelve minutes ago (two heartbeats and slack); a rollup that counts none running is final until the next launch and never reads stale. A launcher killed outright stops its heartbeat, so its "running" reads "as of" within twelve minutes, and the next writer, or abcd agents, which judges a running entry by its process, rebuilds the rollup. The 30-second interval of spc-2611050023402644's refreshed cache is not used. Grounds: the row may not read the process table and the ledger keeps no heartbeat, so the rollup's own write time is the only liveness the row can read, and the launcher lives exactly as long as its launch runs. The cost: one small rewrite every five minutes per running launch, off the status path. To reverse: drop the heartbeat and the time-based as of, and show the rollup's counts as written.

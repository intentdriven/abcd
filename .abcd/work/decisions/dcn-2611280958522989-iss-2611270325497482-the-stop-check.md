2026-11-28 — iss-2611270325497482: the stop check judges each check (a check run by its workflow and name, a commit status by its context) by its newest run, and sets a run aside only when it had finished (a readable, non-zero completedAt) at or before the start of another run of the same check, or when another run of that check is waiting to start. Runs whose windows overlap are concurrent and are all judged: matrix legs given one display name, or one workflow run for push and for pull_request, share the key without being a run and its rerun. A run with no start time sets others aside only while it is still unfinished (no conclusion, and a status other than COMPLETED), as a queued rerun is; a finished run with no start (one cancelled while queued) is placed at its completedAt, and one with neither time sets nothing aside and is judged alongside the rest, so a finished success with no times cannot hide an earlier failure. Runs that cannot be ordered (two at one instant, one whose end is unknown, entries naming no check) are all kept and judged as before. A commit status carries no completion time in the forge client's output, so it is read as ending the moment it was created, which keeps the newest-by-time rule for statuses; the forge lists only the latest status per context anyway. Grounds: a queued rerun of a failed check is the forge's newest verdict-to-be, so the check is pending rather than failing, and keeping what cannot be shown superseded errs toward reporting a failure rather than hiding one (review notes on forge.go:90 and forge.go:160). To reverse, change superseded, ordered and waiting in internal/core/autonomy/forge.go, and the matching cases in forge_checks_test.go.

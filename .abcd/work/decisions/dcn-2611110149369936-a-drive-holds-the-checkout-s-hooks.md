2026-11-11 — A drive holds the checkout's hooks directory across its lanes, beside origin's identity and by the same in-memory route: as it starts it hashes each entry of the hooks directory git runs at the checkout exactly as the run's fingerprint does, through one shared reader, and each lane's worktree stage reads it again just before git's add and refuses the lane on any difference, naming the hook file, before any add and so before any hook runs. This extends dcn-2611110107010491: the fingerprint records the checkout's working-tree copy of post-checkout at the run's first check, and within a run a later change is refused; across the lanes of one drive the drive holds it; elsewhere (a step the host runs, a single build, a drive started again) nothing does, so that copy must not change between runs, and nothing enforces it. The drive also holds credential.*, core.askPass, protocol.allow and every protocol.*.allow, as hashes. When a standing lane branch moves while git adds its worktree, the stage removes the worktree it added in that call, by its own path and through git's forced removal, and never the branch, so the next step meets the standing branch and judges it again before any add. Grounds: git's add runs the checkout's copy with the drive's rights, and each lane of a drain is a run of its own whose fingerprint takes that copy as its starting point, so the drive is what spans its lanes; the removed tree is one the step itself just made, with nothing committed in it. To reverse: drop the hooks hashes from the drive's held record, the check before the add and the removal on the moved-branch refusal; no persisted state changes either way.

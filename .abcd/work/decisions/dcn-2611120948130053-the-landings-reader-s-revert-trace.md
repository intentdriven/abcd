2026-11-12 — The landings reader's revert trace (spc-2610301950480609 step 3) reads revert lines as follows, where the spec leaves the case open. (1) Only a line at the start of its line counts, as git revert writes it and as RS001's revert_pairs greps it, so a quoted or indented line names nothing; only the first hex name on the line is read, because git's merge revert goes on to name the side it keeps. (2) A line marks a row only when git resolves its name from stored objects to a commit in the range that is a strict ancestor of the reverting commit and was brought by an older row; a name that is ambiguous, names nothing or no commit, lies outside the range, names the reverting commit itself, names a commit the same row brought, or names a non-ancestor marks nothing and says why on the row. The ancestor rule is RS001's and makes a cycle impossible. (3) A revert of a revert marks the first revert's row, and the originally reverted row keeps its mark with the withdrawing commit named, as RS001's withdrawn_by reinstates; the grouped view keeps such rows, since the change was reverted. (4) One commit's lines are read up to 64, and one listing follows at most 1024, oldest row first; lines past either bound are counted on their rows, not followed. (5) The forge's revert line in a squash's pull request body counts only where that row's answer was read and confirmed, only for an older row whose answer was also read, and its owner/repo form only when it names the repository the pull request merged into, which the batch reads beside the body (Repository.nameWithOwner, pinned in internal/ghcontract). (6) The positional trace reads the listing from the oldest row it needs to the tip, so a traced row's revert mark is the listing's. Grounds: git's own message format and RS001's existing reading; each case is tested in internal/core/landings/revert_test.go. To reverse any one, change its rule in internal/core/landings/revert.go and the matching test.

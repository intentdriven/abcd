2026-11-27 — RefreshScheduledRun in internal/core/claim/scheduled.go keeps dropping the error from writing its failure record (_ = paths.keep(paths.failed, data)), and that leaves no wrong answer. The refresh runs detached with stderr sent to /dev/null, and the store is the only place the prompt reads, so a failure record that cannot be written has nowhere else to go. A probe on 2026-11-27 confirmed what the prompt does instead. Nothing false is kept: the dated green stays and the attempt stamp is newer than it. The prompt treats this as a refresh that kept nothing, the case scheduledPastDue already covers for a refresh that died before it could keep a failure. So once the answer is more than 7 hours old (the 1-hour refresh interval plus the 6-hour margin) it says the state is unknown and that a refresh started since kept nothing, and after 48 hours it calls the answer stale. Before 7 hours the prompt stays silent, as it does for a refresh lost to a closed laptop, where a written failure record would have said unknown from 1 hour. A store that stays unwritable is caught sooner: the next due prompt, 15 minutes later, cannot write its own stamp, and since iss-2611051719396028 it says so on stderr and starts nothing. abcd status prints the not-read line to the person directly. To reverse this, have the read treat a due answer as unknown whenever a stamp more than scheduledRefreshDeath old is newer than both the answer and the failure record, dropping the 6-hour margin for that case, and pin it with a test that blocks the failure record's path.

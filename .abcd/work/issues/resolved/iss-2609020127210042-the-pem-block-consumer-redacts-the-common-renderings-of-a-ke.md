The PEM block consumer redacts the common renderings of a key body but not every one, and one armour form is not detected at all. scanner.pemBodyLineRe accepts an optional gutter then a single base64 run, so a body rendered as log-prefixed lines (a timestamp/level prefix), as CSV cells, as one element per XML tag, with a trailing hash comment, as a source-string concatenation, as a JSON array on one line, or with double-escaped backslash-n separators is not body-shaped, the block ends at that line and the rest is stored verbatim; the tail of a block longer than maxPEMBodyLines survives by the same route. The RFC4716 armour (four dashes, BEGIN SSH2 ENCRYPTED PRIVATE KEY) does not match the bundled pem_private_key pattern at all, so no block is ever opened for it. Evidence: scanner.pemBodyLineRe and maxPEMBodyLines in internal/adapter/scanner/pem.go, DefaultPatterns pem_private_key in patterns.go. A fix must either widen the body-shape rule over these renderings or arm an entropy rule for a headerless base64 run (iss-96), and add the RFC4716 armour to the header pattern.

Two further residuals, from the fix round that added the block consumer and its evidence rule. (a) The same-line body in the bundled pem_private_key pattern (scanner.pemPrivateKeyPattern in patterns.go) orders its alternatives so that a short final padding chunk is taken unconditionally only in a CLOSED block, where the END marker after it is the evidence; in the `open` alternative the short chunk must END the line. So a one-line key rendering with no END marker that is followed by prose keeps its trailing padding chunk of under sixteen base64 characters — "pasted <BEGIN header> <64 base64 bytes> QQQ= and then prose" stores "QQQ=" verbatim. A fix must decide that chunk on the run before it rather than on what follows it.

(b) In the other direction, the evidence rule that opens a block over-claims: scanner.pemBodyOpened treats ANY single run of sixteen or more base64-alphabet characters carrying at least one alphanumeric byte, on a body-shaped line within pemEvidenceWindow of a header, as proof that a key body opened. A header that is merely MENTIONED in prose therefore still opens a block whenever a long single-token line follows within two lines — a CamelCase identifier alone on a line, "CertificateRotationPolicy" for instance, inside a fenced snippet is enough — and the consumed run deletes those lines from a committed record, ending mid-fence and orphaning the closing fence marker. A fix needs a stronger opener test (a base64 run at a key body's characteristic width, or the entropy rule iss-96 tracks) rather than a bare length threshold.

Sub-residual (b) is closed; this record stays open for the rest. scanner.pemBodyOpened no longer reads a bare sixteen-character length as key material. One line is conclusive evidence only at a key body's characteristic width (scanner.pemOpenerRunRe, forty — under RFC 7468's sixty-four, OpenSSH's seventy and MIME's seventy-six, so no canonically rendered body line falls beneath the bar), and a block re-wrapped narrower than that opens through scanner.pemBodyRunPair instead: two consecutive body-shaped lines that each carry a run long enough to be key material, which prose that merely names a header does not show. So a mentioned header followed by one fenced identifier opens nothing and the record it sits in keeps its bytes and its fences, while every real-key rendering the three advisories bought still collapses to the placeholder — the pair rule is what carries the narrow-wrapped open block that the width bar alone would have written out verbatim. What is left of (b) is the part only an entropy rule can decide (iss-96): one identifier of forty or more base64-alphabet characters alone on a line inside the window, and two of sixteen or more back to back. Untouched and still open: the body-shape widening over log-prefixed, CSV, XML and JSON renderings, the tail of a block longer than maxPEMBodyLines, the RFC4716 armour the bundled pem_private_key pattern never matches, and residual (a).

Correction to the paragraph above, from the round that closed iss-2609090932441377. A characteristic width is not the only single-line route, and on its own it was the wrong axis: a block truncated by a log rotation or re-wrapped to a narrow column shows ONE body line under forty characters, with no second line for scanner.pemBodyRunPair to read, so the raised bar wrote that line out verbatim while the header pattern went on reporting a handled secret. A run of sixteen or more opens a block on a single line too, under two conditions that say nothing about width and that both have to hold: the header's marker is the whole content of its line (scanner.pemPastedHeaderRe — a PASTED header, as against one named inside a sentence, which goes on past the marker), and the run carries a byte of the base64 alphabet outside [A-Za-z] (scanner.pemNarrowKeyRun — a digit, a plus, a slash or the pad, which material drawn from all sixty-four symbols effectively always carries and a CamelCase identifier does not). What is left of (b) is still only an entropy rule's to decide (iss-96), with two shapes added to it from the other direction: a real body of sixteen to thirty-nine characters whose header carries prose after its marker, and one whose run happens to be letters only.

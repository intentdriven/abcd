An agent host's pull-request watch can switch off the git hooks that hold several of abcd's rules, and abcd beside such a watch has not been observed: this record rests on the host's page (https://code.claude.com/docs/en/ship-command) and on abcd's code. A watch is started by a host command the person types, and it then works on an open pull request over many turns. The page says that during a watch, on turns where the agent acts without a message from the person, it writes its git fetches, merges, commits and pushes in the form `git -c core.hooksPath=/dev/null push`, and its table of rules and hooks says git hooks in the repository's hooks folder do not run for those commands. Among the rules abcd keeps in those hooks are the pre-push refusal of a commit with no preflight receipt, the pre-push refusal of a push that moves the head of a pull request already armed or queued to merge (resolved iss-2611050535437225), the commit-msg check, and the name guard in the pre-commit and pre-merge-commit hooks. dcn-2609250000000003 already says that a push which skips the hook is not stopped and CI stays the authority. In this repository nothing on the forge stands in for the armed-head refusal or the name guard, and the macOS suite stands down on a pull request on the strength of the local preflight. So on such a turn a watch's push could move an armed pull request to a head that no receipt, review or approval names. While the pull request is armed and not yet queued, on a repository with a merge queue or without, the forge takes the moved head once its checks and its own rules allow; the page's table of cases that can lead to a merge says that where auto-merge is on, what the agent does during the watch, such as pushing a fix, can bring the merge about. Once the entry is queued or merging, the same push is the dropped-push hazard iss-2609181223354098 records. That an arming stays on a moved head is read from abcd's code and records, not observed here. Whether the shell guard stops the push is not observed either. The guard refuses a commit or push that points `core.hooksPath` elsewhere for itself (`internal/core/guard/hookspath.go`, `commands/guard.md`, resolved iss-2609251640464212). The page's rules table says a permission rule that asks on every git command matches a watch's push, which suggests the push is an ordinary tool call the guard would see and refuse. Of tool hooks during a watch, that table says they do not apply to the `gh` and `git` commands the host program runs itself, outside the sandbox, and the page's table of code a watch runs says the person's own host hooks run without asking. If the guard does refuse the push, a watch cannot push from a guarded checkout, and no page of abcd's says that either. On the bundled guard entries the refusal covers commit and push only, so there a watch's merge in that form is not refused and skips the pre-merge-commit name guard; this repository's own guard file adds a merge entry (resolved iss-2610301330557789), under which that form is refused, as read from the code and not run. Assessed with the question in `.abcd/development/principles/abcd-fixes-what-it-adds.md`, this is a check abcd adds being set aside and not a danger abcd adds: a repository without abcd has none of these hooks to lose.

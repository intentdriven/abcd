## 1. Summary

abcdev.app today is the MkDocs Material rendering of `docs/`, served at the root by an assets-only Cloudflare Worker. The docs tree is thin (a Diátaxis index, the terminology crosswalk, the generated CLI reference, and three stub READMEs), so the root URL currently greets a visitor with a filing system rather than a product. Meanwhile the repository holds an unusually rich, machine-readable development record (37 ADRs, 123 intents, 32 specs, 24 principles, a 374-entry issue ledger, a CSL-JSON bibliography, and `Assisted-by:` trailers on 69% of 1,188 commits) that nobody can see without reading YAML frontmatter on GitHub.

The plan: move the docs to `/docs/`, put a product-thinker-first landing page at `/`, and add a **record explorer** (`/record/…`, `/contributors/`, `/references/`) whose every page is rendered from the repo on each build. The decisions you took in this session are baked in: a hybrid, SSG-agnostic build (keep Material for `/docs/` for now; generate everything else with an `abcd site build` step in Go); product thinkers first above the fold; the full record including the issue ledger; a short `curl -fsSL https://abcdev.app/install.sh | sh` as the one new distribution endpoint; **no text written for the website** — every sentence the site renders is a span of a repository file, which makes README.md a slim contributor page and moves its product narrative into `docs/` (§5.0); one relationship chart with two arrangements — a date-ordered coil and a links-only force layout — instead of a hairball (§5.4); every picture a committed asset under `docs/assets/img/` (§5.0); and a hard requirement that the core renders perfectly on phones (§5.5).

Two findings shape the architecture more than anything else. First, the MkDocs ecosystem is fracturing: MkDocs 1.x has had no release since August 2024, Material for MkDocs announced maintenance mode on 6 November 2025 with "critical bug fixes and security updates for 12 months, at least" and no new features, and MkDocs 2.0 removes plugins entirely ("it will cease to work with MkDocs 2.0"; 9.7.5+ pins `mkdocs<2`). That is why nothing in this plan depends on a MkDocs plugin or hook: the generator writes plain files, and the SSG that renders `docs/` becomes replaceable (Zensical, Hugo/Hextra, or anything else) by a later ADR. Second, the record's frontmatter already forms a clean typed graph (`related_adrs`, `related_intents`, `spec_id`, `builds_on`, `supersedes`, plus 1,287 body mentions), so the dashboard, genealogy timeline, interactive graph, contributors and references pages are renderings of one generated `record.json`, not five separate systems.

## 2. What exists today

**Repository and identity.** The canonical remote is `github.com/Partnermedia/abcd` (the Claude project description still says `<personal account>/abcd`; the plugin manifest names the personal account as author and Partnermedia as homepage, and CODEOWNERS assigns the publish surface to the product thinker's account). The brief's *Identity (canonical)* block is the single source for the title, tagline and pitch, and `.abcd/positioning.json` already re-renders three surfaces from it (README strapline, manifest description, AGENTS.md opening). The site hero should become the fourth.

**Docs and site build.** `mkdocs.yml` (site_url `https://abcdev.app`, Material 9.7.7 pinned in `docs/requirements.txt`, no plugins block, no `repo_url`/`edit_uri`, no `content.code.copy`) renders `docs/` into `site/`, which is gitignored. `wrangler.jsonc` is an assets-only Worker (`"assets": {"directory": "./site", "not_found_handling": "404-page"}`) with custom domains `abcdev.app` and `www.abcdev.app`; the build, deploy and branch-preview commands live in the Cloudflare dashboard and are recorded as comments in the file, including the observed quirk that non-production branches run only the version command, so it repeats the build. `docs-lint` (`abcd docs lint`) gates `docs/` and README: present-tense prose, resolvable links, no stray root markdown, citation hygiene, and a `harness/*` family of banned tokens that keeps user-facing prose host-agnostic (naming a specific agent harness is a blocker outside an attribution escape). Live checks: the site serves an 8-URL sitemap, no `/llms.txt`, no `/.well-known/security.txt`.

**Releases.** Changelog-driven (adr-37): `auto-release.yml` tags the newest dated CHANGELOG version and calls `release.yml`, which re-verifies the commit, cross-compiles four binaries, writes `checksums.txt`, attests provenance on the public repo, and publishes with `gh release create`. Asset names are version-free (`abcd-darwin-arm64`, `abcd-darwin-amd64`, `abcd-linux-arm64`, `abcd-linux-amd64`, `checksums.txt`), which is exactly what makes GitHub's permanent `…/releases/latest/download/<asset>` redirect usable. Ten releases so far, v0.1.0 (7 Jul) to v0.6.1 (20 Aug).

**The record as data.** ADRs carry `id, status, date, supersedes, superseded_by, related_intents, related_adrs, related_rfcs`; intents carry `id, slug, spec_id, kind, builds_on, severity, impact` with lifecycle by directory (`drafts/ planned/ shipped/ superseded/ disciplines/`); specs carry `id, intent`; issues carry `id, severity, category, resolution`. Intents and specs carry no dates (git first-commit dates fill that gap at build time). Extracting the graph surfaced six unresolved references — adr-22→adr-14, adr-25→adr-8, adr-27→adr-16, adr-28→adr-18, adr-35→adr-4 (all `supersedes` pointing at ADRs removed from the tree under "retire the name") and itd-3→spc-1 — plus 74 records with no cross-references at all. A site build is a second place where that drift becomes visible.

**Prior landing-page work.** The July asset in the Claude project (`assets/landing-page.html`) has the right instincts (the comic, the cast, "Given/When/Then" done well) but its links point at `<personal account>/abcd` and at docs paths that no longer exist (`docs/reference/commands.md`, `docs/reference/facilitator.md`). The mockup reuses its imagery and retires its copy in favour of text rendered from README and the brief.

## 3. State of the art, condensed

**Landing pages for single-binary CLIs (20 sites inspected).** The common denominators are a one-line value proposition with a one-sentence subhead; "Get started" into the docs as the primary call to action with GitHub secondary; the docs link first or second in the nav; a 3–8 card feature grid; dark mode on every SSG-built site; and, on about half, an install command in or directly under the hero, always served from the project's own domain (`bun.sh/install`, `mise.run`, `starship.rs/install.sh`, `setup.atuin.sh`, `get.chezmoi.io`, `astral.sh/uv/install.sh`). A demo is near-universal for terminal tools (asciinema on k9s, a recording on bun, GIFs on fzf/lazygit). The closest live template for the `/` + `/docs/` split is trivy.dev (custom marketing page at `/`, Material docs under `/docs/latest/`); GoReleaser and golangci-lint (Hugo/Hextra) and Task (VitePress) are the closest "one generator for both" templates. Version display is split: a nav badge or banner on the larger projects, none at all on about half.

**Generators.** Among Go CLIs the 2025–26 moves were Material → Hugo/Hextra (GoReleaser, March 2026; golangci-lint, August 2025), with VitePress (Task, mise) and Docusaurus (OpenTofu) the other common choices; chezmoi, ko and trivy stay on Material. Astro Starlight is the most modern docs framework but brings Node into a repo that has none. Zensical, the Material team's Rust/Python successor, reads `mkdocs.yml` directly but is alpha and supports neither plugins nor hooks yet. The honest conclusion is that there is no safe "forever" choice this quarter, which is the argument for keeping generation outside the SSG.

**Latest binary.** The permanent links are `https://github.com/OWNER/REPO/releases/latest` and `https://github.com/OWNER/REPO/releases/latest/download/ASSET` (both 302s, both exclude pre-releases and drafts). The REST endpoint `GET /repos/{owner}/{repo}/releases/latest` supports CORS from any origin but is rate-limited to 60 requests/hour per client IP unauthenticated, which is why Material's own header widget swallows failures silently; a static site should inject the version at build time and treat any client-side fetch as progressive enhancement. GitHub releases became immutable in October 2025 (assets cannot be modified, tags cannot move), so floating-tag schemes are now an anti-pattern; abcd's pipeline is already compatible. Shields.io badges remain the zero-effort fallback for README.

**Record-to-site tooling.** No existing ADR tool (log4brains, dormant since December 2024; adr-tools, 2018; adr-viewer; Backstage's ADR plugin; Structurizr's decision explorer) renders a cross-entity graph of decisions, intents, specs and issues. Quartz's graph view is the right architectural precedent (build-time content index, client-side force graph, SPA-aware navigation). For the graph itself, `force-graph` (canvas, d3-force, ~57 KB gzipped, MIT, released April 2026) covers zoom, hover-neighbour highlighting, click-through, filters and search; Sigma.js is the step up if the graph ever exceeds several thousand nodes. For timelines the static-first route (SVG generated at build; Neoteroi's CSS-only timeline for narrative lists; d3-dag for supersession chains) beats Mermaid's experimental, ordinal `timeline`. For references, `mkdocs-bibtex` is archived (November 2025) and pandoc is not in Cloudflare's build image; `citation-js` with a vendored CSL style (or pandoc in a GitHub Action) is the workable path. For contributors, `git shortlog -sne` through `.mailmap` plus `git log --format='%(trailers:key=Assisted-by,valueonly)'` is all that is needed; we found no other project publishing its AI-assisted share on a contributors page, so abcd would be an early example, which argues for linking the policy next to the number.

**Cloudflare Workers static assets.** One assets Worker serves `/` and `/docs/**` with the default `auto-trailing-slash` handling, which maps 1:1 onto MkDocs directory URLs. `_redirects` and `_headers` are supported for Workers assets (2,000 static + 100 dynamic redirects; 100 header rules) and are evaluated before asset lookup, so old root URLs can 301 to `/docs/…` without any code. `404-page` handling walks up the directory tree, so MkDocs' own `site/docs/404.html` serves docs misses and the landing page's `site/404.html` everything else, provided `site_url` ends in `/docs/`. The build image ships Go 1.24.3, Python 3.13 and Node 24, so `go run ./cmd/abcd site build` works there unchanged; pip and Go module caches are not cached between builds. Branch previews land on `<branch>-abcd.<subdomain>.workers.dev`. Cloudflare's stated direction is Workers over Pages, so staying put is right.

Per the repo's own *prefer-SOTA* principle (adopt the state of the art only after an adversarial fit-challenge against local constraints), these are the places where the generic best practice collided with a deliberate abcd rule and lost:

| Generic SOTA | abcd constraint | What the plan does |
|---|---|---|
| Move docs to Starlight/VitePress/Docusaurus | No Node toolchain in the repo; new dependencies need sign-off; single-binary ethos | Keep Material for `/docs/`; generate everything else in Go; defer the SSG switch to an ADR before ~Nov 2026 |
| "Built with X" badges, harness-specific install tabs | `harness/*` docs-lint blockers keep user-facing prose host-agnostic | Landing and docs copy name no harness; the plugin install block uses the generic `/plugin marketplace add` form already in README; attribution appears only on `/contributors/` under the sanctioned escape |

| Client-side "latest release" widget via the GitHub API | 60 req/h per IP; visitors behind shared IPs see failures | Version, date and asset links injected at build from CHANGELOG.md and the tag list; no runtime API calls |

## 5. Target architecture

### 5.0 The single-source rule: nothing is written for the website

**The rule.** The site may render only (a) spans of Markdown files in the repository, selected by path and heading, (b) structured data the repository already maintains for other consumers (the Identity block, CHANGELOG.md, record frontmatter, the generated CLI reference, `personas.json`, git history), and (c) interface strings from one small allowlist file, `site-src/ui.json` (nav labels, button labels, tile captions — twenty-five entries today). Headlines are the source pages' headings; card blurbs are their paragraphs; the "testimonial" is a shipped intent's press release quoted verbatim; diagram labels must be words that occur on the page they illustrate. If a sentence would improve the site, it is written into the documentation where it must also read correctly on GitHub — the site only selects and arranges.

**The mechanism.** `.abcd/site.json` is a composition manifest that names *where* each block comes from and carries no prose (sibling of `positioning.json` and `docs-lint.json`, same shape of idea: surfaces rendered from canonical text). The generator walks it: for the landing page, a hero from `docs/explanation/rationale.md` (H1 + first paragraph) and the Identity block, then four chapters that are README's own table of contents — a Roles, b Artefacts, c Process, d Install — each rendered from its docs page with a layout rule (`cards-from-h2`, `lead-in-cards`, `prose`, `install`), then the record strip from `.abcd/development/README.md` with counts from `record.json`. Every rendered block carries `data-src="path#heading"`, which gives the "notes" layer its provenance captions for free and gives CI a check: after a build, every visible text node must sit inside a `data-src` element or match an `ui.json` string, a number, a date, a file name or an asset name; anything else fails the build. Rendered text is additionally run through the docs-lint banned-token rules regardless of which tree it came from, so record text rendered on the site cannot reintroduce a harness name. The prototype already passes the provenance audit (334 text nodes on `/`: 296 sourced, the remaining 38 are ui.json strings, numbers, asset names and the four loop-figure labels).

**Every picture is a committed asset under `docs/assets/img/` and is referenced from a docs page like any other image**; the build never draws one. That covers the cartoon (`intro.png`, from rationale.md), the three role portraits cropped from the cast illustration (`role-product-thinker.png`, `role-facilitator.png`, `role-ai-agents.png`, from roles.md — and reused above the column labels of the artefacts table), the three artefact icons (`artefact-brief.svg`, `artefact-intents.svg`, `artefact-audits.svg`, each on the line before its lead-in paragraph in artefacts.md), the process loop (`process-loop.svg`, after the first paragraph of process.md) and a 1200×630 crop for the OpenGraph card. SVG assets use `var(--token, fallback)` colours: the site inlines them so they follow light and dark theme, GitHub and the docs page render the fallbacks. Rasters are optimised (WebP/AVIF, sizes) at build time. One check keeps the figure honest: every label in `process-loop.svg` must be a phrase on process.md. Each of these files is committed under `docs/assets/img/` as the page that references it lands.

**README.md becomes a contributor page.** Its product narrative moves verbatim into Diátaxis pages — § Purpose → `docs/explanation/rationale.md` (titled "Who abcd is for"), § Roles → `roles.md`, § Artefacts → `artefacts.md`, § Process → `process.md`, § Install → `docs/how-to/install.md` — with only heading levels and relative links changed; the header block (logo, `<h1>`, the tagline `<p>` that `positioning.json` checks, badges), Install one-liner and Resources stay. The slim README points at abcdev.app and the docs pages, then lists AGENTS/CONTRIBUTING/SECURITY/ACKNOWLEDGEMENTS. The pages, the section indexes, `.abcd/site.json` and `site-src/ui.json` are committed at the paths named above; nothing in `internal/` reads README's prose, so the slimmer README breaks no test. Two consequences worth deciding explicitly: the CLI section of `install.md` now carries per-OS commands under H3s (macOS with `shasum`, Linux with `sha256sum`, a Windows H3 that says the build is planned, and an *Afterwards* H3 for PATH and older installs) while README keeps the universal `uname`-detecting one-liner — the per-OS forms are that command specialised, same URLs and checksum step, and a test should assert exactly that so the three cannot drift; and the brief's own press release (`brief/01-product/01-press-release.md`) tells the lifeboat story rather than the product-thinker story the README tells — the brief already records that as an open question; the site follows `docs/`, and the question stays with the team.

### 5.2 Build pipeline

One Cloudflare build command, in this order: `go run ./cmd/abcd site build --out site` (writes the landing page, record pages, `record.json`, `install.sh`, `_redirects`, `_headers`, `llms.txt`, `security.txt`, OG images), then `pip install -r docs/requirements.txt && mkdocs build -d site/docs`. Deploy stays `npx wrangler deploy`; the branch-preview command repeats both builds before `npx wrangler versions upload`, for the reason already recorded in `wrangler.jsonc`. `wrangler.jsonc` gains nothing but comments unless a Worker script is ever needed (it is not, for this plan). Add `mkdocs.yml`, `cmd/abcd-site/**` (or wherever the generator lives), `site-src/**` (templates and static assets) and `docs/requirements.txt` to CODEOWNERS, since they alter what the site build produces.

Where the generator lives is a judgement call for the team. The cleanest fit with the repo's conventions is a `site` verb family on the binary (`abcd site build`, `abcd site check`) so that `record.json` export, cross-reference validation and the "pinned command snippets" check reuse `internal/core`; the lighter alternative is a separate `cmd/abcd-site` tool like `cmd/abcd-gen-cli-ref`. Either way it is Go, deterministic (fixed seeds, sorted inputs, no timestamps except the build stamp), and tested by a golden-file test over a fixture record, the same way the CLI reference is gated.

### 5.3 `record.json`

A versioned schema (`schema_version: 1`) with `nodes` (id, type, lifecycle/status, title, path, dates from frontmatter or git first-commit, kind/severity where present, precomputed x/y), `edges` (typed: related, supersedes, spec, implements, builds_on, resolved_by), `mentions` (body references, deduplicated against typed edges), `releases` (version, date from CHANGELOG), `contributors` (from `git shortlog` through `.mailmap`), `assistance` (trailer tallies overall and per release), `counts`, and `health` (unresolved references, orphans, spec↔intent mismatches). Layout is computed at build (the prototype used a hub-dampened spring layout with a radial decompression so the dense core stays legible; d3-force headless in Node or a small Go port both work) so that every visitor sees the same picture and the page needs no simulation at runtime. A CI step re-exports and diffs against the committed copy so the published data can never drift from the tree; `health` findings fail the build the way `record-lint` fails CI, which forces the dangling-supersedes question (§7) to be answered rather than rendered around.

### 5.4 Pages

**Landing (`/`).** Content inventory, in order, answering the "what must go on the front page" question directly — and, after §5.0, every item names its source: the canonical eyebrow/tagline/pitch (Identity block); the headline and lede (`rationale.md` H1 and first paragraph — the "bet"); three calls to action labelled with the titles of the pages they reach; the four-panel cartoon as the hero image (the most characteristic artefact abcd has, referenced from `rationale.md`); chapter **a** Roles (`roles.md`: intro paragraph, then the two H2 sections as cards with their pre-created portraits); chapter **b** Artefacts (`artefacts.md`: intro, the who-does-what table, the three bold-lead paragraphs as cards, the cross-cutting paragraph, then the newest shipped intent whose audit verdict is MET quoted verbatim — press release and first acceptance criterion — as the only "testimonial"); chapter **c** Process (`process.md` as prose with both one-liners as copyable blocks and the Given/When/Then table, plus the loop figure); chapter **d** Install (`install.md`: intro, the CLI lead paragraph, then a tab row that is the page's structure — macOS · Linux · Windows from the CLI section's H3s, then Plugin · Build from the remaining H2s; each OS panel shows its command and prose followed by the *Afterwards* section with its tail folded; a line of links to the latest release, checksums.txt, CHANGELOG.md and all releases; the version lives in the header only); footer (file names and links). The record strip that an earlier draft placed before the footer is gone — the header's Record link is the bridge. Every `abcd …` snippet is a fenced block from a docs page and is checked against the generated CLI reference at build time, so a renamed verb breaks the build rather than shipping stale copy.

**Docs (`/docs/`).** Unchanged content; `site_url` moves to `/docs/`; Material overrides for the shared header and type; `content.code.copy`, `repo_url`/`edit_uri`, the social-cards plugin, `mkdocs-llmstxt`. The three stub sections (tutorials, how-to, explanation) stay out of scope for this plan but the landing page is designed so no first-time reader is sent to an empty tutorial.

**Dashboard (`/record/`).** Stat tiles (releases, decisions, intents, specs, issues, principles); lifecycle bars with 2 px gaps and an ordinal blue ramp for draft→planned→shipped; a release cadence strip with versions only (dates on hover); latest decisions; record health. Record health is a ratchet, not a big bang: the six unresolved `supersedes`/`spec` references that exist today (nothing checks them yet, and retired ADRs are removed under "retire the name") are committed as a baseline in `.abcd/site-baseline.json`, the build fails only on a reference that is not in the baseline, and fixing one shrinks it — the same shape as the citations baseline. Everything has a table twin for assistive tech.

**Relationships (`/record/graph/`).** One chart, two arrangements, the same bubbles; never a hairball. *By date* is the coil: records are placed one at a time in date order — frontmatter `date` where a record carries one (ADRs, from 4 May), otherwise the day its file first appeared in git — the first at the centre, each next one beside the last, a little further round and as close in as the bubbles already placed allow, so the record winds outward like a snail shell. Under the coil, concentric bands mark the months the way fare zones are drawn on a tube map: a boundary circle at the first record of each month, alternate bands tinted, the month's name at the top of each band (bands too thin to carry a name merge with their neighbour). *By links* is a force layout over the typed links only (body mentions excluded — with them it is a hairball): connected work forms islands (one of 131 records, one of 6, one of 3, fifteen pairs), the 429 records without a typed cross-reference sit on the rim in date order. Both arrangements are computed at build time (the coil is a 40-line greedy packer with 4.5 px of air between neighbours, deterministic, no overlaps, 0.3 s; the force layout is a seeded spring embedding) and shipped in `record.json`; at runtime the bubbles glide between them, a small collision pass keeps them apart, and the simulation idles once settled so nothing twitches. The viewer can drag to move and scroll, pinch or double-click to zoom (buttons and a reset too); the switch between arrangements is an explicit two-state control, never a side effect of dragging. Tapping a bubble — or picking it from search or the list — rings it and keeps it opaque while its linked records turn translucent and everything else fades; links are drawn with arrowheads where the relation is directed (`builds_on`, `supersedes`, `implements` point at their target; `related` has no direction), labelled from the frontmatter, with labels that step aside rather than overprint. Hover highlights with a ring, not a size change, so nothing around a bubble ever moves. The card keeps to what matters: the title; type and state as pills in GitHub's palette (green open/planned/proposed, purple accepted/shipped/closed/resolved — GitHub's "closed as completed", grey drafts and superseded/wontfix; severity on the critical–high–moderate–low ladder); then every date of the record on one continuum that runs the whole project — dated (frontmatter, a diamond in the type colour), in the tree since (dot), state since (ring in the state colour), last touched — with the date shown on hover or focus and spoken as one sentence to screen readers; linked records are a pull-out listing each with its relation phrased from the focused record (*builds on* / *built on by*) and its date; then the GitHub link. Back and forward buttons in the card (and Alt+arrows) walk the history of records looked at, the way a browser does; a fresh pick drops the forward trail. Body mentions stay off by default. Two data facts surfaced while building it: the spec link is recorded from both ends (intent `spec_id` ↔ spec `implements`, all 32 pairs) and 20 `related` pairs appear in both files, so the 278 stored references are 226 distinct links — the build collapses them; and issues carry no typed cross-references at all, which is why they ring the by-links view. Overlays sit in the corners and leave the middle to the chart: the arrangement switch and the Filters button (type chips, the mentions toggle, the legend) top-left; the search field top-right; full screen (Fullscreen API where it exists, a fixed overlay on iPhone Safari) and the zoom buttons bottom-right; and the card anchored bottom-left — it grows upward as far as the control row and no further, its head (title, pills, continuum) and foot (GitHub link left, back and forward right) stay put while the linked-records pull-out scrolls between them, and a record with no typed links shows the pull-out greyed and shut. On phones the card spans the width and the chart pans so the focused bubble stays above it. "Browse as a list" under the stage, in date order, is the accessible twin and the keyboard path. Every record is a circle — no squares, hexagons or diamonds; bubble size is link count; fill is lifecycle; colour names only the three durable types that stay distinguishable under colour-vision deficiency, issues are light grey and principles, RFCs and phases ink. Disclosure is graceful: the card slides in, changes height smoothly when the record changes and fades out on close; pull-outs (linked records, the list, the install tabs' "more") animate open and shut; `prefers-reduced-motion` removes all of it, and nothing drifts at rest. Earlier shapes, for the record: clustered-by-type bubbles with an orbiting ego view (dropped: clusters split what belongs together), rings-by-month with closeness as angle (dropped: a simulation where the coil is a rule), zoomable packed circles, a ring with bundled curves, lanes with arcs.

**Genealogy (`/record/timeline/`).** Five lanes over one axis, May to August: releases (ticks, each a link to its GitHub release, labels stepping outward when they would collide), decisions at their frontmatter dates, then intents, specs and issues at the day each file first appeared in git — the record carries no dates for those, so one `git log --reverse --name-status` pass at build time supplies created / entered-current-directory / last-touched for every file, and the same dates feed the relationship chart's card. Crowded days fan out into columns; a day too crowded to show one by one (the 6 July import: 64 intents) becomes a capsule with its count and the breakdown in its tooltip; issues are a histogram per day (resolved solid, open outlined) rather than 374 dots. Supersession is drawn as arcs where both ends exist (adr-32→adr-12 above the decisions lane, adr-26→itd-49 down into the intents lane) and as short dashed stubs ending in × for the five arcs that point at ADRs retired from the tree — never as arcs to invented positions. The first commit (6 July, the day adr-21 was accepted) is the dashed vertical marker: everything dated earlier was designed on paper. Every mark opens its record in the relationship chart (`/record/graph/?focus=<id>`). Rendered as static SVG at build time — deterministic, printable, no runtime library — and scrolled inside its panel on phones.

**Contributors (`/contributors/`).** Authors of record from `git shortlog -sne` through `.mailmap`; a separate bot/tool row; the AI-assistance share (822 of 1,188 commits carry an `Assisted-by:` trailer) with the agent/model breakdown and, later, a per-release trend; the policy text and a link to CONTRIBUTING.md; the page sits under the attribution escape so model names may appear. Two data facts need a rule in the build: one early commit carries "Claude" in the git author field (pre-policy) and two are dependabot.

**References (`/references/`).** The bibliography rendered from `research/references.csl.json` (citation-js with a vendored ACM style, or pandoc in a GitHub Action that commits the HTML), numbered identically to ACKNOWLEDGEMENTS.md, DOIs linked, with the CC BY-SA attribution line the CSL styles require; beside it the inspirations list, headed *Inspirations — Ideas adopted*. The page header names the two counts only (sources cited, inspirations credited); the CSL file is linked under the list rather than named in the header, and the style is not announced. The citation baseline (`.abcd/citations-baseline.json`) can later supply a last-verified date per source.

### 5.5 Design system

**Header.** A "Beta" badge sits beside the brand and "beta" in the footer line for as long as the major version is 0 — a rule on the release version, not copy, so it disappears with v1.0. A small old-style house icon leads to the top of the landing page ("Who abcd is for"); the top-level label stays lit while the viewer moves between its sub-pages (Record stays highlighted on Dashboard, Graph, Timeline, Contributors, References), with `aria-current` set on it.

**Mobile is a hard requirement, not a breakpoint.** The core — the landing page, `/docs/`, the dashboard, contributors and references — must render perfectly at 360–430 px: no horizontal scroll, no element wider than the viewport, tap targets ≥ 44 px, copy buttons that work, code blocks that scroll inside their own box, portraits that move inside their cards, the genealogy SVG scrolling inside its panel. Heavy visuals degrade rather than break: the relationship chart keeps its full behaviour on phones (tap to focus, bottom-sheet card, the chart pans so the focused bubble stays visible, bubbles scale to the disk) but is allowed to be replaced by the list view when `prefers-reduced-motion` is set or the device reports low memory; the genealogy is a static SVG so it simply scrolls. The prototype already passes a 390 px audit (scrollWidth = viewport on every route); CI should screenshot every route at 390, 768 and 1360 px and fail on overflow.

Tokens defined once for light and redefined for dark (OS preference and explicit `data-theme` both honoured). Neutrals carry a slight blue bias toward the logo's "a"; the four logo colours mark the four chapters and nothing else; the accent is the logo blue. Type: Bricolage Grotesque for display and UI, Newsreader for running prose and press-release quotes (the intents *are* press releases), IBM Plex Mono for ids, commands and data. The "not yet real" hazard-stripe mark is lifted from the cartoon's construction barrier and from the brief's own rule that ambition is visibly marked; on the site it is data-driven from the surface registry's shipped/staged flags, so it disappears when the capability ships. The graph palette was validated with the data-viz checker in both themes (the durable triad passes all-pairs CVD checks; the fourth slot does not, hence the remaining types take neutrals rather than a fourth hue). Stat tiles use proportional figures; tables use tabular figures.

### 5.6 `install.sh`

A static file, not a Worker: served from `site/install.sh` with `Content-Type: text/plain; charset=utf-8` via `_headers`, generated from a template so the README one-liner and the script share one source. Behaviour identical to today's inline command: detect OS/arch, refuse unsupported platforms with a plain-language message, download the binary and `checksums.txt` from `…/releases/latest/download/`, verify SHA-256 (refuse on mismatch or a manifest that does not list the binary), install to `~/.local/bin` (override with `--bin-dir`), never escalate privileges, print the PATH fix when needed, run `abcd version` at the end. Patterns worth copying from the leaders: wrap everything in `main "$@"` so a truncated download executes nothing (chezmoi), `curl --proto '=https' --tlsv1.2` (atuin), a visible "read the script" link next to the command (bun). The landing page keeps the "do it by hand" paragraph and the link to the releases page for anyone who will not pipe to a shell. Deferred, with a one-line note each in the plan's "later" list: `/latest/<os>-<arch>` redirects (a one-line `_redirects` rule if ever wanted), a Homebrew tap (needs a publisher step in `release.yml` and a second repo), and an attestation-verification section (the workflow already attests; `gh attestation verify --owner Partnermedia abcd-linux-amd64` should already work for releases published since the repository went public, and could be documented in `/docs/` at any time).

## 6. Phased rollout

Each phase is sized to be one intent in abcd's own idiom; the acceptance criteria below are written so the intent auditor can grade them.

**Phase 0 — prepare the move (small).** Land the README migration PR (`readme-migration/`: four explanation pages, the install how-to, the slim README, the section indexes; `docs-lint` passes on the moved text). Set `site_url` to `/docs/`, build docs into `site/docs/`, add a temporary generated `site/index.html` that redirects to `/docs/`, add `_redirects` for every current root URL, add `_headers`, `robots.txt`, `security.txt`. *Given* a visitor opens any URL from today's sitemap, *when* the new build is live, *then* they land on the same page under `/docs/` via a 301 and nothing 404s. *Given* README.md after the migration, *when* `positioning` and `docs-lint` run, *then* both pass and the strapline surface still resolves.

**Phase 1 — the landing page.** The generator renders `/` from `.abcd/site.json`: the docs pages, the Identity block and the CHANGELOG; the cartoon and the role portraits are optimised; OG card and `llms.txt` are emitted; docs get the shared header; the provenance check runs in CI. *Given* the Identity block changes, *when* the site rebuilds, *then* the hero shows the new tagline with no template edit. *Given* a verb is renamed, *when* the site builds, *then* the build fails on the stale snippet. *Given* a template gains a sentence that is not in `ui.json` or a source span, *when* the site builds, *then* the provenance check fails naming the text.

**Phase 2 — `record.json`, dashboard, contributors, references.** Export, validation, CI diff, the three data pages, per-record pages. *Given* an ADR's `supersedes` names an id not in the tree, *when* the site builds, *then* the build fails naming the ADR (or, if the team chooses tombstones, renders the retired id as such).

**Phase 3 — relationships and genealogy.** The relationship chart with its two build-time arrangements, arrowheads, full screen and list twin, the static SVG timeline with git-derived dates for intents and specs. *Given* a visitor with a keyboard only, *when* they open `/record/graph/`, *then* every record and its links are reachable in the list view. *Given* a 390 px viewport, *when* a record is focused, *then* its card is a bottom sheet and the stage never scrolls horizontally.

**Phase 4 — polish.** Cookie-less analytics (Cloudflare Web Analytics via the JS snippet, since edge auto-injection on Workers custom domains is undocumented), search across landing and record (Pagefind over the generated pages is the simplest), print styles for the timeline, a per-release assistance trend.

**Phase 5 — the SSG decision.** An ADR before Material's maintenance window closes (~November 2026): Zensical if it reaches feature parity for what `/docs/` needs (overrides, tags, search), Hugo/Hextra if the team prefers a Go-native toolchain. Because the generator already owns everything outside `/docs/`, either migration touches only `mkdocs.yml`, `overrides/` and the build command.

## 7. Decisions the team still needs to take

Whether the README migration lands as drafted (page titles — "Who abcd is for" is the one new heading — and whether the install one-liner stays in README as a registered surface or becomes a link). Whether retired ADRs get tombstone files or the superseding ADR records the retired title in frontmatter (the graph, the timeline and record-health all hinge on it). Whether the generator is a verb on the binary or a separate `cmd/` tool. Whether `/record/<type>/<id>/` pages render full bodies or summaries plus GitHub links (full bodies are the plan; they make the site the readable front door to the record, but they also mean the site republishes working-tier issue text). Whether the contributors page publishes model names (the plan says yes, under the attribution escape, with the policy linked) and how bot/tool author rows are labelled. Whether to amend ADR-30 to name the site as a third publication surface. Which persona quote rule picks the landing page's featured intent when several qualify. And, for Phase 4, whether analytics are wanted at all.

## 8. Risks

The docs tree's emptiness is the biggest product risk: a polished landing page that leads into three stub sections will disappoint, so Phase 1 should ship with at least one real how-to (install and first `abcd intent`) even though docs authoring is outside this plan. Material's maintenance window is a calendar risk, mitigated by keeping generation outside the SSG. Publishing the issue ledger makes every capture's wording public the moment it lands; it already is on GitHub, but a rendered page is more visible — the `abcd capture` convention of plain, non-identifying text holds, and the privacy-hygiene lint is the backstop. The graph's cost is front-loaded in the layout step; at ~600 nodes it is trivial, and the design (precomputed positions, canvas, table twin) scales to several thousand before Sigma.js becomes necessary. Finally, the cartoon's characters and the persona names are fictional by design; the contributors page is the one place real names appear, and it shows only what git already publishes.

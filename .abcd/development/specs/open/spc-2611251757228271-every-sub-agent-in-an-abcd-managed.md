# every-sub-agent-in-an-abcd-managed

## Summary

This spec delivers itd-2611251725190796 in two steps. Step 1 tells every sub-agent, as it starts, where the repository's conventions are and which commands print abcd's rules, and has its stop keep one line for what it skipped. Step 2 has the guard refuse a sub-agent's write until it has read the conventions file, as the product thinker ruled on 2026-11-25 (dcn-2611251823160636). The sibling spec spc-2611251757236507 wires the same verb, `hook subagent-start`, into the settings `abcd start` hands a session: the verb's name is all the two specs share, and nothing here touches `internal/core/runner`.

The file paths, the verb, the manifest's figures, the gap's id, the fact names, the marker's file name and the held git commands are fixed by this spec. Function names are suggestions, and the fixed words of each message are the implementer's, held to the content this spec lists.

### Approach

**The manifest and the shim.** `hooks/hooks.json` gains a `SubagentStart` event: one group, one command, `sh "${CLAUDE_PLUGIN_ROOT}/hooks/subagent-start.sh"`, `"timeout": 10`, no matcher and no `statusMessage`. `hooks/subagent-start.sh` is the body `hooks/subagent-stop.sh`, `hooks/stop.sh` and `hooks/stop-failure.sh` share, copied by hand: the old-home stop first, then the plugin-root binary, then the owned `PATH` binary, then the dogfood rung, and never `bootstrap.sh`. It differs from them in three places only: the event named in its comment, the verb `hook subagent-start` (five times), and its last line, `abcd: the plugin binary is missing, so this sub-agent was not told where the conventions and the rules are — install per https://github.com/intentdriven/abcd#install`, with `exit 1`. No generator writes the files under `hooks/`: searching `cmd/`, `scripts/` and the Makefile finds none, and the tests in the footprint are what hold the copies to one shape. The file is committed with mode 100644, as its siblings are.

**The verb.** `abcd hook subagent-start` (`newSubagentStartCommand`, in `internal/surface/cli/hook_subagent_start.go`, registered in `newHookCommand` and in `applyHookPlaneFailOpen`) reads the host's payload: `session_id`, `cwd`, `agent_id` and `agent_type`. The host shows a start hook no task. It answers in this order, under one deadline:

1. The payload's `cwd`, else the process directory, is asked for its checkout with `managedRootContext(ctx, cwd)` (`internal/surface/cli/hook_away.go`). A checkout abcd does not manage ends the hook: nothing on stdout, nothing on stderr, nothing written, exit 0.
2. The rules are loaded as the prompt router loads them: `rulesRootContext(ctx, cwd, …)`, then `rulesForHook(root, …)`. A set whose kill switch is on (`RuleSet.Disabled`, from the repository's file or the machine's) ends the hook the same silent way. A set that will not load is the hook failing (below), which is what the loader's own contract says of a file it refuses.
3. The conventions file is `AGENTS.md`, else `CLAUDE.md`, as a regular file at the checkout root. It is found with a stat and never opened, so nothing in it, its check word included, can reach the output. With neither, the message says nothing of a conventions file and still carries the commands and the domains.
4. The sub-agent's `told` fact is written (below), and then the message.

Steps 1 to 3 are one function, `subagentConventions(ctx, cwd, errOut) (root, file string, applies bool, err error)`, which the guard's hold reuses in step 2, so the start hook and the guard cannot disagree about where the conventions apply.

**What a repository abcd does not manage is.** The rules loader has no such test of its own: `abcd rules` in a plain git repository with no `.abcd/` prints the thirteen bundled domains, and `rules --prompt` recalls them (checked on 2026-11-25 in a scratch repository). The test reused is the one every silent hook already asks, `managedRootContext`: a `.abcd/` directory at the checkout root, or a linked worktree whose main worktree has one. `TestHookStopUnmanagedRepoSilent` and `TestAwayHooksLeaveUnmanagedRepoAlone` pin it for the other hooks.

**What is sent.** stdout is one JSON object, written once and whole, with HTML escaping off, as `emitPrompt` writes the prompt router's:

```text
{"hookSpecificOutput":{"hookEventName":"SubagentStart","additionalContext":"<the message>"}}
```

On the installed host (2.1.332) a start hook's plain stdout is not delivered to the sub-agent; only this field is. The message carries, and carries nothing else:

- The conventions file: its name, that it stands at the root of the worktree the sub-agent works in, the root this hook looked in, and that a sub-agent given another worktree reads the copy at that worktree's root. The hook cannot do better: the payload carries the session's `cwd` and no worktree of the sub-agent's.
- The two commands, since no one command prints the rules a task recalls (iss-2611251739436752): `<abcd> rules --prompt "<your task in one sentence>"`, which names the domains the task recalls, and `<abcd> rules <DOMAIN>`, which prints one domain's rules.
- The names of the domains in force: `RuleSet.Active()`, in its sorted order, with their count.
- From step 2, one sentence saying that the guard refuses the sub-agent's writes until it has read the file.

It carries no rule's text, no word of the conventions file, and nothing from the payload but the directory. An example, for this repository:

```text
abcd: for a sub-agent starting in this repository.
Conventions: read AGENTS.md at the root of the worktree you work in, before you change a file. This hook looked in /path/to/worktree; if you were given another worktree, read the copy at its root.
Rules: abcd's rules are not sent to you; fetch them from that root.
  scripts/abcd.sh rules --prompt "<your task in one sentence>"   names the domains your task recalls
  scripts/abcd.sh rules <DOMAIN>                                 prints one domain's rules
Domains in force (19): ATTRIBUTION, BUGHUNT, COMMITTING, CONCURRENCY, DECOMPOSITION, DOCUMENTATION, DOGFOODING, GRILL, INTENTS, ISSUES, LEAVING, LIFEBOAT, LOAD, OPINIONS, PII, ROADMAP, SCRATCH, SECURITY, SHELL
```

**Which binary the commands name.** Where the checkout root is abcd's own source tree (`abcdrepo.LooksLikeSourceTree(root)`, and `scripts/abcd.sh` is a regular file there), the commands name `scripts/abcd.sh`, run from the worktree root: an installed release or a dogfood build of another commit is never what a sub-agent in abcd's checkout is sent to. Everywhere else, where no `scripts/abcd.sh` exists, they name the absolute path of the hook's own executable (`osExecutable()`, the seam in `internal/surface/cli/staleusage.go`): the binary the shim's ladder chose, so it exists and is the version that named the domains. A path, the executable's or the root's, is written in single quotes where it holds a space, and is left out where it holds any byte outside letters, digits, the space and `/ . _ - + @ ~ , : =`: the commands then name bare `abcd`, and the sentence naming the root is dropped. Domain names need no such care, since the loader accepts only `^[A-Z][A-Z0-9_]*$`.

**The limit.** The whole stdout document is held to `rules.InjectionBudgetBytes` (9,500 bytes, under the host's 10,000). The loader caps neither how many domains a rules file declares nor how long a name is, so every name cannot be promised to fit. When the names would take the document over the budget, the list is replaced whole by the count and the command that lists them (`<abcd> rules`), and stderr says so. No name is ever cut, and no partial list is sent.

**The bound and a failure.** The deadline is `subagentStartBound`, five seconds, set at the top of `RunE` before stdin is read, under the ten the manifest declares. The work runs beside a timer and its output is buffered: stdout is written only when the work finished inside the bound. A failure is an unreadable payload, a rules file that will not load, git not answering before the deadline, a `told` fact that cannot be written, a panic (recovered), or the bound itself. On a failure stdout stays empty, stderr carries exactly one line (the helpers' own diagnostics are buffered and folded into it or dropped, newlines flattened), and the exit is 1: never 0, and never 2, which a Go panic would give and the host reads as blocking on other events. The sub-agent starts all the same. A spent deadline in a checkout that does not look managed (`looksManaged(cwd)`, which runs no git) stays silent at exit 0, as the other hooks do. The failure is counted in the lane marker (below) with the kind `start-failed`. The failure path runs no git: the store is the one the session-start hook noted for the session (`history.SessionRepo(session_id)`), and where there is none, the one line says the failure was not counted. Every git call the verb makes takes the hook's context, so `internal/surface/cli/testdata/hook-git-baseline.txt` gains no line.

**The sub-agent's facts.** abcd keeps what it knows about one sub-agent of one session beside the session ledgers, in the folder `stateFolder` opens (`~/.abcd.noindex/rules-state/`, or `ABCD_RULES_STATE_DIR`), in `internal/core/rules/subagent.go`. A leaf is the hex SHA-256 of `subagent`, the session id and the agent id, NUL-separated, plus a suffix naming the fact: `.told`, `.passed`, `.held` or `.unjudged`. Each fact is one small JSON file, written once and whole with `fsutil.WriteFileAtomicInRoot` at mode 0o600 and read with the guarded read `LoadState` uses. No fact is rewritten from a read, so two hooks answering for one sub-agent at the same moment cannot lose one another's write. The facts are not fields of `SessionState`: the prompt router rewrites that file whole on every prompt, and the reset hook removes it at each session start and compaction, either of which would drop a fact while its sub-agent still runs. `PruneState` already removes every file in that folder by age (`StateTTL`, seven days), so the facts need no sweep of their own. `told` holds the conventions file's name (empty for none), the root looked in, and who wrote it (`start` or `guard`). A payload with no usable `session_id` or `agent_id` gives nothing to key a fact on: the sub-agent is still told, no fact is written, and it is never judged or held.

**The stop's reading.** `hook subagent-stop` (`internal/surface/cli/hook_subagent.go`) reads the sub-agent's `told` fact. A sub-agent with none was never told, and gets no line: that is every sub-agent in a repository abcd does not manage or whose rules are off, and every sub-agent of a plugin with no start entry. For one that was told, the judgement is made on the bytes the hook already holds, by `history.JudgeSubagent` in `internal/core/history/subagentreading.go`, over the transcript's `tool_use` blocks only:

- The conventions file is read when the input of a tool call that is not itself a write holds the file's name with no letter, digit, `.`, `_` or `-` on either side of it. A file-reading call on `/any/dir/AGENTS.md`, and a shell `cat AGENTS.md` or `sed -n 1,40p ./AGENTS.md`, both count. A call that writes does not, so a refused write of the file is never its own reading. What a write is comes from one predicate the caller passes in: the host's file-writing tools in step 1 (`isFileWriteTool`), widened by the held git commands in step 2.
- The rules command is run when a tool call's `command` holds a word whose last path element is `abcd` or `abcd.sh`, followed by the word `rules`.
- Only lines holding `"tool_use"` are decoded, so a transcript at the 64 MiB cap is still scanned in well under a second.

One line is kept for a sub-agent that skipped either: its type, its id, and which was missing. With no `agent_transcript_path` in the payload, or a transcript `readSettledTranscript` cannot read, or one over `maxTranscriptBytes`, the line says the sub-agent could not be judged, and why, from a closed set. A `told` fact the guard wrote (step 2) reports the file only, since that sub-agent was never given the commands. The reading runs before the stage, recovers its own panic, and returns nothing: the hook still exits 0 on every path and stages exactly as it does today, and the stop refuses nothing.

**Where the line is kept and counted.** The line goes in the history lane's marker mechanism: a new marker, `subagent-readings.json`, beside `stage-misses.json` in `laneDir`, written under the same file lock and atomic write `noteMissAt` uses, at 0o600. It holds a count of every line ever kept, the count already reported, the first and last times, and the newest fifty lines, each with its time, the agent's type and id, and a kind from a closed set: the file unread, the rules command not run, both, could not be judged, or the start hook failed. The start hook's failure path takes this lock with a one-second timeout, so the bound and the count together stay under the manifest's ten seconds. The session-start hook reads no lane marker today, only the pending directory's (`TakePendingMiss`), so counting there is new code: it gains one read of this marker for the repository it starts in, adds one notice carrying the number of lines kept since the last notice, and records that number as reported, under the lock, so each line is counted once. `abcd history staged` lists the kept lines after the stage-miss note, newest first. Under `--json` the envelope stays the array it is and the lines go to stderr, as the other two notes do. `--all-repos` is unchanged.

**ahoy.** `detectHookManifest` raises a second gap, `hooks.subagent_start_unwired`, when the manifest is otherwise sound (`verifyHookManifest` returns nothing) and no `SubagentStart` entry reaches `hook subagent-start`, read through to the script as `eventHasCommand` reads the others. It is plugin-owned, machine-scoped, not required and not resolvable, with the step `Update the plugin.` A missing or malformed manifest stays `hooks.manifest_missing` alone. The fixture manifests the other ahoy tests stand on gain a `SubagentStart` entry, so no existing test's gap set moves.

**The guard's hold (step 2).** The guard hook's payload type gains `agent_id`, `agent_type` and `transcript_path`. On host 2.1.332 a pre-tool-use payload for a call made inside a sub-agent carries the first two and the main session's carries neither (probed by the planning session on 2026-11-25). A new arm, `subagentHold` in `internal/surface/cli/guard_subagent.go`, is asked before `fileWriteGate` for the host's file-writing tools (`Write`, `Edit`, `MultiEdit`, `NotebookEdit`), and for the shell tool once the session root has resolved, when `guard.RecordActs(command)` names a held git command. It answers in this order, and anything but the last line lets the call go on to the guard's existing checks unchanged:

1. No `agent_id`: the call is the session's own, or the host has not said whose it is. Not held, and no store is read.
2. A drive's stage (`stageActive()`): not held.
3. The sub-agent's `passed` fact exists: not held.
4. No `told` fact: `subagentConventions` is asked under `guardGitBudget`. Where the conventions do not apply (not managed, rules off), nothing is held and nothing is written. Where they apply and a conventions file stands, the guard writes `told` itself, so a sub-agent whose start hook failed, or whose plugin has no start entry, is held as well, and its refusal is what tells it.
5. No conventions file: not held.
6. A build or a drain is running for the call's checkout (`loop.RunningUnattended`, the question `hook permission-request` asks): the guard writes `passed` with the reason `briefed`, and does not hold.
7. The sub-agent's own transcript is read, with the stop hook's guarded read and cap, from `<transcript_path without .jsonl>/subagents/agent-<agent_id>.jsonl`, and judged by `history.JudgeSubagent` with the same predicate the stop uses. A reading there: `passed` with the reason `read`, not held.
8. No reading: the guard writes `held` and refuses the call with the host's deny (`denyCall`). The reason names the conventions file and the root looked in, says to read it with the host's reading tool or `cat` and send the call again, and says that a read sent in the same turn as the write may not be seen yet.

Whatever cannot be judged is not held: an agent id that is not a plain scalar, a fact store that cannot be read, git not answering inside the budget, a run state that cannot be read, a payload with no absolute `transcript_path`, and a transcript that is absent, unreadable or over the cap. Each writes `unjudged` with its reason where there is a key to write it under, and one diagnostic line. The stop's line then says so: for a told sub-agent with no reading, it says its writes were held (a `held` fact), or that they could not be judged and so were not held (an `unjudged` fact, or a write in its transcript with no fact of the guard's at all, which is what a payload that named no sub-agent leaves behind). A `passed` fact with the reason `briefed` drops the file from the line: that sub-agent's brief carried the conventions.

**The shell commands that count as a sub-agent's write.** The git commands that make a commit or send one: `commit`, `merge`, `rebase`, `cherry-pick`, `revert`, `am` and `push`. `guard.RecordActs` (`internal/core/guard/recordacts.go`) reads them as `BranchActs` reads a branch: each command of the line after the guard's own tokenizer, assignment words and git's global options stepped over, the subcommand taken by position, so `git stash push`, `git log --grep=commit` and `echo git commit` are not held. A line the tokenizer cannot split, and a subcommand a variable or a substitution prints, read as no act. No other shell command is held: no closed reading of a shell line tells a write from a read, and an edit made through the shell is held at its commit.

**How the build loop's agents are told apart.** A drive's stage is a host process abcd started with the stage's environment, which `stageActive()` reads; its settings wire no start hook, and its brief carries the conventions. A host-delegated build's implementer is a sub-agent like any other to the host, so it is told apart by its run: while a build or a drain is running for the checkout the call is made in, or that checkout is a lane of a running build, `loop.RunningUnattended` says so, and the loop's brief (`internal/core/implement/loop/brief.go`) has already carried the conventions whole. The fact `passed: briefed` is kept so later calls answer from it.

### Decisions made in this spec

1. Two steps. The start hook, the stop's reading and the ahoy gap are whole without the hold, and the hold changes the guard hook, which is reviewed on its own. Step 1's change carries no `Delivers:` trailer; step 2's closes the spec and ships the intent.
2. The hold reads the sub-agent's own transcript at the held call, and the pre-tool-use matcher does not gain the reading tool. A matcher that named it would run the guard's shim on every read of every session: `hooks/pre-tool-use.sh` blocks at exit 2 in the old-home stop and salvages a missing binary by download, the stage's settings in `internal/core/runner/wall.go` (not this spec's to change) would no longer match the manifest's, and an older binary behind a newer manifest would warn that every read runs unguarded. Against that, the transcript route changes no manifest line and no shim, costs nothing until a sub-agent's first write, and gives the hold and the stop one definition of a reading. Its cost is a path the host does not document. On host 2.1.332 the record of a tool call is in the sub-agent's transcript on disk by the time the call runs (read on 2026-11-25 from inside a running sub-agent), so a read made in an earlier turn is there at the write. A host that moves the file leaves every hold unjudged, which is not held and is said at the stop.
3. A sub-agent is judged at its stop from its `told` fact, not from a marker in its transcript. The host does record a start hook's run in the sub-agent's transcript, but that record is undocumented too, and the fact is abcd's own.
4. Naming is the test of a reading, at the hold and at the stop alike. A call that names the file without reading it passes, so the hold proves a skipped reading and never a careful one.
5. The seven git commands are the shell writes held, and the file tools' every write is held wherever it lands, the local tier included.
6. A sub-agent with no `told` fact is held too, on the guard's own asking of the start hook's test, so the hold does not depend on the start hook having been delivered.
7. A `told` fact that cannot be written fails the hook whole, and nothing is sent: every sub-agent that was told has a fact, and a store that cannot be written is counted and seen at the next session start.
8. While a build or a drain runs for a checkout, no sub-agent of it is held, one started by hand included. The loop's roles are not named to the host in a way a hook can read, so the run is the nearest fact.

### Limits the code sets

- The hook cannot know the sub-agent's worktree. The first criterion's "in the worktree the sub-agent works in" is met by naming the root looked in and telling the sub-agent to prefer its own.
- The second criterion's "the name of every domain in force" holds for every rule set whose names fit, and cannot hold for every file the loader accepts: a set that does not fit is counted and pointed at.
- The host skips a start hook's context for a sub-agent it runs with an isolated context. Such a sub-agent has a `told` fact and was not told; it is still held, and the refusal names the file.
- A hook the host kills at ten seconds counts nothing. Where a dogfood build fails, the shim runs the installed release for the same event, which can use up what is left of the ten.
- A failure is counted only where the session-start hook left a note for the session, and not in a repository that keeps its transcripts in its own checkout.
- A read and a write sent in one turn can be held once; the refusal says to read first.
- A sub-agent's facts are swept after seven days, after which it is neither held nor judged.
- abcd's own cold-reading agents are told like any other sub-agent, as the first criterion's "of any kind" says, though their definitions' blindness core gives them no project context. This spec builds the criterion as written and builds no exemption by agent type; the conflict is reported to the planning session.

# A drive carries on from one command, and says in one line when it cannot

## Summary

spc-2611141617199772 delivers itd-2611141610197753. After an interrupt, `abcd drain --drive` carries on with every run the interrupt left in the checkout, the lanes its drain lists included, and nothing else is typed. A lane the drive cannot take is set aside and the next lane opens. One stored state value says `working`, `waiting`, `stalled` or `stopped`, since when, on what and the one act open to a person, and the drive's terminal, `abcd implement status` and the board show it as the same line.

The design is the one the lab on drive operations prototyped and measured (lab-261114145658-67e1f9b, findings F-3 to F-9, F-11 and F-14 to F-17). Its two loop prototypes are 121 changed lines in `control.go` and `terminal.go`; they are the starting point for steps 3 and 1, and they are not merged as they stand. The `control.go` half of the first prototype is superseded: after this spec was written, pull request #1544 put a take-over claim with stricter conditions on the default branch, so step 1 builds on that claim and keeps only what the prototype has that the default branch still lacks. Decisions 1, 2, 4, 5, 7, 8 and 9 of the intent are the product thinker's, given on 2026-11-15 (decisions 1 and 2 reverse the run's first answers). Decision 3 and the storage part of decision 6 were decided by the run for owner review (dcn-2611141613199819), and the product thinker kept decision 3. They fix the figures the lab left to the product thinker.

The intent carries no open question. The one open note this spec carried, on the conditions of the claim now on the default branch, was answered by the product thinker on 2026-11-25: the intent's first criterion is narrowed to the claim's conditions and the claim is not widened (intent decision 10; Open Questions). The steps are ordered so that what needs no answer is built first. Steps 1 and 2, what the start still lacks beside the claim on the default branch and the interrupt, wait on no question and on no later step. The fix for iss-2611140902531015 is already on the default branch (pull request #1544), so step 1 no longer carries it. Step 3 builds decision 9: a drive whose lanes are all set aside keeps waiting. Steps 4 and 5 follow step 3, as the lab's build order has the state after the set-aside. The ninth criterion's count was settled on 2026-11-25: three lane hand-backs in a row with one key, read from `pace.stuck_refusals` (intent decision 11). This order differs from the lab's brief, which put the lane-less refusal and the set-aside before the claim. The lane-less refusal is now part of the set-aside (decision 8), so the lab's separate step for it is dropped.

Nothing here adds a command or a flag. No step raises the run-state schema version. A set-aside lane leaves nothing to clear (decision 8). A lane handed back as stuck still leaves a mark, a worktree and a branch, and the drive keeps opening lanes while hand-backs repeat (decision 7).

## Approach

### What is on the default branch today

All paths are under `internal/core/implement/loop/` unless they say otherwise.

- **The driver claim.** `claimDriverMade` (`control.go`) refuses a run whose control record names a live driver that is not this process, with the `contend` at `StageDriver`: "is driven by …, which has been alive since it took the run". `abcd implement resume --take` typed in a terminal records that terminal's login process as the driver. Since pull request #1544 (iss-2611140902531015, resolved) the claim makes one exception for a drive. Where the claim is a drive's own (`takesFromTerminal`: `Options.driverIsSelf`, not a claim in passing, and a recorded driver that names no session), `startedUnder` reads the process table again under the run's lock and takes the run only when all of these hold: there is a home to read session markers from; the walk up from the drive reaches the machine's first process; no process on that walk is named by a session marker, and no file in the markers' folder was passed over unread; the walk's answer is the recorded driver; and every live process beneath that driver is a shell, leaving out the drive, its ancestors and its descendants. The run's record then says that the recorded driver is the process the drive's shell runs under. Anything unsure leaves the run. In three cases the refusal says what kept the drive and names the way on in place of the usual remedy: a process beside the drive under the same shell, a marker file it could not read, and a table it could not read again under the lock. So a drive started in the terminal a run was taken over from takes the run when nothing else runs there, and a drive whose output is piped to another program, or that shares the terminal with a long-lived helper, still waits (F-3). `claimRun` claims nothing while a stop's mark stands or once a stop has halted the run, so a marked or halted run is reached only through `TakeRun` (`resume.go`), whose claim lets an idle live driver that claimed before the halt give way (`overHalted`) without asking `startedUnder`. `abcd implement resume` lists a run whose live driver names no session with the note that a drive started from that driver's own terminal, with nothing else running there, takes it.
- **The whole save.** `mayWholeSave` (`control.go`) lets a session replace a run file that states an earlier schema version only when the live driver its control record names is the calling process. `haltRun` (`stop.go`) saves through `saveRun`, so a signal's stop on such a run is refused while the recorded driver is still the terminal, which is so wherever the claim above has not taken the run (F-16).
- **The stop's messages.** `stopRefusal`, `waitsForItsTakeOver` and `stopMarkNote` (`stop.go`) compose the paragraph that ends a start on a signal's mark. It names `abcd implement step --run` and `abcd implement resume --take` and tells them apart by whether a stop's mark stands (F-4, F-15).
- **The drive's waits.** `terminal.idle`, `terminal.sleep`, `terminal.failed` and `terminal.limited` (`terminal.go`) are the four waits. `terminal.idleSince` is when the run last stopped moving, and `terminal.moved` clears it. Only `idle` sets it: `failed` and `limited` wait without setting it, and an outage's own clock (`terminalOutageClock.since`) starts when the failures enter the schedule, not at the first failure. `sayWait` prints a wait's sentence when its reason changes and every `terminalSayEvery`. Under `--until` `idle` never ends the run; without it the run ends after `terminalOutageLimit`, eight hours (F-5).
- **The stuck bounds.** `noteRefusal` (`stuck.go`) logs a lane's refusals for `stuckReason`, which hands a lane back after `pace.stuck_refusals` identical refusals or `pace.stuck_minutes` at one stage (`resolveStuckBounds`, 3 and 60 as bundled). It returns at once when the refusal's `Lane` is empty. `runFootprint` (`reservation.go`) refuses with no lane when the issue's record is in no status folder of the checkout, and `reserveOnLeavingLand` calls it at the landing (F-14).
- **Passed lanes.** `terminal.passedLanes` and `DrainOptions.PassedLanes` are a list held in the drive's memory that every later move leaves alone: no save, claim, reservation pushed or renewed, and no agent run (`PassedLane`, `passLane`, `passedLane`, `renewHeld`, `letGo`). A drive whose only lanes left are passed ends `TerminalPassedLanes`.
- **The end of a drive.** `terminal.ended` calls `haltOnSignal` on a stop and then `letGo`, which releases the reservation of each lane in progress unless a stop's record stands on its run. Where `haltRun` was refused, no record stands, so the reservation is released and the run is left with no mark, a driver that is the terminal, and no reservation (F-16).
- **The surfaces.** `driveLog` (`internal/surface/cli/drain_drive.go`) is the one writer of the drive's lines and of its log, `.abcd/.work.local/logs/drain-drive-<stamp>.log`, and `renderDriveEnd` and `driveEndWords` say how a drive ended. `abcd implement status` is rendered in `internal/surface/cli/build.go` and prints each run's record. The board's building line is composed in `internal/core/board/board.go` from `board.Input`, which the root command in `internal/surface/cli/cli.go` builds from `boardOutput` (`internal/surface/cli/board.go`). Its `Status` is the `statusblock.Block` that `boardStatus` (`internal/surface/cli/board_status.go`) reads through `loop.StatusLanes`; with no lane it says "building: nothing right now" (F-17).

The patches are in the lab's `state/patches/` and on its snapshot's branches `lab/drive-ops-p1` and `lab/drive-ops-p2`, both cut from the pin 67e1f9b8c9b1, which is the default branch these steps start from.

- **P1, second form** (`p1-claim-earlier-runs-2.patch`, 67 lines). In `claimDriverMade`, a live recorded driver is the drive's own when the caller is a drive (`Options.driverIsSelf`), the driver names no session, and `ownAncestor` finds it above the drive in the process table with no session marker on it; the drive then takes the run and the record says the terminal gave way. In `terminal.run`, `takeEarlier` runs before the first move: for each lane of the drain's state that is in progress or parked on its pull request, whose run carries a mark that is not from a person's stop file (`Stop.FromFile` false), it calls `TakeRun`. A person's stop is left alone. The `claimDriverMade` half is not taken, because the claim on the default branch covers the same case with stricter conditions. `takeEarlier` is still missing from the default branch.
- **P2** (`p2-set-aside.patch`, 54 lines, `terminal.go` only). `terminal.blocked` counts how long one lane has waited on something the drive cannot end, and at the bound adds the lane to `passedLanes` and `DrainOptions.PassedLanes`, says so, and clears `idleSince`. It is called at four places: the contention branch of `driveLane`, `stepRefused` for a refusal that names no lane, `takeOver` at `StageDriver`, and `tookUp`. `moved` clears the count.
- **P4** was not a loop change. It read the drive's sentences back into a state line (`internal/surface/cli/drivescreen/events.go` on the lab's branch) and read them wrong twice (F-11). Nothing of it is taken except the line's fields.

### The landing's reservation refusal (criterion 5; decision 8)

`noteRefusal` is called for every refusal a step's move returns (`loop.go`, the step's save), for a consumed receipt (`receipt_standing.go`) and from the drive (`terminal.laneRefused`, and the refusal to which `terminal.go` gives the current lane before it logs it). The loop package builds several hundred refusals, and the design review counted over a hundred built without a lane, many of which are not a lane's: the review set (`reviewset.go`), the configuration watch (`configwatch.go`) and the remote's identity (`remoteid.go`) refuse for the machine. Counting every lane-less refusal against the lane in hand would let one machine-wide fault hand every lane back in turn. So this plan does not change `noteRefusal`'s rule.

The product thinker ruled that a lane whose landing cannot find its record is set aside and not handed back as stuck (decision 8). The refusal the lab found is `runFootprint`'s (`reservation.go`), which refuses with no lane when the issue's record is in no status folder of the checkout, called by `reserveOnLeavingLand` at the landing. The set-aside is the lab's prototype's fourth call site, `stepRefused` for a refusal that names no lane and is not a wait by design, limited to this refusal, so a machine's refusal is counted against no lane. The lab measured it: set aside at +36m21s under `--until` and at +30m0s without it, both other lanes landed, and nothing was left to clear (F-9). Its cost is that the lane holds the drive for the stuck bound's minutes, and a drain that a host session steps has no set-aside, so the refusal still goes uncounted there (F-14). The lab's separate step that names the lane on the refusal, which would hand it back as stuck, is dropped, and `reservation.go` is not edited.

### Set aside and go on (criteria 4 and 5; decisions 3, 4, 5 and 8)

P2's `blocked` is built in `terminal.go` with these changes from the prototype:

- The bound is the stuck bound's minutes, read through `resolveStuckBounds`, not a constant of thirty minutes (decision 3).
- The call sites are the three the stuck bounds never count: a run the drive cannot claim (`takeOver` at `StageDriver`), a run it cannot take up (`tookUp`), and a contention at the lane's opening (`driveLane`). The fourth is `stepRefused` for the landing's missing-record refusal (decision 8, above).
- The words are the set-aside's own. A lane set aside is said as "set aside", with how long it waited and the refusal's reason, and `renderDriveEnd` and `driveEndWords` (`internal/surface/cli/drain_drive.go`) stop saying "since this drive may not save it" for a lane that was set aside for another reason.

One of the lab's three fixtures no longer reaches a set-aside: the own-terminal fixture never does, because the claim on the default branch takes that run at once. A run its own terminal holds that the claim leaves, because a process runs beside the drive or a marker file cannot be read, is a run the drive cannot claim, and it is set aside at the bound like any other. So this step's fixtures are the lab's two missing-record fixtures, the three call sites above, and the three cases the lab did not try: two lanes blocked at once, a block that clears just after the set-aside, and a drain with a cap of one. A fixture for the second try (decision 5) is added.

The prototype's set-aside is a passed lane: the drive writes nothing for it, so its reservation is neither released nor renewed, and it is in the drive's memory alone, so only a later start tries it again. The first half is the ruling: a set-aside lane's reservation is left to lapse (decision 4), which needed itd-2610222215485265's press release and mechanism test amended (iss-2611150635298371); that amendment was made on 2026-11-25 (its decision 12), so nothing now holds this step's merge on it. The second half is changed by decision 5: after the other lanes are done the same drive tries each set-aside lane again, so a set-aside lane leaves `passedLanes` then, with a new bound for its second wait and a guard against a lane that flaps; the step plans both, and the prototype does not have them. When every lane left is set aside the drive does not end (decision 9): it keeps waiting, retries the set-aside lanes every hour until its end time, and the line reads `waiting`. The hourly retry is a named end for the stall rule, which decision 6 does not count as one for a look-again time, so step 4 reconciles the two before it writes the stall rule. The cost the product thinker accepted is a drive process that stays running, mostly idle, until its end time.

### Claim at the start (criteria 1, 2 and 3; decisions 1 and 2; not built or tested in the lab for decisions 1 and 2)

The claim that takes a run from the drive's own terminal is on the default branch (above), so this step builds neither `ownAncestor` nor an `own` branch in `claimDriverMade`, and it does not edit `control.go`. The claim already refuses a live driver in another terminal and a driver under a session marker (the lab's fixtures four and five), and its tests in `control_terminal_test.go` cover both. What is left of P1's second form is built in `terminal.go` and `stop.go`:

- `takeEarlier` before the drive's first move walks every interrupted run in the checkout, not only the lanes of the drain's state (decision 2). The prototype walks the drain's lanes, so this is not built or tested in the lab, and this step tests it, a run parked on its pull request whose drain was replaced included.
- `takeEarlier` takes through `TakeRun`, whose claim lets an idle live driver that claimed before the halt give way and never asks `startedUnder`. So the claim on the default branch does not stop `takeEarlier` from taking a halted run from a live driver in another terminal, which the third criterion says is left. This step keeps that case out of `takeEarlier` and tests it.
- A person's stop that still stands is not taken, and `passOverHalted` and `waitsForTakeOver` keep their words for it. Once the person has lifted the stop, the next start takes up the run it halted (decision 1). The prototype leaves a lifted stop alone on purpose, so this is also not built or tested in the lab, and this step tests it.
- In `stop.go`, the remedy of `stopRefusal` for a signal's mark and the unsettled branch of `stopMarkNote` no longer send a person at a drive's terminal to two commands. Where the reader is a drive and the run is any interrupted run in the checkout, the drive takes the run and says "took over"; the paragraph remains for a host session's `abcd implement step`, which is not a drive.
- `TestASignalAtTheArmingStepWaitsForItsTakeOver` (`stop_drive_test.go`) states the old rule and is rewritten. `TestANewDrainNamesARunASignalParked` states the case decision 2 now answers, a run parked by a signal whose drain was replaced, and is rewritten to say the drive takes it.
- The lab's first fixture is added as a drive's start, where three lanes land and the start is the only command. The claim's own tests prove the take at the claim, not across a drive's lanes.
- Review of the step settled four bounds (2026-11-26). A run that names no driver is taken only on a sign its session ended, a settled mark or a lapsed reservation; otherwise it is left and named. `takeEarlier` takes issue runs only: an intent's build is left and named with `abcd implement resume --take`, since a drive does not start agents on a build it did not open. A lane the drain lists short of its pull request is left to the drain, where `takeUp` takes it by the same rules, so it is never stepped outside the drain's bounds; a lane passed over is passed over in the drive's memory and never written `halted`; the drive's closing words for such lanes still give the version reason ("since it may not save them"), and step 3 (L3b) rewrites them. A run `takeEarlier` steps that no drain lists is halted on a signal and let go at the drive's end as the drain's own lanes are, and the walk checks for an interrupt and the bound between runs.

### An interrupt leaves every lane marked or reserved (criterion 10)

With the claim on the default branch, a drive that takes its own terminal's run is that run's driver, so `haltRun`'s whole save is the driver's and the stop is applied at any schema version the build reads. One case remains: a lane the drive holds whose run it could not claim, which includes a run its own terminal holds where a process runs beside the drive or a marker file cannot be read. There `haltOnSignal` records, in the drive's memory, each run whose stop could not be applied, and `letGo` and `leftHeld` leave that run's reservation as they already leave one whose stop record stands. The lane then keeps its reservation until its lease lapses, and the next start reads a reserved run, not an unreserved one with no mark. The drive's end says when each kept reservation lapses, a run with members naming every member's. Review moved one case here from step 1 (2026-11-26): a run no drain lists that a drive's end let go with no mark, at its bound or for a limit, is taken up by the next start by step 1's rules, reserved again as it is stepped, since no drain hands it out again.

### The state as a value from the loop (criteria 6 to 9; decisions 3, 6 and 11)

The loop computes the state; no surface reads it back out of a sentence.

- **The value.** A new file `drivestate.go` holds `DriveState`: the state word; `Since`; `Until`, absent where the wait names no end; `On`, the issue and its stage or the thing outside the drive; `Do`, one act or nothing; the counts of lanes done, in flight, set aside and handed back; the drive's process id and start time; `Written`; and `Next`, the time by which the drive will have written again. It is set where the loop already knows each field: `sleep` and `idle` (the wait, `idleSince`, the refusal's `Remedy`), `failed` and `limited`, `moved` (working), the set-aside, and `ended` (stopped). A wait's own `Remedy` is used as `Do` only where it is a person's act at a terminal; a remedy written for a host session, such as handing back a receipt, is never shown (F-21).
- **Which waits have a named end.** Two on the default branch, and a third by decision 9: the pace window, whose move names `NextEligibleAt` (`moveWait`, `terminal_wait.go`), and a rate limit whose reset the provider names (`limited`). Every other time the loop holds is the time of its next look, not an end: an outage's next try on its schedule (`terminalOutageClock.fail`), a look at origin (`OriginWait.NextProbeAt`), a look at a cap or at work others hold (`WaitingUntil`), a probe of a limit that names no reset, and `idle`'s look-again. Those waits carry no `Until`. Decision 9 adds a third end: the hourly retry of set-aside lanes while every lane left is set aside, which carries an `Until` at the next retry, so `idle`'s look-again is an end only in that case. The lab's design also lists a lease's lapse; a wait on another holder's reservation gets an `Until` only if the refusal on the default branch carries that time, which step 4 checks before it sets one.
- **The start of a wait.** The time rule needs to know when the drive last stopped moving, and today only `idle` records that. Step 4 gives `failed` and `limited` their own start: each sets the same time at the first failure, or the first limit, after a movement, if it is not already set, and `moved` clears it. Without this an outage has no `since` to measure from.
- **The stall rule by time.** `stalled` replaces `waiting` when a wait with no `Until` has lasted the stuck bound's minutes since that start, whatever reasons the waits gave in between, which is the prototype's first error written as a test. So an outage reads `waiting` for the stuck bound's minutes and `stalled` from then on, with the `since` of the last movement, which is what the lab's row for the incident note's event 5 and its drawings show ("stalled 2h44m · on outage"). The drive's behaviour does not change.
- **The stall rule by hand-backs.** Three lane hand-backs in a row (`DrainRoute.From == "lane"`) that share one key make the state `stalled`, the figure read from `pace.stuck_refusals`. The key is the hand-back's kind, the stage the lane was at and the check of its last logged refusal; the reason's text is not in it. A lane that reaches its pull request, or a lane hand-back with another key, clears the run; a hand-back at the judgement, by the rule or at a reservation neither counts nor clears it. The line reads `stalled` since the first hand-back of the run, on the count, stage and kind, with the act that it needs a look, and the drive keeps opening lanes (intent decisions 7 and 11).
- **The file.** The drive writes the value whole, by rename, to `.abcd/.work.local/logs/drive-state.json` in its checkout each time a field changes. The file carries a version of its own. It is not run state, and the next drive overwrites it. Nothing was stored in the lab, so the stored form rests on no measurement.
- **Telling a drive that is gone.** A reader that may read the process table checks the recorded process by its id and start time, as `claimDriverMade` and `mayWholeSave` (`control.go`) check a run's recorded driver: `readProcs`, then `sessionname.Table.Alive` on the recorded host, with the same slack the driver's record keeps. A process that is gone reads `stopped`, not heard from since `Written`. `abcd implement status` and the board read this way. This is not the lab's rule in detail: its design says only "a reader that finds the drive's process gone".
- **The next-write time is a fallback.** It is for a reader that may not read the process table, which is the status line of itd-2611141507299828. The drive rewrites the file at every look of a wait, and while an agent is in its call or a preflight runs, at each tick of `renewing` (`terminalRenewTick`, five minutes), which already runs through both; `Next` is the end of the current stretch plus a margin. A stretch of `sleep` can be as long as `terminalRenewEvery`, an hour, so a fallback reader can show a dead drive as `waiting` for up to that long. It never shows it as `working` for longer than one tick and its margin. The seventh criterion is met in full only by a reader of the process table, and the status-line draft's freshness bound is that draft's to set against this.
- **The line.** One function composes the displayed form, `<state> <elapsed> · on <what> · you: <act>`, from the value; where the act is nothing, it reads `nothing to do` while working or waiting and `needs a look` while stalled or stopped.
- **The surfaces.** `internal/surface/cli/drain_drive.go` prints `state: <line>` when the state word, `On` or `Do` changes. `abcd implement status` (`internal/surface/cli/build.go`) prints the line above the runs' records. The board does not get it through its status block: `boardStatus` (`internal/surface/cli/board_status.go`) returns a `statusblock.Block`, which has no field for a drive's state and is also what the site renders. A new reader in `internal/surface/cli/board_drive.go` reads the file; `boardOutput` (`internal/surface/cli/board.go`) gains the value for `--json`; the root command in `internal/surface/cli/cli.go`, which builds `boardOutput` and `board.Input`, hands the composed line to the renderer; and `board.Input` and the building line in `internal/core/board/board.go` show it in place of "nothing right now". A missing, unreadable or newer-version file shows no line and names why on stderr.

The loop package (`internal/core/implement/loop`) has open lanes on files these steps also edit: `control.go`, `validate.go`, `reviewset.go`, `state.go`, `land.go` and others. So each step below names its files exactly, no step starts until the package's open lanes are on the default branch, and each step is cut from the default branch as it then stands. ### The run-state schema

The lab's stop condition forbade a prototype that raised the run-state schema, and none did. No step here raises `SchemaVersion` (26 in `state.go`): the set-aside lives in the drive's memory, the claim adds a line to the run's record through `saveRecord`, which keeps the version the file states, and the drive's state is a file of its own. One risk is stated plainly. Criterion 10 is met for a run the drive could not claim by keeping its reservation, not by writing a mark, because writing the mark's record line is a whole save that would raise an earlier-version file out of its driver's reach. If review asks for the mark on every such run, that needs a save path that does not exist today, and it is a decision to take back to the product thinker and not one to build inside step 2.

## How the Acceptance Criteria are met

The criteria are numbered in the order the intent lists them.

1. A run taken over from the drive's own terminal is taken: `takesFromTerminal` and `startedUnder` in `claimDriverMade`, on the default branch since pull request #1544, where nothing but shells runs beneath the recorded driver besides the drive and every session marker can be read. Its claim-level tests are in `control_terminal_test.go`. Step 1 adds the lab's first fixture as a drive's start: three lanes land and the start is the only command. Where the claim's conditions do not hold the run is left waiting and the refusal names the act that frees it, which the narrowed first criterion states (decision 10).
2. An interrupted drive carries on with every lane its drain lists, and takes every other interrupted run in the checkout: `takeEarlier` before the first move, and the `stop.go` messages (step 1). Proved by the lab's second and third fixtures, at this version and at version 25, settled and unsettled, and by a new fixture for a run whose drain was replaced.
3. Another live session's run and a person's stop that still stands are left and named, and a lifted stop's run is taken up: the claim on the default branch takes only from a recorded driver that names no session, with no session marker on the drive's walk, and `takeEarlier` skips a run whose stop file still stands and a halted run whose live driver is in another terminal (step 1). Proved by the claim's tests on the default branch for the lab's fixtures four and five, by step 1's halted run with a live driver in another terminal, and by the stop fixture changed to take the lifted run; that the drive goes on to other work is step 3's.
4. A lane the drive cannot take is set aside at the stuck bound's minutes and the next opens: `terminal.blocked` (step 3). The reservation is left to lapse, the lane gets another try after the other lanes are done, and when every lane left is set aside the drive keeps waiting and retries hourly until its end time (decision 9).
5. The landing's reservation refusal no longer holds the drive without bound: it is set aside by step 3's fourth call site. A machine's refusal is counted against no lane.
6. One line, the same in three places: `DriveState`, its file and the one composing function (steps 4 and 5). Proved by a test that renders the terminal's `state:` line, `abcd implement status` and the board from one stored value and compares the three.
7. A drive that ended without a last line reads `stopped`: the reader's check of the recorded process (step 5).
8. Stalled by time, with the `since` of the last movement, and never before a named end: the rule on the wait's start and `Until` (step 4). Proved by a wait whose reason alternates with the pace window's line, by an outage that reads `stalled` past the bound, and by a drive whose every lane left is set aside, which reads `waiting` on its hourly retry and never `stalled` (decision 9).
9. Stalled by lanes handed back in a row: three lane hand-backs in a row with one key (kind, stage and check), read from `pace.stuck_refusals`, make the line `stalled`; judgement, rule and reservation hand-backs neither count nor clear it, and a lane that reaches its pull request clears it (intent decision 11, 2026-11-25). The drive keeps opening lanes (decision 7).
10. An interrupt leaves every lane marked or reserved: the claim on the default branch makes the drive the driver where it takes the run, and `letGo` keeps the reservation of a run whose stop could not be applied (step 2). Proved by the lab's interrupt fixture at version 25 and at this version.

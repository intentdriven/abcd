# The drain fixes several small issues of one kind in one place with one pull request

## Summary

The drain opens one issue run per issue today. This spec lets one issue run carry several issues of one category in one directory: a lead issue and up to `drain.bundle_max - 1` members. The run keeps one lane, so the bundle gets one branch, one review set per round, one preflight and one pull request. Each member keeps what a single issue has today: its own eligibility, its own judgement, its own reservation, its own resolution commit and `Resolves:` line, and its own hand-back. A bundle that fails as a whole is split back into single lanes. A drain whose cap is 1, or that finds no second issue, behaves as it does today. Each drain reports its own figures. The intent's forty-issue comparison is counted once by hand from the forge, not by this spec's code. Six steps, each one pull request. Bundling stays off by default until the split and the figures have landed.

## Approach

### What is on the default branch today, and every place that assumes one issue per lane

Read at 81739e558.

- **The drain's lane** is `DrainLane{Issue, RunID, OpenedAt, Outcome, PR}` in `internal/core/implement/loop/drain.go`. The drain state's version is 3. `drainMove` walks the eligible set in drain order. For the first issue it can take, it reserves the issue (`reserveForJudgement`, footprint from `issueFootprint`, which is the one path its `found_at` names). It then asks one judgement (`st.Judging` holds one request). On a no it calls `startLane(repoRoot, v.ID, lane)` and returns. A move opens at most one lane.
- **Taken and passed over** are judged by issue id against `DrainLane.Issue` (`DrainState.taken` in `drain_readmit.go`) and against a run's `Key` (`r.Key == v.ID` in `drainMove`). `Start` finds a run to resume by its `Key` (`liveRun` in `loop.go`).
- **The run** is `State` in `state.go`, version 29. An issue run has `Key` set to the issue and `Issue()` returns it. It has one `ReservedAt`. A record line (`Entry`) names no issue.
- **The reservation** lives in `reservation.go`. It is `refs/heads/abcd-reserved/<key>` for `run.Key` alone, and it is renewed, fenced before the push and the arming, and tombstoned or released per run. `widen.go` widens that one hold to what the branch changes beyond it (`receiptHoldGaps`), and `unheldPaths` reads the hold by `st.Key`. The drain's lease renewal (`drain_lease.go`) and `renewruns.go` renew per run.
- **The other acts on `st.Key` alone**: the stop's release (`stop.go`); the drive's let-go, take-over, take-up and its record comparison on take-up (`releaseReservation`, `releaseReservationAt` and `recordMovedOn` in `terminal.go`); the drive's let-go of a judgement's hold (`letGo` releases `st.Judging`'s one hold, and `leftHeld` names it); `letGoAtLand` (`hold.go`) on `st.ReservedAt`; the pause's state fingerprint (`runner_pause.go`), which zeroes `st.ReservedAt`; and `abcd implement check`'s open-issue and peers checks (`check.go`), on `res.Key`.
- **The brief** is rendered by `issuebrief.go`, which reads one issue's record and remedy.
- **The receipt** is checked in `receipt.go`. It must resolve the run's issue (`resolvesIssue`), and `handBackGaps` refuses resolves beside a `handback`, so a lane either fixes everything or hands everything back. `Lane.Resolves` is already a list, capped at 50, and a single lane's receipt may resolve other captures beside its issue. `recordReceipt` only adds or replaces resolutions.
- **The hand-back** is `handBackLane` in `handback.go`, which hands back the whole lane. Its callers are `stuck.go` (`handBackStuck`), `schedule.go` (fix rounds spent), `loop.go` (the receipt's own hand-back), `receipt_standing.go` (a late writer), `terminal.go` (the drive's `dropRun`) and `drain_finish.go` (a pull request closed unmerged). Every step that hands back but `dropRun` releases the reservation itself: `releaseAfterWrite` (`handback_release.go`) calls `releaseOnHandBack` (`reservation.go`), which pushes a tombstone of the hand-back's kind on `st.Key` before any drain move reads the lane. `laneOutcome` in `drain.go` reads one hand-back per lane, `routeHandBack(l.Issue, …)` routes it, and `releaseHandedBack` reuses the step's `reservation_released` line or releases `run.Key` again. `releasedThisHold` reads the run's record for any release line. `dropRun` ends a lane whose take-up was refused while the run held nothing: it hands the lane back, sets `st.ReservedAt = nil` and pushes no release (`terminal.go`, the comment on `dropRun`). The spot-check's `routedLane` (`handback.go`) maps a route to a lane by issue.
- **The landing** in `land.go` already writes one `Resolves:` trailer per entry of `lane.Resolves` and resolves each record (around lines 586 to 607). `prTitle` and `prBodyParked` name `st.Issue()` alone.
- **The finish** is `finishMerged` in `drain_finish.go`, which marks one lane done per merged pull request, and only the current drain's lanes are marked (`drain.go`, around lines 913 to 918). A new drain replaces the drain's state. `drainCounts` counts every lane with a pull request, merged or not, and counts no issues.

### The run carries members (step 1; decisions 1, 8, 9 and 13)

`State` gains `bundle`, a list of members. Each member has the issue id, its footprint, its `reserved_at`, a `hand_back` once it is handed back alone, and `split` once the drain has split the run. `State.Issues()` returns every issue of the run, the lead and each member, that has not been handed back alone; a lead handed back alone is left out like any member. `covers(id)` reports whether the run still carries `id`: true for an issue in `Issues()`, and false for an issue handed back alone and for every issue, the lead included, of a run the drain has split (step 5). So a run no longer holding an issue is never found as that issue's run.

Every act that iterates the run's reservations uses `Issues()`:

- the renewal, the push fence, the land fence and the release on landing;
- the release on hand-back (`releaseOnHandBack`), which in this step releases each issue with the hand-back's kind;
- the stop's release (`stop.go`), which releases each issue plainly and clears every member's `reserved_at` with the run's;
- the drive's let-go and its release for a usage limit (`terminal.go`), which release each issue plainly, and `dropMovedRun`, which tries again each issue's own let-go release that did not reach origin, by the `issue` on its lines;
- the take-over and take-up (`reserveTaken` in `reservation.go`), which hold each issue again in `Issues()` order, and `recordMovedOn`, which compares every issue's record on the default branch before anything is pushed, so a take-up whose member's record moved is refused as the lead's is, having pushed nothing. A take-up that has held some issues again and then meets one that backs off to another holder, or any other refusal, first releases plainly every reservation it made fresh in that call, and only then returns the refusal, naming the issue it stopped at. The run is left holding nothing and its state unchanged, which is what `reserveTaken` promises for one key today ("a refusal leaves the run unchanged") and what `dropRun` relies on. A member whose fresh hold could not be released is named with when its lease lapses, as `leftHeld` names a hold today;
- `letGoAtLand` (`hold.go`), which reads a run as let go only when no issue of it is held;
- the pause's fingerprint (`runner_pause.go`), which zeroes every member's `reserved_at` with the run's, so a renewal does not read as a change;
- `abcd implement check` (`check.go`), which runs the open-issue and peers checks for each issue of a run with members.

Each reservation line in the run's record names the issue it is for, in a new `issue` field on `Entry` written only in a run with members. The widening judges the branch against the members' footprints together, and widens the hold of the first issue in `Issues()`, the lead while it is held. `unheldPaths` reads that hold, not `st.Key`'s. `widenOnto` moves the paths widened onto one issue's hold to another's, widening the second before the first is released, for step 2 to call when the issue holding the widened paths is handed back. `covers(id)` replaces `r.Key == v.ID` wherever the drain asks whether a run holds an issue. A run with no members writes no `bundle` key and no `issue` on its lines, so its file differs from today's only in `schema_version`. `resume.go` and `validate.go` keep naming the run by its key, which stays the lead's: the members are named by the drain's summary and the run's state.

Migration: version 30. Version 29 is its strict subset, read as a run with no members and written back at 30. A file of version 29 or lower carrying `bundle`, or an `issue` on a line, was not written by that version and is refused naming the key. Releases that write 29 refuse a version-30 file as a newer abcd's before any strict decode. This is the same pattern as versions 26 to 29 in `state.go`. The lane receipt stays at version 1 (decision 9).

Step 1 starts only after the change that makes `abcd build` reserve only the step it opens next has merged, from the default branch as it then stands, never by rebasing mid-flight. That change rewrites the hold checks in `widen.go` and the reservation acts in `reservation.go` that this step loops over members, and until it lands `abcd build` reserves every remaining step's packages. The builder re-reads `SchemaVersion` in `state.go` and `DrainSchemaVersion` in `drain.go` then: 30 and 4 are this spec's only if the default branch still holds 29 and 3, and otherwise the next free numbers are taken and the migrations are written from them.

### The brief, the receipt and the landing of a bundle (step 2; decisions 6 and 13)

The issue brief renders every member's record and remedy from the lane's base, in drain order, with the lead first. It asks for one commit per member, with each commit named in that member's resolution. It asks the implementer to name every issue of the run still held exactly once in every receipt, in `resolves` or in `handbacks`, so a fix round's receipt names each resolution's commit afresh. `handbacks` is a list of `{issue, kind, reason, home}`, each checked as `handBackGaps` checks a lane's hand-back. In a run with members the receipt check refuses:

- an issue of the run still held named in neither list, or in both;
- an issue that is not a member, which a run without members still may resolve as today;
- a top-level `handback`;
- an issue handed back whose resolution commit from an earlier round is still reachable from the receipt's head, naming the commit, so its change is off the branch before the lane goes on.

A run without members refuses `handbacks` and is otherwise checked as today.

A member handed back, in the first round or a later fix round, is recorded on the run's member. `recordReceipt` takes its resolution off `lane.Resolves`, so the landing writes no `Resolves:` for it. Its reservation is released with its tombstone of its own kind through the same release a lane's hand-back uses, and the release line names the issue (step 1). `releasedThisHold` judges each issue by those lines, so a member released alone is never released again and its line is never read as another issue's release. When the issue handed back holds the paths the lane widened, the lead handed back alone among them, those paths are first moved onto the next issue in `Issues()` with step 1's `widenOnto`, so the pinning tests a fix adds stay held. If every issue, the lead included, is handed back, the lane is handed back as today. Each issue was then already released with its own tombstone as it was handed back, so the lane's hand-back releases nothing more.

The landing already writes one `Resolves:` per resolution. In a run with members the records commit's body says it is the landing of a bundle and names the lead and every member, whether resolved or handed back, in prose and never as a trailer. A run without members writes today's body. `prTitle` names the area and the count, for example `fix(.abcd/development/brief/04-surfaces): 4 issues, iss-A and 3 more`. The body lists each member with its resolution, and gives a `Refs:` line for each member handed back, so every record id the text names carries a trailer.

### The cap and who joins (step 3; decisions 2, 3, 4, 9 and 12)

`drain.bundle_max` is a new key under a `drain` namespace. It is resolved through `layered` as the pace keys are (`pace.go`): the repository's `.abcd/config.json` over the machine's `config.json` over the bundled default, from 1 to 10. The bundled default is 1 in this step and stays 1 until step 6 raises it to 5 (decision 12), so a drain bundles only where a person sets the key until the split and the figures exist. The namespace is claimed, so a misspelt key is refused naming the file. The cap is read once when a drain starts and kept on its state as `bundle_max`, with its layer and origin, as `Pace` is kept. A running drain keeps its cap.

`bundleCandidates` is a pure function over the plan's dispositions, the lead and the cap. It returns the issues after the lead in drain order that:

- are eligible;
- have the lead's category exactly;
- have the lead's area: `path.Dir` of the `issueFootprint` path, or the path itself when it is a directory in the checkout;
- are not of the `security` category;
- have an area other than the repository root.

A member's severity may differ from the lead's. The order chooses each lane's lead, and a member may be taken ahead of an older or a `nitpick` issue in another area, as the dated amendment of 20 Nov 2026 to adr-2609291342092738 records (decision 11). The lead itself must pass the same area and category tests to be bundled at all; otherwise its lane opens alone. `abcd drain --dry-run` shows, under each eligible issue that would lead, the members its next lane would take. It also says that judgements, reservations and `reservation.max_live` may make the bundle smaller.

Migration: drain state version 4 is defined whole in this step: the drain's `bundle_max`, a lane's `bundle` (member ids) and `split`, the drain's `forming`, and a lane's `ci_minutes`. Each field is written only by the step that uses it, so no later step raises the version again. Version 3 is its strict subset, read as a drain with the bundled cap's layer recorded as `bundled` and no bundles, and written back at 4. A version 3 file carrying any of them is refused naming the key, and releases that write 3 refuse 4 as a newer abcd's.

### The drain forms and opens bundles (step 4; decisions 3, 4, 5 and 8)

After the lead's judgement answers no, the drain does not start the lane at once when `bundleCandidates` is not empty and the cap is above 1. It records `forming`: the lead, its hold, and the members judged so far with their holds. The rest of the move, and each move after it, takes the next candidate the way the drain takes an issue today:

- it passes over a candidate that is held, skipped, lapsed or already run, as now;
- it reserves the candidate (`reserveForJudgement`) and asks its judgement;
- a no adds it to `forming`;
- a yes routes it as today, and it leaves the bundle.

The holds of the lead and the members are kept across moves. They are added to the move's `judgeHolds` as kept, so `settle` does not release them on the way out. `renewInProgress` renews them at half their lease. The lane opens when no candidate is left, the cap is reached, or the person's live reservations would reach `reservation.max_live` with the next one. At the cap of reservations the bundle opens as it stands rather than waiting. A forming bundle can hold up to `bundle_max` of the person's live reservations across several moves, which leaves fewer for other work in that time. That cost is accepted, and lowering the cap is its remedy. `startLane` takes the members through `Options`, and `Start` writes them on the new run with the hold each was reserved on, as `heldReservation` does for one issue today. `liveRun` looks runs up with `covers`, so `abcd build <member-id>` in the copy that holds the bundle resumes the run that carries the member and names its lead, rather than opening a second run on it. In another copy the member's reservation is another's, and the start is refused as today. A member handed back alone while its bundle is parked is no longer covered, so a person's `abcd build <member-id>` finds no run that carries it and opens the member's own run, as for an issue no run carries, rather than resuming the bundle.

A stop, a pace window that elapses, or an origin that does not answer while a bundle is forming keeps `forming` and its holds, as `st.Judging` is kept today. A drain that ends releases every forming hold plainly, with no tombstone. The drive's `letGo` (`terminal.go`) releases every forming hold plainly and clears `forming`, as it releases `st.Judging`'s hold, and `leftHeld` names each forming hold it would have released. `DrainState.taken` and the run lookups count a member as taken. The lane's routing reads each member handed back alone (step 2's record) and routes it with `routeHandBack(member, "lane", …)`. A whole-lane hand-back routes every member's hand-back in this step, and step 5 replaces that with the split; the bundled default of 1 keeps this off unless a person sets the cap. A pull request closed unmerged is a person's word on the whole lane, never a split: every issue still held is handed back with the `closed` kind, as a single lane's is. `finishMerged` marks the lane done for every member, and `routedLane` and `DrainSummaryLine` name every member.

A cap of 1, a lead that is not bundleable, or a lead with no candidates goes through the path the drain takes today, with no `forming` written. The test for criterion 8 compares that drain's state, run state, brief, receipt check, pull request text and summary with a fixture of today's. It masks exactly the schema versions and the drain state's `bundle_max` with its layer and origin, and nothing else. Step 6 extends the same test to mask the figures it adds to the summary and `--json`.

### A failed bundle is split (step 5; decisions 7, 13 and 15)

The split starts in the step that hands the lane back, because that step releases the reservation itself before any drain move reads the lane. In a run with members, `releaseOnHandBack` releases every issue in `Issues()` plainly, with no tombstone, for a whole-lane hand-back: `VerdictUnachievable` at the fix-round cap (`schedule.go`), `handBackStuck` (`stuck.go`) and a late writer (`receipt_standing.go`, whose release is made in `loop.go`) all reach it through `releaseAfterWrite`, so no other copy reads the issues as a person's. The drive's `dropRun` (`terminal.go`) does not reach it and needs no release: it hands back a run that holds nothing, which stays true for a run with members because step 1's take-up released what it had re-held before it refused. A lane hand-back made by the receipt's `handbacks` for every issue (`loop.go`, step 2) releases nothing more, since step 2 released each issue with its own tombstone, and a pull request closed unmerged tombstones each held issue with `closed` (step 4). `releaseHandedBack`, which the drain calls as it reads the lane, judges each issue by the `issue` on its reservation lines (step 1), as `releasedThisHold` does from step 2, so a member released alone earlier is never released twice, and its release is never read as the others' release: the issues still held are released.

The drain then does not route a hand-back. It marks the drain lane `split`. It keeps each member's judgement, and the judgements are kept by remedy digest, so none is asked again for the same remedy. Each issue the lane still held is then taken up again in drain order as a bundle of one, which the drain never bundles again while it runs. An issue that then fails its own fix rounds is handed back as today. A member already handed back alone stays a person's and is not taken up. A lane handed back because every issue was handed back in its receipt (step 2) is not a split. Those issues are a person's.

A plain release frees each issue to every copy at once. Between the step's release and the drain's take-up of the singles, a peer's drain or `abcd build` may reserve one of them. The split then finds it held by another and passes it over, as it passes over any held issue, and routes nothing for it. This is what a plain release means, and it is accepted: the issue is being worked, by whoever now holds it.

**A bundle the drive drops is split, not routed whole** (dcn-2611201534051375). `dropRun` ends a lane whose take-up was refused because one issue's reservation backed off to another holder, or one issue's record moved on the default branch while the run was let go. In a run with members the refusal names that issue (step 1), and in this step `dropRun` records the drop on that issue alone, as its member's `hand_back` or the lead's, with the kind and reason a dropped lane carries today, before it hands the lane back. It still pushes nothing. The drain reads the lane as a whole-lane hand-back with one issue handed back alone: that issue is routed alone, as a dropped single lane is today, with a flag that names who holds it or that its record moved. Every other issue, which the take-up released before it refused, is taken up again on its own as above. Routing the whole bundle as dropped was rejected, because the other issues are still the drain's to fix and would become flags for a person. A dropped run with no members is routed as today.

A split run covers no issue (step 1's `covers`), so `liveRun` never resumes it for its lead or a member. `superseded` (`drain_readmit.go`) compares a run's `Key` with a newer run's today. For a run with members, handed back, it judges by `covers` instead: the run is superseded when a newer run carries its lead or any member. So a person's `abcd build <member-id>` after a split resumes that member's single run when one exists and otherwise opens one, and never resumes the dead bundle, whether or not the lead was taken up again.

### The drain's figures (step 6; decisions 10, 12 and 14)

Each drain's summary gives that drain's own figures, read from its own state, and nothing across drains (dcn-2611201605030535). `DrainCounts` keeps the pull requests the lanes opened and gains:

- `issues_resolved`, the resolutions on lanes that merged;
- `issues_handed_back`, counted per issue: a member handed back alone counts once, a split lane's issues count once, in the single lanes they are taken up in, since a split routes nothing for its bundle (step 5), and a pull request closed unmerged counts each issue it handed back;
- `merged_pull_requests`, the pull requests of lanes that merged, and `closed_pull_requests`, those closed unmerged;
- `preflights`, the merged lanes whose landing reached its gate;
- `ci_minutes`, summed over merged lanes;
- the three figures per resolved issue, each over merged lanes only, so a lane still in progress or parked is in no figure.

`DrainPRHandBacks` (`hand_backs_by_pr`) gains the issues each pull request resolved. When `finishMerged` reads a merged pull request, it reads the pull request's check runs from the forge: the `statusCheckRollup` contexts, with `startedAt` added to the query in `internal/core/landing` and to `internal/ghcontract/graphql-fields.txt`. It stores the sum of `completedAt - startedAt` on the drain lane as `ci_minutes`. A check that never started or never completed adds nothing, and the summary says how many were left out. The merge queue's own runs are not counted, since they run on another ref.

`abcd drain` prints these figures in its summary, and `--json` carries them in `counts`. A new drain replaces the drain's state, so its figures start afresh, and nothing beyond that state and the forge's checks is read for them. The intent's forty-issue comparison is not this step's: it is counted once by hand from the forge, as the intent's Mechanism says, and recorded in its Audit Notes (dcn-2611201605030535). This step also raises the bundled default of `drain.bundle_max` from 1 to 5, as the last step to land (decision 12).

## How the Acceptance Criteria are met

The criteria are numbered in the order the intent lists them.

1. Who joins: `bundleCandidates` (step 3), applied by the forming moves (step 4). Proved by a ledger with a lead and issues of the same category in the same directory, one of another category, one in another directory, a security issue and a root file, with only the first group joining.
2. The cap's layers: the `drain` namespace and its resolution (step 3), the default raised in step 6. Proved by the repository's value, the machine's, both, neither, 0, 11 and a misspelt key.
3. `reservation.max_live` headroom: the forming loop opens the lane rather than reserving past the cap (step 4). Proved with `reservation.max_live` of 3 and a cap of 5.
4. One branch, review set, preflight and pull request with one `Resolves:` per resolved member: one run, one lane (step 1), and the landing and pull request text (step 2). Proved by landing a fixture bundle of three and reading the records commit's trailers and RS001 over its diff.
5. A reservation per member, renewed, fenced and released: `State.Issues()` across the reservation acts, the stop, the drive and the checks (step 1) and the forming holds (step 4). Proved by a fixture run of three members on a fixture origin, stopped, let go and taken over.
6. A member handed back alone: the receipt's `handbacks`, the resolution taken off, the commit off the branch, the widened paths moved and the per-member release (step 2), routed by the drain (step 4). Proved by a receipt that resolves two members and hands one back, a fix round that hands back a member resolved in round 1, and the lead handed back alone holding widened paths.
7. A failed bundle is split: the plain release in the hand-back step and the split (step 5). Proved by a bundle whose fix rounds are spent, one stuck, and one with a member handed back before the lane fails, each with no tombstone pushed by the step, then each held issue's single lane, one passing and one handed back; and by a bundle the drive drops because one member backed off, which pushes nothing, routes that member alone and takes up the others singly.
8. A bundle of one is today's drain: the unchanged path (step 4) and the absent fields (steps 1 and 3). Proved by the fixture comparison in step 4, which masks only the schema versions and the recorded cap, extended in step 6 to mask the figures.
9. The figures: step 6. Proved with `pr-state-1018-merged-timed.json` extended with `startedAt`, and a drain of merged, parked, handed-back and closed lanes, one of them a bundle of four with a member handed back alone.

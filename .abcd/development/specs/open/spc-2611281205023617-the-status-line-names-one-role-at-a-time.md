# The status line shows each role what it needs, in a table a repository can tune

## Summary

This spec delivers itd-2611031342000215. abcd's row on the host's status line becomes one table: an entry per element, a column per view, with the thresholds beside it, shipped as bundled defaults and overridable per entry from the machine's and the repository's `config.json`. The first element names one role, the one whose item has waited longest, or `abcd-managed`; under a facilitator working by hand a red `waiting` and its age follow it where an answer blocks; under `auto` no mode badge renders and the existing `facilitator:` element says the mode. The view follows the blocking answer, giving three views. The row sheds to the width the host reports, detail first, whole elements next and the role word last. Every element has a deterministic explanation, `abcd statusline --explain`. The row gains text mode, a warning style, gauges, links, and the session's own figures.

The intent's decisions 1 to 19 are the product thinker's rulings of 2026-11-03. Decisions 20 to 30 are the session's technical calls of 2026-11-28 (dcn-2611281148461313 to dcn-2611281148519955), and decisions 31 to 35 are the session's defaults for the five product trade-offs the planning put to the person (dcn-2611281155245894, dcn-2611281201513663, dcn-2611281201512624, dcn-2611281201529151, dcn-2611281201531202), each for the person's review. Decisions 36 and 37 are the session's technical calls after the two adversarial reviews (dcn-2611281231066048, the session-start reset; dcn-2611281231064739, when the agents element reads stale). The person approved the move to planned on 2026-11-28, after it was made, and asked to see a live version first (dcn-2611281230532771): the defaults stay open to amendment after that preview, and four questions the intent's Open Questions name are deferred to the person after it, each built at its stated default meanwhile. This spec builds on all of them; a reversal of one changes the step that names it.

The frame ships first (decision 31). Steps 1 to 7 build the table, the badge and views, the fit, the explanation, the gauges, the links and the builds, none of which waits on another record. Steps 8 to 10 each add an element whose source belongs to another record: the review count (spc-2610301925429250), the spend (itd-2611011230226453, a draft) and the branch's pull request (spc-2611251806215442). Until its source ships each element is absent from the row and listed in the explanation as unavailable (criterion 21). A step whose source has not shipped when the rest have landed is carried by a `--remainder` close, which keeps the intent planned until it lands.

### The table and its layers (criterion 10; decisions 13, 28)

The bundled table is `internal/core/statusline/defaults/table.json`, embedded and validated at init as `defaults/statusline.json` is. Each element entry carries, per view (`pt`, `tf_human`, `tf_auto`), its `words`, its `visible` flag, its detail `stages[]` and its `drop` rank; beside the entries sit `detail_order[]` and `thresholds` (`reviews_count` 5, `reviews_age_hours` 24, `key_budget_pct` 80, `context_pct` 80, `key_list_max` 2, `margin` 6, `label_cut` 24). `render.go`'s fixed `order` is read from the table.

`table.go` loads the table through `internal/core/layered` under the one namespace `statusline`, from the machine's `~/.abcd.noindex/config.json` and then the repository's `.abcd/config.json`, the repository file read from the working tree as a file, with no git question. Each field of an entry is replaced whole, as `.abcd/rules.json` layers are. For every field but `visible` the repository's value wins the machine's; `visible: false` from any layer, or the element switched off in the person's `statusline.json`, hides the element, which is spc-2611251806215442's rule, extended here and not renamed. An unknown key under `statusline` is refused naming its file. A drop position is an integer rank, ties broken by bundled order, so one entry moves alone.

**The table's text is checked as it loads.** A repository's `.abcd/config.json` is written by whoever commits to it, and `words` and `stages` reach the terminal, so every `words` and `stages` string from either layer is checked when `table.go` loads it, before any of it reaches an element. A string is refused when it carries a C0 or C1 control byte (ESC and BEL among them) or DEL, when `termsafe.Sanitize` would change it, or when it carries a rune `termsafe.IsHidden` reports (a bidirectional control or a zero-width rune); and it is refused when it is longer than 40 runes. One exception applies to both the `Sanitize` and the `IsHidden` clause: a zero-width joiner or variation selector inside one of the emoji the bundled table declares is admitted, since `Sanitize` maps U+200D to `?` and a joined emoji would otherwise fail the bundled table's own check at init. The check judges the string with those declared sequences set aside, then admits it whole. A refused string is refused as an unknown key is: the diagnostic names its file and its key, never echoing the bytes raw, and the row renders with the bundled value for that field. The bundled table passes the same check at init. abcd composes every escape the `Rendered` form carries itself, so the coloured row holds no escape but abcd's own SGR sequences and, from step 6, the OSC 8 links that step admits.

The person's `statusline.json` keeps the on and off switches, the colours and `previous_command`, and gains `text_mode`, `theme` (`dark` or `light`, `dark` by default) and `links` (true by default). A repository or machine `config.json` naming any of those, or `presence`, under `statusline` is refused by name.

The table's views leave out of the product thinker's view the dirty marker, the branch's pull-request state, the person's open pull requests, the peers, the model, the context and the agents (`visible: false` in the `pt` column; decision 33). The builds element's `words` differ by view: the `pt` column reads `in progress N`, and the two facilitator columns carry lane ids and stage names (decision 35). The drive's part, spc-2611251806215442's, keeps one product wording in every column (itd-2611141507299828 decision 9), and its entries are that spec's to write.

### One role, `waiting`, and the views (criteria 1, 2, 3, 5, 22; decisions 1, 2, 5, 26, 32, 34, 36)

The badge names one role, chosen oldest first:

1. The oldest block. The mode store's block is dated by the mode file's modification time (decision 26). `mode.SetAt` writes nothing when the word already stored is the one being set, so a re-set does not reset the age. A drive's block, once spc-2611251806215442 step 5 has given the drive state its `Needs` and its step 8 has added the drive as a block source, is dated by the drive state's `Since`; that spec's step 8 states the same rule, the oldest block winning, in its own text. A source that has not shipped or cannot be read takes no part.
2. With no block, the role of the oldest pending review, once step 8 here supplies the kept spot-check reading.
3. With neither, `abcd-managed`.

`waiting` is an element after the role, red foreground text with no background, the only red on the row, and only where `facilitator.mode` resolves to `human` as the kept reading holds it (never the working tree's copy, criterion 3). It carries the block's age, `waiting 2h`, in the table's words. Under `auto` no mode badge and no `waiting` render, whatever is owed; the `merging` element already says `facilitator: auto (project)` (decision 32). Whether an answer that holds work under `auto` still shows `waiting`, a product question an agent asks or a drive that needs a person (itd-2611141507299828's decision 4), is deferred to the person (the intent's open question 8); this is its default. Where the person has switched the `merging` element off, or the table hides it in the view, nothing on the row says the mode under `auto`: the row shows the role or `abcd-managed` with no `waiting`, and `--explain` names the mode and the view; that cost goes with decision 32, whose standing is the intent's open question 9. Where the kept reading does not know the mode (missing, malformed or refused, the `unknown` state `landing/keptmode.go` gives), a block renders `waiting` as under `human`, since an answer that may block is never hidden, and the `merging` element, where shown, says the mode is not read (criterion 22). `compose.go` reads the kept mode for the badge whether or not the `merging` element is on; today it reads it only for that element. The badge's `plain` text changes (a role, and `waiting` beside it, in place of `waiting on the technical facilitator`); the board relays it, and the JSON `state`, the element keys and the off switch are unchanged (decision 30).

The view follows the badge (decision 5) and is chosen in `view.go` from the role the badge names and the merge mode: the product thinker's view while the badge names the product thinker for a block, else the facilitator's working by hand or the facilitator's under auto. With blocks owed to both roles the badge names the oldest block's role, and the view is that role's, so a facilitator whose block is older than the product thinker's sees the facilitator's view. A pending review sets the badge, never the view, and no role setting exists (criterion 5).

**The session-start reset (decision 34; iss-2609291032194222).** The session-start hook (`hook session-start`, in `internal/surface/cli/cli.go`) runs the same reset the answer runs, `mode.ResetOnAnswer`, through a named entry `mode.ResetAtSessionStart` in `question.go`: it sets the mode back to managed only when the question marker is present, names the stored word, and names a session that is not still holding the question open (decision 36, dcn-2611281231066048). The first line stays the one word. A marker with no session line, written before the change, is reset only when no other live session started in the checkout; where the live sessions cannot be read, nothing is reset. The cost: a park stays until a session starts, and a question an idle but live session holds stays on the badge, with its age, until that session answers or ends or the person sets the mode. ### Fitting the width (criteria 7, 8, 9; decisions 6, 23)

The front door reads `COLUMNS` as a positive integer; absent, zero or not a number means no fit, and nothing is shed. Core reads no environment: the width is passed in as a value. The fit measures the `Plain` form plus the badge's two fill cells; a test holds that no `Plain` carries `\x1b` or an OSC 8 sequence.

`fit.go` is one engine: an ordered list of sheds, each a detail stage of one element or a whole element, applied in order and stopped at the first row that fits `COLUMNS` less the margin. The list is the table's `detail_order` (the same in every view), then the view's elements by drop rank, then the role word's short form (`PT` or `TF`). The badge is never shed, so every prefix begins with it. If spc-2611251806215442 step 3 has landed, this spec lifts its guard that fits only rows carrying one of its parts, so every row sheds, and re-baselines that spec's golden row, naming the change in the pull request; if this spec's step lands first, it builds `fit.go` in that spec's shape and that step only adds its sheds (decision 29).

`internal/textwidth` gains a cluster-aware measure, with no new dependency: a zero-width joiner joins a sequence that counts two; VS16 makes its base two; VS15, skin-tone modifiers and combining marks count nothing; a regional-indicator pair counts two; C0 and C1 controls count nothing. The emoji the table declares are a closed set, each tested against the measure.

### The explanation, warnings and text mode (criteria 11, 14, 15, 21; decisions 8, 9, 12)

### Gauges and the session's own figures (criteria 16, 18; decisions 10, 14, 15, 16, 27)

The transcript token total is kept incrementally in the fill record (`internal/core/rules/fill.go`): its byte offset and running sum by basis, so a refresh reads only the tail appended since the last. This extends the one admitted write and adds none. Only the session's own payload, transcript and fill are read.

It loosens two tests that pin the fill file to exactly `used_percentage` and `at`: `TestWriteFillRecordsTheTwoFields` (`internal/core/rules/fill_test.go`) and the write-case helper `runStatuslineWriteCase` (`internal/surface/cli/statusline_readonly_test.go`), which every write-case test of the status path shares. That ground does not settle it: the product thinker's ruling of 2026-10-11 (itd-2610091918433290, "Allow one fill file") admitted "exactly that one figure" with "no cache", and the offset and sums are a cache of the transcript read. ### The refresh interval and links (criteria 11, 12, 13; decisions 11, 21, 22, 24)

`ahoy install` sets the host's refresh interval on the `statusLine` setting to five seconds unless it already carries one, which it keeps. It records what it found and what it wrote in the person's `statusline.json`, beside `previous_command`: `previous_refresh_interval`, the value the setting carried before the install or `null` where it carried none, and `refresh_interval_written`, the value abcd wrote, absent where abcd kept the person's own and wrote nothing. Uninstall touches the interval only while the setting still holds exactly `refresh_interval_written`: it puts back `previous_refresh_interval`, or removes the key where that is `null`. An interval the person changed after the install, or one abcd never wrote, is left as it stands, and so is every other key of the `statusLine` setting (today's `harnessLineWith` keeps them); the command is restored as today. That holds where the install recorded a previous command, so uninstall rewrites the line; where none was recorded, uninstall removes abcd's whole `statusLine` line as it does today (`uninstallStatusLine`), the interval and any key the person added to that line going with it, since the line itself was abcd's. So uninstall does not promise the setting byte for byte as it was: it takes back only what abcd wrote and the person has not changed since, or, with no previous command, the line abcd wrote.

A line wired before this change gains the interval too. Today `detectStatusLine` (`statusline_detect.go`) raises no gap for a line that is already abcd's and `offerStatusLine` returns at `statusLineInstalled`, so an existing install would never get it. Step 6 adds an advisory gap in the status-line category, `statusline-refresh-interval`, raised for a line that is abcd's, carries no refresh interval, and has nothing recorded under `refresh_interval_written` or `previous_refresh_interval`; `ahoy install` closes it by writing the five-second interval and the same two records (`previous_refresh_interval: null`). It is idempotent: once closed, the line carries the interval or the record says abcd wrote one, so the gap is not raised again, and a person who later removes the interval is not offered it back. A line abcd owns that already carries an interval raises no gap; its value is recorded as found, with nothing written. The step confirms the key's exact name against the host's current status-line documentation and pins it in `statusline_install_test.go` from a captured settings file.

OSC 8 links go in the `Rendered` form only, as `ESC ] 8 ; ; <uri> ESC \ text ESC ] 8 ; ; ESC \`. Only `https://` links to the forge host of the repository's `origin`, and `file://` links under `~/.abcd.noindex/session-work/`, are admitted, each through `termsafe`; a URI with any byte outside its safe set is dropped and its text kept. `links: false` emits none.

The explanation page and the lanes page are written off the status path by a detached `abcd hook statusline-pages`, which the prompt hook (`internal/surface/cli/status.go`) starts at most once per refresh interval per session, in the pattern of `spawnScheduledRefresh` (`hook_scheduled.go`), into `~/.abcd.noindex/session-work/<key>.explain.html` and `<key>.lanes.html`. Each page states when it was written. Both pages are rendered through `html/template`, never by joining strings, so every value (a branch name, a repository's `words`, a lane's worktree path, an element's `why`) is escaped in its context: a branch named `<svg/onload=…>` lands as text. The pages carry no script, load nothing from outside, and declare `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'` in a meta element. The row links to a page only once it exists; otherwise the symbol or count shows with no link.

## How the Acceptance Criteria are met

The criteria are numbered in the order the intent lists them.

1. One role, oldest first, its own count, unshipped sources skipped: step 2 (the block rung, the mode file's age, a drive's `Since` once readable) and step 8 (the review rung). Tests: a table of blocks and reviews for both roles gives the oldest block's role, then the oldest review's, then `abcd-managed`; a source absent takes no part.
2. `waiting` red with its age under `human`; nothing under `auto`; the session-start reset: step 2. Tests: the mode × resolved mode table; `waiting` is the only red foreground SGR and has no background; under `auto` no badge word and no `waiting`; a session start over an agent-set mode whose asking session is the starting one or has ended resets it, over one a live other session still holds keeps it, over a hand-set one keeps it and its age.
3. The resolver's answer, never the working tree's: step 2. Test: a working-tree `facilitator.mode` that differs from the kept reading changes nothing.
4. The review count grey, yellow `!` at the thresholds, layered: step 8.
5. The view follows the badge's role where that role's item is a block, a pending review never turning it: step 2. Test: blocks owed to both roles give the view of the oldest block's role, in both orders of age.

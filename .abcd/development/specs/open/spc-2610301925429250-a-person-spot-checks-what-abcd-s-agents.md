# abcd's unattended work is spot-checked against specs and intents

## Summary

Delivers itd-2610301750162657. abcd gains a spot-check in two lanes that never hold each other up. The collection lane runs inside the landings abcd already makes: when a change lands and the repository's window has passed, abcd fetches one value from a public randomness beacon, draws up to the set number of items per group from the work decided alone in that window, and appends the drawn items to a review queue on the shared remote. The review lane is a new verb, `abcd spotcheck`, through which the technical facilitator, a human facilitator and the product thinker work the queue whenever they have time, one judgement per item, never reading code. A finding files an issue against the rule that admitted the item; a clean cycle states per group what it rules out. Two smaller pieces ride with it: the drain's summary counts its hand-backs per pull request, and the implement loop refuses to have a change reviewed by the model that wrote it.

The intent is blocked by itd-2610301850454860 (the landing record), planned with spc-2610301950480609, settles the shape this spec reads and nothing more: the evidence of how a change was admitted is written into history before the merge (an `Admitted-by:` trailer on every lane's records commit); a read-only `abcd landings` reader classes every first-parent commit of the default branch as `person-approved`, `drain`, `automatic` or `person-push`, naming the rule that admitted it, from history and from the forge only where history cannot answer; its `--unattended` view lists `drain` and `automatic` and every row the evidence cannot place with a person; and a revert is traced through `This reverts commit <sha>`. This spec depends on no freeze of that listing at a release cut: each drawn item's state is copied into the queue at the draw. The drain's hand-backs and the automated facilitator's decisions are outside that record, so this spec records them itself.

### Approach

1. **The store: one branch on the shared remote, written only by appending files.** A new package `internal/core/spotcheck` keeps the spot-check's record on `refs/heads/abcd-spotcheck` on `origin`, tracked at `refs/remotes/origin/abcd-spotcheck`, with `claim`'s `push` and `fetch` exported for it (one refspec added to the fetch the calling verb already makes). The branch is an orphan whose tree holds four folders of small JSON files, each written once and never edited:
   - `window-open.json`: The commit and time the first window opened (written by the first check that finds no cycle, which draws nothing).
   - `cycles/<cycle-id>.json`: One per draw: the window (`from_commit`, `to_commit`, `from_time`, `to_time`, `closed_by` = `days` or `changes`, the observing site), the beacon (`url`, `chain_hash`, `round`, `signature`, `randomness`, `fetched_at`), the sample (`per_group` from the configuration, `size` applied, `why` = `full` or `halved`, the closed cycles counted), and per group the population's item keys (or, above 5,000 keys, the key range and the population's SHA-256) and the keys drawn.
   - `items/<cycle-id>/<nn>-<group>-<key>.json`: One per drawn item: its group, its key, the roles it is for, and the whole of its state at the draw, copied in (the landings row, the promise, the outcome and the withheld verdicts, approach 6), so what a person later sees as `then` never depends on a later read of history or the forge.
   - `handbacks/<at>-<issue>.json` and `decisions/<at>-<ref>.json`: The drain's hand-backs and the automated facilitator's decisions (approach 2).
   - `judgements/<cycle-id>/<nn>-<group>-<key>.<role>.json`: One per judgement (approach 7).
   The queue is derived: an item waits while a role it is for has no judgement file. Because every write is a new file keyed by item and role, two writers never conflict; a push `origin` rejects is retried once after a fetch, and a judgement whose key the fetch shows already on `origin` is dropped and the earlier one named. A push that fails offline leaves its commit on the local tracking copy, the sitting goes on, and the next push carries it; a sitting's end and the board say how many judgements have not reached `origin`.
   Why the shared remote and not a tier of the tree: The draw runs inside a landing, which has no tree to write into (`land` refuses a dirty tree, `landing/land.go:274`; a lane's worktree is removed at `landMerged`), and the landing on one machine must be seen by the facilitator and the product thinker on others, so a per-machine store under `~/.abcd.noindex/` would fragment the queue across whichever machines land. A committed `.abcd/work/spot-checks/` would dirty the observing worktree at every draw and send a hundred judgements through a pull request per sitting, through the very gates being checked. The remote branch is where abcd already keeps state every copy must see (reservations, announcements), under invariant 7's named-verb rule; the findings themselves become committed issues, the reviewed and durable trace, so a lost branch loses judgements but never a finding. A repository with no `origin` has no unattended landings to draw from; there the check and the verb refuse, naming the missing remote, and write nothing.
2. **Hand-backs and the automated facilitator's decisions are recorded as they happen.** The drain writes `handbacks/<at>-<issue>.json` (issue, kind, `From`, `Route`, `Rule`, `Reason`, the lane's pull request if one was opened, the run id, the record blob) from `routeHandBack` (`loop/drain.go:1365`), and `decisions/<at>-<issue>.json` (kind `drain-judgement`: issue, question, answer, kind, the route's model, the rule record, the reason) from `decideDrainJudgement` when `Route` is set (`loop/drain_decide.go:167`). The merge gate's two callers (`landing/land.go:1284`, `loop/land.go:898`) write `decisions/<at>-pr<n>.json` (kind `merge-gate`: pull request, head, the mode and its layer, the author's role, whether a receipt named the head, `Arm`, `Method`, `Why`) whenever the mode is `auto` and the author a maintainer, which is the case in which abcd is the facilitator and no person's approval was counted; a decision in `human` mode, or over a contributor's pull request, waits for a person and is not recorded here. Each file is committed on the local tracking copy at once and pushed with the next push its verb makes anyway (the tombstone, the lane's branch, the half-lease renewal, `land`'s own push), and at the drain's end; none adds a push of its own. `DrainRoute` gains `PR int` from the lane, and `renderDrainCounts` (`cli/drain.go:435`) gains the per-pull-request table the intent asks for: One line per pull request the run opened with its hand-back count and kinds, then the hand-backs with no pull request.
3. **The window and the trigger.** `.abcd/config.json` gains a `spotcheck` block, claimed through `layered` (`Claim("spotcheck", "window_days", "window_changes", "per_group")`): `window_days` (1 to 90, bundled default 7), `window_changes` (10 to 100,000, no default, 0 meaning unset), `per_group` (1 to 100, default 10). Either window may be set and the first to pass closes it; the repository layer is read last and wins, as the drain's pace keys are read. One function, `spotcheck.AfterLanding(root, now) Note`, is called from the three observing sites: `landMerged` after `ld.Merged` is set (`loop/land.go:1030`), `Land` when `Landed` or `mergedAt` reports the branch on the default branch (`landing/land.go:300`, `:315`), and the drain move after its fetch of the default branch (`loop/drain.go:447`). It reads the last cycle's `to_commit` and `to_time` from the branch as last fetched, counts `git rev-list --first-parent --count <to_commit>..origin/<default>` and compares `now` with `to_time`; when neither bound is passed it returns at once, having read two files and run one local git command and touched no network. Its return is a note for the run record or the verb's text, never an error, an outcome or a hold: a draw that refuses for any reason (beacon unreachable, forge unread, push rejected twice) leaves the window passed, writes nothing, and the next observed landing tries again. The window closes at the observing instant and spans everything since the last cycle, so a week with no landing is drawn at the next one and nothing falls between windows.
4. **The beacon and the draw.** The draw fetches `https://api.drand.sh/v2/beacons/quicknet/rounds/latest` through `urlguard.NewDownload` pinned to `api.drand.sh` (falling back once to `api2.drand.sh`, then `api3.drand.sh`), ten seconds in all, body bounded at 4 KiB, and accepts only a positive `round` with a 96-hex `signature`; the randomness is SHA-256 of the signature bytes. A reply that is late, malformed or unreachable refuses the draw: nothing is written, one line names the beacon, the landing's outcome is unchanged. The populations are read for the window: Groups `drain-landed` and `automatic-merges` from the landings reader's rows in `from_commit..to_commit` classed `drain` and `automatic` (every row the evidence cannot place with a person included, its decision 9; a `person-approved` row excluded, its decisions 7 and 8); groups `drain-hand-backs` and `facilitator-decisions` from the branch's `handbacks/` and `decisions/` files with `at` in `from_time..to_time`. A row whose approval the reader could not settle from history and reports as unread from the forge refuses the draw, so a person's approval is never drawn as unattended on a guess. An automatic merge's rule is `facilitator.mode: auto`, the requirement the gate's table holds; the review receipt itself stays in the local tier and is not recovered afterwards (itd-2610301850454860, decisions 6 and 7), so the reader names the mode's requirement and the item copies it. Each item's key is its merge commit or its file name; within a group the keys are sorted, each is given `HMAC-SHA256(randomness, cycle-id || group || key)`, and the `size` smallest are drawn. The same stored randomness and population give the same list, every item has a chance, and no agent can steer it: the value does not exist until the window has closed. The beacon's signature verification needs a BLS library abcd does not carry; the record stores round, signature and chain hash so anyone with the drand client can verify it later, and this spec adds no dependency. The fetch is written into the documented meaning of `land`, `drain` and `implement step` in invariant 7 and their pages, so abcd still asks the network nothing on its own.
5. **The sample size adapts over fully reviewed cycles only.** `size` is `per_group` unless the three most recent closed cycles, in window order, each have zero findings, when it is `ceil(per_group / 2)`, never below one; a closed cycle with any finding makes the next size full. A cycle is closed when every role slot of every item has a judgement; an open cycle is skipped in the count and counts as neither clean nor a finding. The cycle record names the cycles it counted.
6. **A card, never code.** `spotcheck.Card(item)` renders what a role sees, in plain text, from records alone: the landings row (class, rule by id and path, when, pull request number); the promise, which is the issue's text and remedy, or the spec's criteria, or, for the product thinker, the intent's press release and acceptance criteria; the outcome, which is the pull request's title and the record section of the body the loop composed (`prbody.go:61`), the `resolved_by` stamp and the changelog line where one exists; and for a hand-back the issue, the kind, the route, the clause of the rule that applied and the question whether the drain was right to hand it back; for a decision the question put, the answer given and the rule record. Every card ends with `then` and `now`: `then` is the item file's own copy, written at the draw and never re-read from history or the forge; `now` is read at the sitting from the default branch as last fetched: still on it, reverted by `<sha>` (the landings reader's revert trace), changed again by later first-parent commits touching the change's paths, the issue reopened, or the handed-back issue since resolved, by whom. A card never includes a diff, a file body or a test body; `TestCardCarriesNoCode` renders every fixture and refuses a fence, a `diff --git` line or a path with a line number. Withheld until the judgement is saved, though copied into the item file at the draw: the validators' verdicts the pull request body carries, the drain judge's reason on a judgement item, the gate's `Why` on a merge-gate item, and any reviewer's verdict; `show` and `next` leave them out and the card says `verdicts: shown after you judge`.
7. **The sitting.** `abcd spotcheck review [--as facilitator|human-facilitator|product-thinker]` (the role defaults from the mode file and is asked when unset) makes one fetch of the branch and the default branch, then walks the queue in window order, oldest cycle first, group order within a cycle, item order within a group, for the role's unjudged slots. Each item is put through `question.Ask` with the card as `Material`, the one question for its group (`Does the outcome match its spec?`, `Was the drain right to hand this back?`, `Was the decision right under its rule?`, `Does what came back match the intent?`) and the options `sound`, `wrong` and the decide-later option, a typed line for `why` on `wrong`; in a terminal through `ask.Terminal.Put`, one key per item; in a host session the page has the agent render `spotcheck next --json --as <role> [--batch N]` and put the same question through the host's tool, then record the answer with `spotcheck judge <item> sound|wrong --why "<text>" --as <role>`. Both routes end in the same judgement file (`verdict`, `why`, `role`, `answered_in`, `at`, `state_now`, the issue id on `wrong`), committed and pushed as it is made, so a sitting stopped at any item resumes at the first unjudged slot with nothing to restore. `later` moves the item to the end of this pass and writes nothing. A progress line reads `item 37 of 112, cycle 3 of 9`. After each saved judgement the withheld verdicts print, one line each, and the next card is already read.
8. **A finding files an issue; abcd never edits the rule.** On `wrong`, `spotcheck` calls `capture.Capture` with `Source: review-followup`, `FoundDuring: spot-check <cycle-id>`, `FoundAt` the admitting rule's file (the drain rule record for a drain item, `.abcd/config.json` for an automatic merge or a merge-gate decision), `Text` naming the item, its group, its cycle, the rule by id and the person's words, severity `minor` unless the person raises it, category `process`, and a `Remedy` that opens `Waits on <rule id>: <the person's why>`. That opening is what `eligibility` hands back under `RuleWaitsOnRuling` (`eligible.go:158`), so no drain can take the issue and rewrite the rule; `TestFindingIsNeverDrainEligible` runs `PlanDrain` over such a record. The issue's id is written into the judgement.
9. **The closing statement.** `abcd spotcheck` bare and `spotcheck cycles` render each cycle: per group, `drawn n of N, judged j, findings k`, and for a group with `j = n` and `k = 0`: `rules out a failure rate above about one in r (95%)`, `r = round(1 / (1 - 0.05^(1/n)))`, which is one in four at ten, and in words what it cannot rule out: a lower rate, and the `N - n` items not read. A group with no items says `nothing drawn: no items in the window`. No render ever says `no problems`; `TestStatementNeverSaysNoProblems` holds the phrase out of every fixture.
10. **The board and the verb's surface.** `boardOutput` gains `SpotCheck{Waiting, ByRole, OldestDays, Unpushed, Due}` computed from the branch as last fetched (disk only, nothing fetched), and `boardRows` a `spot-check` row: `37 wait (facilitator 30, product thinker 7), oldest 41 days`; the product view adds one line when items wait for the product thinker; `--json` carries it. `Due` says the window has passed and no landing has been observed since. The verb is new and top-level, `abcd spotcheck`, with sub-verbs `review`, `next`, `judge`, `show <item>` and `cycles`: no existing verb's documented meaning holds a review queue people work across months (`reflect` is one release's interview, `lab` one snapshot, `status` the hour's announcements, `landings` a read-only listing), and a sub-verb of `land` or `drain` would put the reader's verb under a writer's. It lands with its brief row (41, `04-surfaces/README.md`), its chapter `04-surfaces/42-spotcheck.md` with the `## Sub-verbs` table, its page `commands/spotcheck.md` (block `people`), its sentence in the `internal/core/surface` manifest, the regenerated snapshot, and the `spotcheck` block in `05-internals/03-configuration.md`. Invariant 7 gains the branch's fetch and push for `spotcheck`, and the beacon fetch and branch push for `land`, `drain` and `implement step`.
11. **Nothing waits for the queue.** `spotcheck` exports to `loop` and `landing` only `AfterLanding`, the two record writers of approach 2, and nothing that returns a hold, a count or a boolean; `mergeGate`, `DrainJudging`, `RunningUnattended` and the away mode's `Judge` are untouched. `TestNothingWaitsForTheQueue` lands a lane and plans a drain over a branch holding ten thousand unjudged items and asserts the same outcomes and no read of `items/` or `judgements/`.
12. **A model other than the writer's reviews every change.** Before a validator is dispatched (`loop/validate.go:594`, `:1003`), the loop compares the implementer's reported model (`ReceiptRecord.Model`, or its `Route.Model`) with the reviewer's resolved `ReviewClass.Model`, by `matrix.sameModel`'s normalisation; on a match it takes the next class in `BundledClasses` whose model differs, and when none does the lane hands back as `stuck` with the reason `no reviewer model other than the writer's`. A host-run validator's return must name its model, as the implementer's receipt does; a return naming none is treated as the writer's. `ValidatorRun` gains `WriterModel` and `ReviewerModel`, the lane receipt and the composed pull request body name both, and `renderReview` (`cli/build.go:540`) shows them.

### How each criterion is met

- **Seeded from a public value, stored, every item a chance, recomputable.** Approaches 1 and 4. Tests: `TestDrawIsDeterministic` (same cycle file, same list, across two runs and a shuffled population), `TestEveryItemCanBeDrawn` (over many fake randomness values every key of a 50-item group is drawn at least once), `TestBeaconUnreachableWritesNothing` (a refusing fake beacon: no cycle file, no item, the landing's `Merged` still set and exit 0).
- **Groups, ten by default, half after three clean, full after a finding.** Approaches 3 to 5. Tests: `TestFourGroupsFromTheirSources` (rows classed `drain` and `automatic` and the branch's `handbacks/` and `decisions/` files; a `person-approved` row never drawn), `TestSizeHalvesAfterThreeClosedCleanCycles`, `TestSizeFullAfterAFinding`, `TestOpenCycleCountsAsNeither`, `TestPerGroupBounds` (0, 101 and a string refused with the key named).
- **Never code; the right thing beside each item; verdicts after the judgement.** Approaches 6 and 7. Tests: `TestCardCarriesNoCode`, `TestCardPerRole` (facilitator sees spec and outcome or rule and decision, product thinker sees the intent, human facilitator sees only decision items a model took), `TestVerdictsShownOnlyAfterJudging` (the rendered card lacks the verdict text; the post-judgement text holds it).
- **A finding files an issue naming item, group and rule; abcd never edits the rule.** Approach 8. Tests: `TestWrongFilesAnIssue` (the record names all three and the person's why), `TestFindingIsNeverDrainEligible`.
- **A clean cycle states what it rules out, never "no problems".** Approach 9. Tests: `TestStatementAtTen` (one in four), `TestStatementAtFive` (one in two), `TestStatementNeverSaysNoProblems`, `TestEmptyGroupStatesNothingDrawn`.
- **The window passes at a landing; otherwise nothing is drawn.** Approach 3. Tests: `TestWindowByDays`, `TestWindowByChanges`, `TestWindowNotPassedDrawsNothingAndFetchesNothing` (the zero-network harness), `TestFirstCheckOpensTheWindow`, `TestThreeObservingSites` (lane landing, land re-run, drain move each call once).
- **Nothing autonomous waits for the queue.** Approach 11. Test: `TestNothingWaitsForTheQueue`.
- **Items keep across months, ordered by window and group, stop and resume anywhere.** Approaches 1 and 7. Tests: `TestQueueOrderOldestFirst` (nine cycles, four groups), `TestResumeAtFirstUnjudged` (a sitting quit at item 37 resumes there, judgements intact on the branch), `TestNoItemExpires` (a two-year-old item still listed).
- **A late item shows then and now; its finding is filed like any other.** Approaches 6 and 8. Tests: `TestCardThenAndNow` (reverted, changed again, issue since resolved), `TestLateFindingFilesAgainstItsRule`.
- **Only fully reviewed windows count towards the halving.** Approach 5. Tests: `TestOpenCycleCountsAsNeither`, `TestSizeCountsClosedCyclesInWindowOrder`.
- **The board says how many wait, for whom, how old.** Approach 10. Tests: `TestBoardSpotCheckRow` (text, markdown, `--json`), `TestBoardReadsTheBranchFromDiskOnly`.

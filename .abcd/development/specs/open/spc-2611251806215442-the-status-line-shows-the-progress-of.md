# The status line shows the progress of work that runs without the person

## Summary

This spec delivers itd-2611141507299828. With no command typed, abcd's row on the host's status line gains three parts: what an unattended drive is doing, where the pull requests this session armed stand, and which step a preflight this session started is on. Each part reads a small state file that the work itself writes. The status command makes no network call, starts no process, asks git nothing new and writes no file.

The intent carries no open question: the product thinker answered all ten on 2026-11-15 (decisions 1 to 10). Four of those decisions left a mechanism to the run to propose, and this spec proposes each: the words for the counts (decision 9), which session shows the drive in full (decision 5), how the detached refresh of pull-request state is started (decision 6), and how the badge's two sources are reconciled (decision 4).

The intent has three dependencies, and the steps are ordered so that what waits on none of them is built first.

- It builds on itd-2611141610197753, whose spec spc-2611141617199772 stores the drive's state as a file in step 4. No step of that spec is on the default branch yet. Steps 1 to 4 here need nothing from it. Steps 5 to 8, the drive's, wait on its step 4. The intent named that intent in `blocked_by`, and `abcd build` takes no intent with an unshipped blocker (the `blocked` start check, `internal/core/intent/startcheck.go`), so at its planning the technical facilitator made the edge `builds_on` (dcn-2611251806134844); Coordination says what follows.
- It builds on the draft itd-2610281253044600 (the status line says what each session is working on), whose four questions are unanswered. No step here waits on them. The match this intent needs is between a session and the pull requests it armed and the check it started, and each of those is recorded under the session's id by the command that does the act. That draft's question is a different one: which record a session holds when its work is in a store worktree.
- It builds on itd-2611031342000215 (the status line names one role at a time), planned on 2026-11-28 with spc-2611281205023617, which divides the row's code with this spec (its decision 29, dcn-2611281148506801): this spec owns the session state files, the part frame and its three parts, the pull-request watcher, `switches.go` and the first `fit.go`; that one owns the table, the views, the badge rework and lifting the fit's guard. This spec takes four of its recorded decisions as given: the view follows the badge (5), the row sheds to `COLUMNS` less a margin of six (6), every warning is yellow and carries `!` (8), and the row never waits on the network (18). It builds the smallest width fit those decisions allow (step 3), in a shape that draft's table can later configure.

One new command is added, and it is hidden: `abcd hook pr-watch`, the detached refresh. No verb, flag or page of the plugin surface is added. The mode store gains no writer. The drive's state file gains three fields (`Cause`, `Needs`, `Full`) and an index of drives beside it, and stays at its own version until step 5 raises it.

## Approach

### What is on the default branch today

- **The status command.** `internal/surface/cli/statusline.go` is the front door of `abcd statusline`. `decideStatus` reads the payload, loads the setting, resolves the checkout, asks whether abcd manages it and calls `statusline.ComposeContext`. All of it runs under a watchdog: `statuslineBudget` is 500 ms and `statuslineGitBudget` 300 ms, and `TestStatuslineBudgetIsUnderASecond` holds the values. Outside a managed checkout it runs the person's previous status command.
- **The one write.** `recordStatusFill` writes the session's fill file, `~/.abcd.noindex/fill/<sha256 of the session id>.json`, through `rules.WriteFill`. Two guards hold the path to that one write: `TestStatusVerbReachesNoWritePrimitive` (`internal/core/statusline/readonly_guard_test.go`) scans every non-test file of `internal/core/statusline` and the front-door file for write primitives, and `TestStatuslineWritesOnlyTheFillFile` (`internal/surface/cli/statusline_readonly_test.go`) compares a snapshot of the home and the checkout before and after a run.
- **The row.** `internal/core/statusline/render.go` holds a fixed `order` of elements (`presence`, `repo`, `branch`, `merging`, `model`, `context`, `five_hour`, `seven_day`, `intents`, `issues`), with the session's name placed after the badge. Every element after the badge has a switch in `~/.abcd.noindex/statusline.json` (`settings.go`, defaults in `defaults/statusline.json`). An element has a `Rendered` and a `Plain` form, and only the badge's differ. The row reads no width: its comment says truncation safety comes from order alone. There is no view, no warning style and no repository-layer setting.
- **The badge.** `compose.go` reads the stored mode through `mode.ReadAtContext` and `badge.go` renders one of three words. The store, `.abcd/.work.local/mode`, has one writer, `mode.SetAt`, which the guard above refuses on the status path.
- **Import limits.** `internal/core/statusline` cannot import `landing` or anything that reaches `ahoy`, since `ahoy` reads this package. `statusline.MergingMode` is the precedent: a function variable the front door sets to `landing.AutonomousMerging`. The loop package imports `landing`, so the row cannot import the loop's types either.
- **The session a command runs under.** `runner.CurrentSession` (`internal/core/runner/ledger.go`) names it: the id the host exports in its environment, else the session whose host process the command descends from (`sessionname.SessionAbove`), and nothing under a plain terminal. The payload of the status command carries the same id as `session_id`. A clear gives a session a new id, and the session-name register carries the name over (`givenNames.move`, `internal/core/sessionname/register.go`).
- **Pull-request state.** `landing.PRStates` (`internal/core/landing/prstate.go`) reads one pull request in one GraphQL read and tells `armed`, `queued`, `removed` (out of the queue, with the forge's reason), `open`, `merged` and `closed` apart. `abcd land --state` and `abcd implement heartbeat` report through it. `landing.Result` carries the pull request's number once the enqueue step has run, and `landing.Land` has one caller, `internal/surface/cli/land.go`.
- **Detached starts.** `spawnScheduledRefresh` (`internal/surface/cli/hook_scheduled.go`) starts `abcd hook scheduled-refresh` in a session of its own, with its streams on the null device, when the prompt hook in `internal/surface/cli/status.go` finds the kept answer aged. It is the pattern this spec follows for the forge.
- **A preflight.** `make preflight` runs `abcd implement load --wait --timeout 12h -- make preflight-stages`, so the load gate's waiter (`internal/surface/cli/implement_load.go`) is the parent of the whole run from its wait to its end. The full rule has seventeen steps: thirteen gates as prerequisites, then build, vet, the unit stage and the race stage. Nothing records which step a run is on; `scripts/preflight-receipt.sh clock` records stage times after the fact.
- **The drive's state.** Not built. Step 4 of spc-2611141617199772 specifies `DriveState` in `internal/core/implement/loop/drivestate.go`, written whole by rename to `.abcd/.work.local/logs/drive-state.json` in the drive's checkout, with the state word, `Since`, `Until`, `On`, `Do`, four counts, the process id and start time, `Written` and `Next`, the time by which the drive will have written again. That spec says `Next` is the fallback for exactly this reader.
- **Notifications.** abcd raises none. No package sends one.

### Where each part's state lives, and who writes it

| Part | File | Writer | Keyed by |
|---|---|---|---|
| Preflight | `~/.abcd.noindex/session-work/<key>.check.json` | the load gate's waiter | the session's id |
| Pull requests | `~/.abcd.noindex/session-work/<key>.prs.json` | `abcd land` at the arming, then the detached watcher | the session's id |
| Drive | `.abcd/.work.local/logs/drive-state.json` in the drive's checkout, found through `.abcd/.work.local/logs/drives.json` in the main checkout | the drive | the repository |

`<key>` is the SHA-256 of the session id, as the fill file's name is. A new leaf package, `internal/core/sessionwork`, holds the two session files: their shapes, their paths, one guarded reader (`read.go`) and their writers (`write.go`). It imports nothing that reaches `ahoy`, so the row may import it. The reader is the home-declaration read abcd already makes for `statusline.json`: one open with no link followed, a regular file this account owns that no one else can write, under a 16 KiB cap, of a schema version the reader knows. The writers make the folder; the status command never does.

The files are in the account's home and not in a checkout's local tier for one reason. A session whose directory is the main checkout runs its preflight, and arms its pull request, from a store worktree. A file in that worktree's tier is one the status command, which resolves the checkout from the payload's working directory, would never find. A file named by the session's id is found from anywhere. This is why the matching question of itd-2610281253044600 does not have to be answered here.

Each record carries the main checkout of the repository it belongs to, which its writer resolves with git. The row resolves its own main checkout without git, from the `.git` marker: in a linked worktree `.git` is a file naming the worktree's git directory, whose `commondir` file names the shared one. Two small reads. A record of another repository is not shown.

### The row's parts (criteria 10, 12 to 16, 19, 25)

Three element keys are added, each by the step that builds its part: `check`, `pull_requests` and `drive`. They follow `merging` in `order`, so with no width a host that cuts the right edge cuts the payload and record elements before them. Each has a switch in `statusline.json`, on by default, and an entry in `statusLineElementAbout` (`internal/core/ahoy/prompt_help.go`), which the install's questions read.

A small frame in a new file, `part.go`, serves all three:

- **A part that is off is not read.** The switch is tested before the read, and a test counts the reads.
- **A part has a share of the ceiling.** Each part's read runs in its own goroutine with 50 ms. One that has not answered is dropped, a note names it for stderr, and the row renders. The reads are a fixed, small number of capped files, measured in well under a millisecond each on a healthy disk, so the share is the bound on a stalled filesystem and never the cost of an ordinary refresh. What a goroutine was blocked in ends with the process, as the watchdog's does.
- **A part that has nothing to say renders nothing.** No file, or a file with no entry for this repository, is the ordinary case and is silent. So a session with no drive, no pull request and no check renders the bytes it renders today (criterion 10), and the unmanaged path, which never reaches the composition, is unchanged (criterion 25).
- **A warning is a word, a mark and a colour.** The plain form carries `!` and the words; the rendered form paints both yellow. No state rests on the colour (criterion 16).
- **Text the row did not compose** passes `termsafe.Sanitize` (`internal/termsafe`) and is cut by runes at a declared length before it reaches an element (criterion 15). This spec admits little of it: the drive's cause is an enumerated value the row words itself (below), and the check's name is the row's own word. The frame's test still feeds an escape, a control character, a bidirectional override and a hidden rune through every field a state file holds.
- **A clock.** The parts show times, so the composition reads a clock, through a seam a test fixes. The render stays a function of its input.

The read-only guard is widened, not loosened: its scan adds `internal/core/sessionwork/read.go` and the front-door seam file of step 7 to the files it reads, `statusVerbFileFloor` rises with them, and no write is admitted (criterion 14). The snapshot test runs again with all three state files present.

### The preflight part (criterion 9; decision 8)

The waiter writes the session's check file when a whole run starts waiting (the command form without `--narrow`), and it is the one writer. It names its session through `runner.CurrentSession`; under a plain terminal or a drive there is no session, and it writes nothing. The file holds the state (`queued` while it waits its turn, `running` once its command has started), when each began, the step and the count, the main checkout, the time written and `next`, the time by which it will have written again. The waiter rewrites it every thirty seconds and sets `next` a minute ahead. When its command ends, however it ends, the waiter removes the file and the steps file beside it. A waiter killed outright stops rewriting, and the row drops the part once `next` has passed. So an ended check is gone on the next refresh, a killed one within a minute and a half, and no result is kept (decision 8).

Steps come from the check itself. The waiter exports `ABCD_CHECK_STEPS`, the path of a steps file beside the check file, to its command. A check appends one line per step as the step begins: first `of <n>`, then one name per step. The waiter reads the file's tail at each rewrite: the step is the number of step lines, the count is the declared `n`. A new script, `scripts/check-step.sh`, does the append and does nothing when the variable is unset, so `make precheck` and a preflight run with no waiter are unchanged. The make file gives each of the thirteen gates and the four later stages one mark, and declares the count from one variable; a test holds the count to the marks. A repository whose check reports no steps shows the part without a step.

The part reads `preflight 14 of 17, 31m` while running, `preflight queued, 12m` while it waits its turn, and `preflight running, 31m` with no steps reported. A narrow run of a few packages is not a whole run and is not shown. The records-only rule waits at no gate, has no waiter and is not shown; it takes minutes.

Reading the output of the check for its steps was rejected: the lab on drive operations read a state back out of sentences and read it wrong twice (F-11 of lab-261114145658-67e1f9b). A verb called once per step was rejected for its cost: seventeen runs of a Go program inside every preflight.

### The pull-request part (criteria 7, 8, 11; decisions 6 and 7)

**Recording.** When the enqueue step of `abcd land` arms a pull request or finds it in the queue, the front door (`internal/surface/cli/land.go`) records it under the session the command runs under: its number, the main checkout, the branch, its state and the time. An arming made under no session (a plain terminal, a drive's lane) is recorded nowhere, so the row "counts only this session's own". Where the session-name hook moves a name to a new id after a clear, it moves the session's two files to the new key in the same act, so a cleared session keeps its pull requests.

**The detached refresh (decision 6).** `abcd hook pr-watch` is a hidden command that loops. On each pass it reads every `*.prs.json` of this account, asks `landing.PRStates` for each pull request that is not merged or closed, and writes each file back whole by rename, with the time read. It is the one process that reads the forge for the row.

- *Rate.* One pass a minute at most, and at most twenty pull requests a pass. A pull request that is out of the queue is asked again every five minutes, not every one. A forge that cannot be asked doubles the wait, to fifteen minutes at most, and the reason and the time are kept in the file.
- *One at a time.* It holds a lock file in `~/.abcd.noindex/session-work/` for as long as it lives, with its process id and start time in it. A second start finds the lock held and exits.
- *Its end.* A merged or closed pull request is removed from its file (decision 7: a merged one is never shown), and a file with none left is removed. A pull request is retired thirty days after its arming whatever its state. When no file holds a pull request, the watcher exits. It also exits within a pass when the part is switched off in the person's `statusline.json`; step 4 adds the machine's `config.json` to that test when it builds the configuration layers.
- *How it is started.* By `abcd land`, detached, right after it records an arming: the act that creates something to watch starts the watch. And by abcd's prompt hook (`internal/surface/cli/status.go`), detached, when the session's file holds a pull request and no live watcher holds the lock, which covers a reboot and a watcher that died. Both starts follow `spawnScheduledRefresh`: a session of its own, streams on the null device, released at once. The status command contains no start, and never waits.

A refresh started by the prompt hook alone was rejected: a session that is idle, because the person stepped away or because it waits on agents, sends no prompt, and that is when a pull request that drops out most needs to be seen. A system timer (launchd, cron) was rejected: it is an install step per platform with its own consent, for something a process that ends by itself already does.

**The row.** The part reads the session's one file and counts by state: `PRs 1 armed, 2 queued, 1 dropped out`. `removed` reads `dropped out`, and so does `open`, which here is a pull request this session armed whose arming is gone. A state with no pull request is not named. The dropped count carries `!` and yellow (criterion 8). When the file was last refreshed more than five minutes ago the part ends `(as of 14:02)`, so a count the watcher has stopped feeding does not read as current.

**The four things the status command does not do (criterion 11).** Four tests over the status path, with all three state files present and aged:

1. No network call: the existing `TestModeAndStatuslineTouchNoNetwork`, extended to the fixtures.
2. No process that makes one: a recording `gh` and a recording copy of abcd first on `PATH`; neither is run, and the watcher's lock is still absent afterwards.
3. No subprocess it does not start today, and 4. no new git question: a recording `git` first on `PATH` logs every invocation; the log with the fixtures present equals the log with them absent, and nothing else was started.

A fifth, structural: the guard's scan refuses a process start (`exec.Command`, `exec.CommandContext`, `os.StartProcess`) in the files it reads, outside the one that exists today, the previous status command's in `internal/surface/cli/statusline.go`. The row's git questions start no process in those files: they go through `gitutil` (`gitQuery` and `CheckoutRoot`, `internal/core/statusline/git.go`), so the scan also refuses a `gitutil` call outside that file.

### The width fit and the views (criteria 17 and 18; decision 1)

The row is fitted only when `COLUMNS` is set, the row is wider than `COLUMNS` less six, and the row carries at least one of the three parts. A row with none of the parts is returned as composed, whatever the width: criterion 10 holds the row to today's bytes there, and shedding the existing elements for every row is the change itself of itd-2611031342000215. The cost is stated: a narrow row sheds once a preflight starts and stops shedding when it ends. With `COLUMNS` absent nothing is shed (criterion 18).

The guard is this spec's only until spc-2611281205023617 step 3 lands, which fits every row (decision 29 of itd-2611031342000215). Where this step lands first, that step lifts the guard, drops the test that holds a part-less row as composed, and re-baselines this spec's golden rows at 40 columns, naming the change in its pull request. Where that step has landed first, `fit.go` already exists in this shape and fits every row: this step adds its sheds to that engine's list and builds no guard, and the part-less test and the 40-column golden row are that spec's. Either way, one fit rule holds once both have landed: every row sheds.

The view follows the badge, as decision 5 of itd-2611031342000215 rules: the product thinker's view while the badge waits on the product thinker, the facilitator's otherwise. That draft's split of the facilitator's view by merge mode changes nothing for these parts and is not built here.

A new file, `fit.go`, holds one engine: a view is an ordered list of sheds, each either a detail stage of one element or the drop of a whole element, and the engine applies them in order and stops at the first row that fits. Width is measured on the plain forms with `internal/textwidth`, plus the badge's two cells of fill. The badge is never shed, so every prefix still begins with it. That draft's rule (every detail first, then elements) is one such list, so its table can drive this engine unchanged.

The shipped lists, first shed first:

- *Both views, first:* `issues`, `intents`, `seven_day`, `five_hour`, `context`, `model`, `merging`; then the check's elapsed time; the pull requests' as-of note; the drive's cause; the drive's counts from the right, down to the first; `branch`; `repo`; the session's name; the drive's phrase for who it needs; the drive's last count; the word `since`; the pull requests collapsing to their worst state alone (`PRs 1 dropped out`).
- *Product thinker's view, then:* `check`, `pull_requests`, the drive's time. The drive's state word and its `!` are what is left.
- *Facilitator's view, then:* `check`, the drive's time, `drive`. The pull requests are what is left.

So within the drive part the state word outlasts its counts and its detail in both views, and a stall can be the part a facilitator's narrow row dropped, the cost decision 1 accepts. When the drive needs a person the badge names the role (below), and the badge is never shed.

### Switches, the board and `--json` (criteria 19 and 20)

A part is off when its switch is off in the person's `statusline.json`, or when `statusline.elements.<key>.visible` is `false` in the repository's `.abcd/config.json` or the machine's `~/.abcd.noindex/config.json`. Off wins from any layer, as `land.push` does: a repository can take a part off its rows and cannot turn on one the person turned off. The key has the shape of the per-element entry itd-2611031342000215 describes, so that draft extends the namespace and renames nothing. The layers are read through `internal/core/layered`, which refuses an unknown key under a claimed namespace by name. The repository's file is read from the working tree, as a file: no git question.

`abcd statusline --json` already emits the row's elements, so it carries the three parts with their plain forms once they are elements. The bare board composes the same row (`boardPresence`, `internal/surface/cli/board.go`) with an empty payload; it now passes the session it runs under, from `runner.CurrentSession`, so the session's pull requests and check appear on it in the same words. The board composes the row with the drive element left off: the board shows the drive as the one line itd-2611141610197753 composes, and the row's shorter phrase would say it twice.

### What the drive's state gains (decisions 4, 5, 9 and 10)

The row may not read the process table and may not show the drive's own terms, so four things have to be in the stored state. They are added to `DriveState` after step 4 of spc-2611141617199772 has landed, and the file's own version rises by one.

- **`Cause`.** An enumerated reason beside the free text of `On`: the usage window, the pace window, an outage, the remote, a cap, work others hold, a missing record, a run another session holds, the hourly retry of skipped lanes, or one lane's own stage. The row words each itself (`on the usage window`, `on a missing record`, `on one piece of work`) and shows nothing for a value it does not know. `On` is never shown on the row: it carries issue ids and stage names, which decision 9 keeps off it.
- **`Needs`.** The role the drive needs, or none. It is the technical facilitator wherever `Do` names an act, because every act the state names is typed at a terminal, the facilitator's surface. No rule in this spec sets it to the product thinker; the field takes either role so a later rule can.
- **`Full`.** The key of the one session that shows the drive in full (decision 5). At each write the drive reads the live sessions (`occupancy.Live`, which reads the process table, as a drive may) and keeps its pick while that session lives; otherwise it picks the live session that started in the drive's own checkout, the lowest id first, else the lowest id in any checkout of the repository, else none. The row shows the drive in full when the key of its own session equals `Full`, and the state word alone otherwise. A pick that has died is replaced at the drive's next write, five minutes at most, and until then every row shows the word.
- **The index.** A drive adds its checkout to `.abcd/.work.local/logs/drives.json` in the main checkout when it starts, under a lock, and removes it when it ends; a start prunes an entry whose process is gone. The file holds eight entries at most. It is how a session in one checkout finds a drive in another without asking git for the worktrees.

### The drive part (criteria 1 to 6, 13, 22, 23; decisions 3, 5, 9, 10)

The row reads the index in its main checkout, then each state file it names, and its own checkout's state file if the index does not name it: nine capped reads at most, whatever the drive has done (criterion 13). The loop's reader is reached through a function variable the front door sets (`internal/surface/cli/statusline_drive.go`), as `MergingMode` is, because the row cannot import the loop.

- **Working:** `drive working · 20 done · 2 in progress · 3 skipped · 79 need a person`. The counts are the stored ones, since the drive started (decision 3). The words replace `landed`, `in flight`, `set aside` and `handed back` (decision 9). A count of zero is not shown.
- **Waiting:** `drive waiting on the usage window since 14:02 · 20 done`. Past its first count a waiting drive's counts are detail.
- **Stalled:** `! drive stalled since Thu 16:40 on a missing record · needs the facilitator · 20 done`, in yellow. The change shows on the first refresh after the drive writes it, since the row reads the file each time.
- **Stopped:** `drive stopped since 09:12`, with the needs phrase where the state names an act.
- **Not heard from (criterion 5):** when the clock is past `Next` by more than thirty seconds, the part reads `! drive not heard from since 13:40`, whatever word is stored, and so never `working`. The time is `Written`. The cost that spec states stands: a drive that died during a long wait can read as waiting for up to an hour.
- **Unreadable (criterion 6):** a state file the index names that is missing, or one that is unreadable, malformed or of a version the row does not know, gives no drive part, one line on stderr naming why, and the rest of the row. A repository with no index entry and no state file has no drive, and that is silent; the criterion's "missing" is read as a file something says should be there.
- **Several drives (decision 10):** the worst state leads, with a count: `! 2 drives, worst stalled since Thu 16:40 on a missing record`. Worst first: stalled, not heard from, stopped with an act, waiting, working, stopped. The counts are not shown with several drives: each drive's counts are since its own start, and a sum would match no drive's own summary.
- **Other sessions (decision 5):** a row whose session is not `Full` shows `drive working`, `drive waiting`, `! drive stalled` and so on, and nothing more.

A time reads `14:02` on the same day, `Thu 16:40` within a week and `12 Nov` beyond it, in the machine's zone.

### The badge (criterion 21; decision 4)

The stored mode keeps one writer. The row composes the badge from two readings: the stored mode, and the drive part's `Needs`. Each is a block, and the badge names the role of the oldest block, as itd-2611031342000215 rules (its decision 1) and spc-2611281205023617 step 2 builds: the stored mode's block is dated by the mode file's modification time, a drive's by its stored `Since`. So a stored role older than the drive's need stands, a drive's need older than the stored role names the drive's role, and where the store is `managed` and a drive needs a role the badge names that role; the view follows the badge. The badge's words are that spec's (the role, with `waiting` and its age where `facilitator.mode` resolves to `human`). This step adds the drive as a block source to the badge that step builds, and builds no precedence of its own. Under `auto`, that spec's default renders no `waiting`, so a drive that needs a person names the role with no `waiting`; this spec's criterion 21, from itd-2611141507299828's decision 4 ("the badge turns to waiting on the role the drive needs"), is therefore met under `auto` only as the person answers itd-2611031342000215's open question 8, which is deferred to them and covers a drive's need under `auto`. Until they answer, criterion 21 is built and tested under `human`, and under `auto` waits on that answer. When the drive's state stops naming a need, the next refresh shows the stored mode again. Nothing was written, so nothing has to be reset, and the rule of itd-2609212130146198 (a question is refused until the mode is set, and the answer resets it) reads the store and is unchanged.

The board's presence line is the same composition, so it agrees with the row. `abcd mode` prints the store and is unchanged: it can read `managed` while the row waits on the facilitator for a drive. The mode page says so.

Having the drive write the mode store was rejected: the store is per checkout, so a drive would have to write every checkout's, and a drive that died would leave a badge no answer resets.

### The notification (criterion 24; decision 2)

A new leaf package, `internal/core/notify`, sends one desktop notification: on macOS through `/usr/bin/osascript`, with the title and text passed as arguments and never spliced into the script; on Linux through `notify-send` at its absolute path; on any other platform, and where the sender is absent, it reports that it could not and nothing else happens. The drive calls it where its state value changes to `stalled`, once, and not again until a movement has cleared the stall. The text is the row's stalled phrase, in product terms, through the same safety pass. A sender that fails is noted in the drive's log and never stops the drive. `drive.notify` is on by default and `false` in either configuration layer turns it off; off wins.

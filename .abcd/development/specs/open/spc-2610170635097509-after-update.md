# after-update

## Summary

This spec delivers the bundle `after-update`, two intents met in one moment of
the agent's first reply after an abcd update:

- [itd-2610161617096084](../../intents/planned/itd-2610161617096084-after-a-plugin-update-abcd-says-what.md):
  abcd says what changed, one line per release, with the full summary one
  command away;
- [itd-2610161616086564](../../intents/planned/itd-2610161616086564-after-a-plugin-update-abcd-offers-to.md):
  abcd offers, once per update per repository, to run setup again when the
  update brings something the repository needs.

The two intents' `## Decisions` are binding and are not repeated here, except
where a step names one. In short: the session-start hook adds one fixed line
and writes nothing; after the person's first message the agent runs one abcd
verb and relays what it prints, first the summary line per release, then the
offer; the person's answer is recorded by a second run of that verb, in abcd's
own data directory, keyed on the repository's root commit and the release.

**Approach.** Five parts, each on code that already exists.

- **The digest.** `abcd launch ship` already composes, for each release, one
  changelog line per shipped record and proves the lines cite exactly the cut
  (`internal/core/release`, `Ingest`). The cut gains a fourth write beside the
  archive, the page and the CHANGELOG heading: a digest, a JSON file holding,
  per release, its tag, the tag it was cut from (`Cut.BaseTag`) and each line
  as composed, with the record ids it cites and their impact. The file lives in
  a Go package, `internal/core/releasedigest`, which embeds it with
  `//go:embed`, so the binary built from the release's tag carries every
  release up to and including its own. The `.abcd/` namespace never reaches a
  released binary (AGENTS.md, Boundaries), so the digest cannot live there.
- **Release versions, strictly.** One parser, `launch.ParseReleaseTag`, accepts
  exactly `vMAJOR.MINOR.PATCH` (digits only, no leading zero, no pre-release or
  build part) and orders through the existing `launch.Semver`/`CoreGreater`.
  Every version this bundle reads (the running binary's `core.Version`, the
  repository's `meta.setup_version`, the binary record's `previous_tag`, a digest
  tag) passes it or takes no part. `embargo`'s private copy of the same pattern
  calls it ([`one-canonical-primitive`](../../principles/one-canonical-primitive.md)).
- **What waits on this repository.** A new `ahoy.Waiting(cwd, from, to)`
  returns the questions setup would ask here that were never answered, leaving
  out those whose latest setup answers record says `later` (the "decide later"
  value `interview.Write` already records in `.abcd/.work.local/interviews/`),
  plus the settings whose default changed in a release after `from` up to `to`
  and which this repository takes from the default. The default changes come
  from a table embedded in `ahoy`, each entry naming a setup key and the record
  that changed its default; the digest says which release shipped that record.
- **The record of what was shown and answered.** A new core package,
  `internal/core/afterupdate`, composes the moment (the summary lines and the
  offer) from the digest, `ahoy.Waiting` and its own store under
  `~/.abcd.noindex/after-update/`, and owns that store: one file per
  repository and release holding the answer, and one per computer holding the
  newest release whose general news was shown. Only the verb writes it.
- **The front doors.** `abcd ahoy after-update` prints the moment bare,
  the full summary with `--full`, and records the answer with
  `--answer yes|not-now` (or that the summary was read, with `--seen`, when no
  offer was made). `abcd ahoy install --only-waiting` is the setup the yes
  runs: it asks only the waiting set. The session-start hook, which already
  runs `ahoy.Detect`, asks `afterupdate.Pending` (read-only) and, when anything
  is pending, prints one constant sentence to stdout. Both verbs are wired on
  the CLI and on `commands/ahoy.md`.

**The moment, as the agent relays it.** For Alice, set up with v0.15.0 and now
running v0.16.0, with two questions waiting:

```text
abcd v0.16.0: 9 changes, 1 needs you to act (itd-N). Ask for details: abcd ahoy after-update --full
abcd was updated from v0.15.0 to v0.16.0 since this repository was set up; 2 setup questions wait here. Run setup now? (yes / not now)
```

The first line is the general news, once per computer; the second is what
waits here, once per repository. Neither carries a word from the repository's
tracked files: versions pass `ParseReleaseTag`, the counts are numbers, and the
line text comes only from the digest inside the binary. With `--full`, each
release in the range is named, its changes that need action first, each as its
digest line with the record id to read more, then the waiting questions' and
changed settings' titles.

### Settled here

The intents leave these technical choices open. Each is decided on the grounds
given; none changes a criterion.

- **The digest's path is declared, not fixed.** `launch ship` writes it to the
  repository-relative path the repository's `.abcd/config.json` declares under
  `release.digest` (the `release` namespace claimed through
  `internal/core/layered`, read from the repository layer only), and writes no
  digest where none is declared. abcd's own config declares
  `internal/core/releasedigest/digest.json`. Grounds: managed repositories
  replicate abcd's path, so the cut carries no abcd-only case; `go:embed`
  reaches only files under the embedding package's directory, and `.abcd/` is
  denied to released binaries.
- **The digest is JSON with a schema version, read strictly.** Read through
  `jsonstrict` (unknown fields, duplicate keys and trailing content refused),
  capped in size, each line passed through `termsafe.Sanitize` again on read.
  Grounds: the same posture as every other embedded default (`rules.json`,
  `guard.json`), and the intent's "sanitised as every other text abcd reads at
  run time".
- **Each digest entry is one changelog line, with every record it cites.** A
  line that cites two records is stored once with both ids, not copied per
  record. Grounds: the line is the one source (scope condition
  cond-2610170635096007), and two copies of one line would show twice.
- **A gap in the chain is found, never guessed.** Each release stores the tag
  it was cut from, so walking down from the running release finds every
  release in the range; a release the chain does not reach, or a range that
  starts below the first described release, is named as not described, with
  the release notes' published address (`<releaseOrigin>/releases/tag/<tag>`,
  the origin `internal/core/update` already pins), and the summary says it is
  partial. Grounds: the intent's "never fills the gap with a guess", and a
  derived link needs no fetch.
- **The digest is seeded from the derived CHANGELOG sections.** The first
  digest carries every release from v0.7.0 on, whose sections `launch ship`
  derived from records and whose lines cite record ids, each line copied from
  `CHANGELOG.md` and its impact read from the cited record. Releases rolled by
  hand (v0.6.9 and earlier) are named as not described. A test holds every
  digest line equal to its CHANGELOG line. Grounds: scope condition
  cond-2610170635090370 offers either treatment of hand-rolled sections; naming
  them is the one that cannot misstate, and the seed lets an update from any
  recent release summarise in full on the first shipped digest.
- **"Needs you to act" means a breaking record.** An entry needs action when
  any record it cites has `impact: breaking`, the one field the cut already
  carries per record (`release.Entry.Impact`). Grounds: the changelog's own
  rule states a break as an Added line, so the impact, not the section, is the
  signal; nothing new is asked of the composer.
- **The default-change table names a record, not a release.** Each entry of
  `internal/core/ahoy/defaults/default-changes.json` is a setup key and the
  `itd-`/`iss-` record that changed its default; the release comes from the
  digest. A test refuses an entry whose key is not a setup question key
  (`SetupFixedValues` or `helpFor` answers it). Grounds: versions are derived
  at the cut (the derived changelog), so a release written by hand when a
  default changes would be a guess; a record not yet in a digest (a dev build)
  counts in no release.
- **A changed default counts only where the repository takes the default.** A
  key the repository's layer sets is unaffected by its default, so it waits on
  nothing. Grounds: the product thinker's "offered only when something is
  required".
- **"Decide later" is read from the setup answers records of this checkout.**
  A new `interview.Latest(place, name)` returns, per question id, the newest
  recorded value across the records of one interview. A checkout with no
  records (a fresh clone or worktree) counts every unset question as never
  answered, and so errs towards offering. Grounds: one source, the record
  setup already writes; the error costs one "not now" and never a missed
  question.
- **The store is abcd's user-level home, keyed as its other stores are.**
  `~/.abcd.noindex/after-update/<root-sha>/<tag>.json` holds a repository's
  answer for one release, created exclusively (`O_CREATE|O_EXCL` through
  `fsutil`'s guarded home-scope maker), so of two sessions answering together
  the first wins; `~/.abcd.noindex/after-update/news-seen` holds the newest
  release whose general news this computer was shown, replaced atomically and
  only ever raised. Grounds: the worktree and transcript stores key on the root
  commit already ([adr-2610031751065746](../../decisions/adrs/2610031751065746-the-worktree-store-lives-under-the.md));
  the user-level home is host-agnostic where the plugin's data directory is
  not; per-user state stays out of the repository.
- **Where the general news starts.** The range starts at `news-seen`, else the
  binary record's `previous_tag` (read as `ahoy.TakeUnseenUpdate` reads it,
  without its claim), else the repository's `setup_version`, else the running
  release alone; each candidate passes `ParseReleaseTag` or is skipped.
  Grounds: the newest fact on disk about what this computer last knew wins, and
  each fallback is the intent's named source (scope condition
  cond-2610170635095099).
- **`version.upgrade` gains a direction.** It is reported only when the
  running release is newer than `setup_version`, and its fix hint names
  `abcd ahoy install --only-waiting`; `stepVersionStamp` never writes a version
  older than the one recorded. Grounds: Carol's criterion, and a comparison the
  gap already makes by string equality only.
- **The hook's line is one constant.** It carries no version and no count,
  and reads: "abcd: an abcd update has news for this session; after the
  person's first message, run abcd ahoy after-update and relay what it prints
  at the start of your first reply." Grounds: the fixed-text rule of the session-start stdout
  (iss-2608241115201044); the verb's output reaches context by the agent's own
  tool call, the channel every abcd verb already uses, and that output carries
  only numbers, checked tags and digest text.
- **A session with no person records nothing.** The hook writes nothing, and
  bare `after-update` and `--full` write nothing; only `--answer` and `--seen`
  write, and `commands/ahoy.md` tells the agent to run them only with a
  person's reply. Grounds: the binary cannot tell a headless agent from one
  with a person, so the record is tied to the act a headless run never
  performs, the person's answer.
- **Amended 2026-10-17 by the agent, building step 1: a release tag's
  components are bounded at nine digits, and the refusal never echoes the
  value.** `launch.ParseReleaseTag` accepts each component as `0` or one to
  nine digits without a leading zero, so every component fits an int32 on
  any platform and a whole tag is at most 30 bytes; its error names the form,
  never the value. Grounds: the spec asks for bounded components without a
  bound; nine digits is far above any release and keeps the value from a
  tracked file short, and a parser whose input is often a tracked file must
  not hand that text to a caller that relays its error.
- **Amended 2026-10-17 by the agent, building step 1: the stamp keeps a
  recorded release against any running version that is not a release at
  least as new.** `stepVersionStamp` writes the running version unless the
  recorded value is a release tag and the running one is older or not a
  release tag at all (a dev build, a pre-release); a recorded value that is
  not a release tag is replaced as before. Grounds: "never records a version
  older than the one recorded" cannot be judged against a dev build, and
  writing `dev` over a teammate's committed release is the downgrade the
  criterion forbids.
- **Amended 2026-10-17 by the agent, building step 2: the digest's shape.**
  `{"schema_version": 1, "releases": [...]}`, releases newest first, each
  `{"tag", "base_tag", "entries"}`, each entry `{"line", "records": [{"id",
  "impact"}]}`, where `line` is the composed wording without the citation
  suffix the cut appends and the entries keep the CHANGELOG section's order.
  `base_tag` is `""` only for a repository's first cut. Caps: 8 MiB per
  document and 4096 releases, and per release the cut's own caps (500
  entries, 32 records an entry, 4096-byte lines, 32-byte ids). The file is
  written in one canonical form (two-space indent, HTML characters
  unescaped), so an append changes only the release it adds, and a line the
  reader's sanitising would change is refused at the append rather than
  stored changed. Grounds: the spec names the fields, not their form; the
  canonical form keeps a cut's diff to its own release, and storing lines
  byte-equal to the CHANGELOG is what the seed test holds.
- **Amended 2026-10-17 by the agent, building step 2: a gap names a span,
  not a guessed list.** The walk stops at the first release the chain
  reaches that the digest does not carry, and the gap reads "the releases
  after `<from>` through `<that tag>`", with that tag's notes address and the
  release list's (`<releaseOrigin>/releases`). A `from` of `""` is the
  running release alone, and a `from` at or above the running release is an
  empty range. Grounds: below a missing release the chain cannot say which
  releases exist, so naming any one of them would be the guess the intent
  forbids.
- **Amended 2026-10-17 by the agent, building step 2: the release origin
  moved to `core.ReleaseOrigin`.** `internal/core/update` now reads its
  `releaseOrigin` from the leaf package `internal/core`, and the digest names
  notes addresses from the same constant. This touches `internal/core` and
  `internal/core/update`, outside the footprint. Grounds: update depends on
  ahoy, and ahoy will read the digest (steps 4 and 5), so the digest cannot
  import update; a second copy of the origin would break
  [`one-canonical-primitive`](../../principles/one-canonical-primitive.md).
- **Amended 2026-10-17 by the agent, building step 2: the seed is generated
  once and held by tests, not by a kept generator.** A one-off script copied
  the seventeen derived sections (v0.7.0 to v0.15.0) and read each cited
  record's impact from its terminal folder; tests hold every line equal to
  its CHANGELOG line, every base tag to the release below it, every impact
  to its record's, and the file to its canonical form. Grounds: from the
  next cut on the cut itself appends, so a generator would be dead code.

### Known limits, stated, not claimed

- An agent that runs `--seen` or `--answer` without a person (against the
  plugin page) marks the news seen or the offer answered. Nothing in the binary
  can tell; the plugin page is the control, and `abcd ahoy after-update --full`
  still shows the summary, and `abcd ahoy` still lists the waiting setup.
- A host without hooks gets no line; `abcd ahoy` lists the waiting setup and
  `abcd ahoy after-update` shows the summary (scope condition
  cond-2610170635092426).
- A plugin root whose binary has not been swapped shows nothing new: the
  running binary's version is the "updated to" side (scope condition
  cond-2610170635092640).

### How each criterion is met

itd-2610161616086564 (the offer):

1. **The one-line offer, nothing written before the answer.** Step 6 composes
   the offer line from `setup_version`, the running release and the waiting
   count; `--full` adds the titles (step 6); step 8's hook line leads the agent
   to it; bare `after-update` writes nothing (step 7's test).
2. **Nothing needed, no offer.** `afterupdate.Pending` reports no offer when
   `ahoy.Waiting` is empty (step 6); `abcd ahoy` keeps listing
   `version.upgrade` (step 1).
3. **Yes asks only the waiting set and records the version.** `ahoy install
   --only-waiting` asks exactly `ahoy.Waiting`'s questions and settings, never
   one answered with a value or deferred `later`, and `stepVersionStamp`
   records the running release (step 7).
4. **Not now is not repeated.** `--answer not-now` writes the release's record
   (step 6); `Pending` reads it (step 6); `abcd ahoy` still lists the gap with
   `--only-waiting` in its fix hint (step 1).
5. **The verb records it, keyed on repository and release, in abcd's data
   directory; the hook writes nothing.** Steps 6 and 8, with a test that the
   hook leaves the store unchanged.
6. **A new release offers again.** The record is keyed on the release (step 6).
7. **No person: nothing run, nothing written; `--yes` never answers a value
   question.** The hook writes nothing and only the answer writes (steps 6 and
   8); a test holds that `ahoy install --yes --only-waiting` leaves every
   waiting value question unset (step 7).
8. **Matching versions or a dev build: no offer.** `ParseReleaseTag` refuses
   `dev`, and equal versions wait on nothing (steps 1 and 6).
9. **A newer committed setup version: no offer, never a downgrade.** Step 1.
10. **No network; nothing unchecked from tracked files.** Every input is a
    file on disk or the embedded digest; `setup_version` passes
    `ParseReleaseTag` before it reaches any output (steps 1 and 6); the
    zero-network test covers the hook and the verb (step 8).

itd-2610161617096084 (the summary):

1. **One line per release, the full summary one command away, action first.**
   Steps 2 and 6 (`--full` orders entries needing action first and cites ids).
2. **Skipped releases are all covered and named.** The chain walk (step 2).
3. **What waits here apart from abcd's news; news once per computer, waiting
   once per repository.** Two lines from two sources, two records (step 6).
4. **A release the digest lacks is named with where its notes are; never a
   guess, never presented as complete.** Step 2's gap report, rendered by
   step 6 with `partial: true` in `--json`.
5. **No network; only the binary's digest.** Steps 2 and 8.
6. **Shown once, again on request.** `news-seen` (step 6); `--full` shows it
   again at any time and writes nothing (step 7).
7. **No person: not counted as seen.** Only `--answer` or `--seen` raises
   `news-seen` (step 6).
8. **Text only from the binary's digest, sanitised.** `releasedigest` reads
   only its embedded file and sanitises every line (step 2); a test runs the
   verb in a repository with its own `CHANGELOG.md` and asserts none of it
   appears (step 7).

### Proof

Every step is test-first, each test watched fail before its change. The
end-to-end proof is real, per the product thinker's rule that real runs are the
proof: before the spec closes, a binary built at a test tag from this branch
(with a digest carrying that tag) runs in a scratch repository set up by the
previous release's binary, and a live host session's first reply is captured
before and after the answer, with the store and `.abcd/config.json` shown
before and after.

### Coordination

- Step 3 changes `internal/core/release`, which every cut runs through, so it
  lands while no cut is in flight, and the next cut is the first to write a
  digest.
- Steps 7 and 8 change `internal/surface/cli`, whose tests can raise a keychain
  prompt on a person's machine; they run in CI or a fenced lane, not in a live
  session.
- Every step reserves its footprint with `abcd reserve` before it starts.

### Out of scope

- Answering the offer from a plain Terminal outside a host session: `abcd ahoy`
  and `ahoy install --only-waiting` already serve it.
- A digest for any binary but abcd's own: the cut writes one wherever a
  repository declares it, and only abcd's binary reads one.
- Rewording a digest line for the summary: the line is the record's changelog
  line as the cut composed it.

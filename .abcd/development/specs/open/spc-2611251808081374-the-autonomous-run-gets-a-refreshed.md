# The autonomous run gets a refreshed terminal interface and a headless mode

## Summary

This spec delivers itd-2611150636498012. A drive running at a terminal shows one more line under the three live lines of itd-2611141610192096: the option Enter would accept. Space shows the next option, Enter accepts the one shown, and the option shown at rest changes nothing. One option stops the drive after the lane in hand, and two more only show detail: the full sentence of the last event that may need the person, and the log's path. An interrupt now takes two steps: the first stops the drive after the lane in hand and says how to stop now, and the second stops it now. The same drive can be started with `--headless` by a program that reads and writes JSON lines on the drive's own standard input and output, which is how a native app will later show the same state and set the same options.

The six open questions of the intent were answered by the product thinker on 2026-11-25, restated here:

1. The headless interface is JSON lines on the standard input and output of a drive the app starts as its own child. An app never joins a drive started at a terminal, and a drive ends with the app that started it.
2. The drive trusts only its own parent, over its own pipes. There is no token and no socket.
3. The list offers carrying on, stopping after this lane, and options that only show detail. No option acts on the run in any other way.
4. The drive comes first. The keys and the option line are built as a shared piece that the interviews and the build adopt in a later release.
5. The terminal keeps plain lines for a pipe or a screen reader, with no option list, and nothing more is built in the terminal for that case. The app is the accessible form.
6. The interrupt takes two steps, as above. This changes what an interrupt does today, and the start and the documentation say so.

Eight steps, each one pull request. Steps 1, 2 and 6 are leaf packages that wait on nothing and can be built today. Steps 3, 4, 5, 7 and 8 edit `internal/core/implement/loop/terminal.go` or the drive's front door and wait on spc-2611141617199772 (the drive's state as a value) and on the spec of itd-2611141610192096 (the typed event and the one writer), as each step says.

One flag is added, `--headless`. No verb, no dependency and no colour is added. No step raises the run-state schema version or the drain state's. The drive-state file of spc-2611141617199772 gains one field and its own version rises by one.

## Approach

### What is on the default branch today

- **The interrupt.** `watchDriveSignals` (`internal/surface/cli/drain_drive_signal.go`) treats the first interrupt, hang-up or termination as a stop: it closes `stop`, the loop finishes the agent's call in flight, saves the lane's work aside, releases its reservation and ends `TerminalStopped` with exit 3 and a lane left on its branch. The second signal ends the context, kills the agent's process group and exits 130 after five seconds at most (dcn-2611041608057544).
- **A stop is recorded state** (adr-2611050740453233). `haltOnSignal` (`internal/core/implement/loop/terminal.go`) writes a stop on each lane in progress with `SetBy: "a signal to the drive"`, through `haltRun` (`stop.go`).
- **When lanes stop opening.** A drain move opens no lane once `len(st.Lanes) >= st.Max` (`drain.go`), goes on driving the lanes in progress, and ends the drain `DrainStoppedCap` when they are done. `DrainOptions.PassedLanes` is the precedent for a rule held in the drive's memory and handed to every move, never written.
- **The drive replaces itself** on a new release with `syscall.Exec` (`driveReexec`, `internal/surface/cli/drain_drive_update.go`), at a boundary between moves (`TerminalOptions.AtBoundary`). The process id, the terminal and the standard streams carry over.
- **Consent.** `driveConsent` asks `Start? [y/N]` at a terminal, takes `--yes` as the scripted yes, and refuses with neither. `drivePreconditions` refuses a start under a host session's markers.
- **Keys.** `internal/term/raw.go` has `StartRaw`, the one place abcd touches the terminal's modes. It enters full raw mode: no signals from keys (Ctrl-C arrives as a byte), and no output processing. Its own handler restores the terminal on an interrupt, a termination or a hang-up and then lets the signal end the process, and `ask.Terminal`'s comment says a caller with its own handling of those signals must not use it. `ask.DecodeKeys` (`internal/surface/cli/ask/keys.go`) decodes what a read holds into keys. `internal/term/ptytest` opens a pseudo-terminal for a test, types into it and compares terminal attributes.
- **Text the drive did not write.** `termsafe.Sanitize` masks control codes and hidden runes for a terminal. Its comment records that `encoding/json` escapes only the C0 range and U+2028/9, so DEL, the C1 range, bidirectional overrides and zero-width runes pass through a JSON string raw.
- **Not there yet.** `loop.DriveState` and its file (step 4 of spc-2611141617199772). `loop.DriveEvent`, the drawing package `internal/surface/cli/drivescreen` and the one writer `driveScreen` (steps 1 to 4 of the spec of itd-2611141610192096). That spec built the seam this one uses: `Frame.Region` returns a slice of lines, `Live.Print` draws any number of them, and its tests already redraw a region of four lines.

### The layers

1. **`internal/surface/cli/optionline/`, the shared piece (ruling 4).** A list of options, which one is shown, and the one line that names it. It imports the standard library and `internal/termsafe`, and nothing of the drive, the loop or the interviews, so `ask` can import it later without a cycle. It reads no terminal: its inputs are two keys, `Space` and `Enter`, and a clock.
2. **`internal/term`, a key mode.** `StartKeys` reads single keys from a terminal that the program keeps writing to and that keeps its own signals.
3. **The loop.** `AfterLane` is the ask to stop after the lane in hand. The loop records it, opens no further lane and ends when the lane in hand has ended.
4. **`internal/surface/cli/driveproto/`, the headless messages.** Wire types, an encoder that makes every string safe, a bounded strict decoder and a queue that never blocks the drive. It imports `internal/core/jsonstrict`, `internal/termsafe` and the standard library, and nothing of the loop.
5. **The wiring, in `internal/surface/cli`.** The signal levels, the drive's own option list and what each option does (`drain_drive_options.go`), the key reader (`drain_drive_keys.go`), and the headless channel (`drain_drive_headless.go`). The terminal and the channel call the same function to apply an option, which is what makes "the same effect and the same record" true by construction.

### Stopping after the lane in hand (criterion 3)

`loop.AfterLane` (`afterlane.go`) holds one ask: who set it, from where and when. `Ask(source, at)` sets it once; a second ask changes nothing and reports that. The sources are a closed list: `option-list` (the terminal's list), `interrupt` and `app` (the headless channel). `TerminalOptions.AfterLane` hands it to the loop, and nil means no one can ask.

Once it is set:

- **It is recorded.** The loop appends one line to the record of each lane in progress, stage `stop-after-lane`, naming the source and the time, through `saveRecord`, which keeps the version a run's file states. A lane the drive passed over gets no line, as every write to it is ruled out. The drive's state value carries the ask (below), and one event of kind `stopping` goes to the surface. Today's stop keeps its own record (`SetBy: "a signal to the drive"`), so the run's records can count how each stop was set, which is the measure the intent's mechanism names.
- **No further lane opens.** Each later move is given `DrainOptions.NoNewLanes`, held in the drive's memory as `PassedLanes` is. The move then opens no lane, asks no new judgement, takes up no earlier run and gives a set-aside lane no further try. It drives the lanes in progress as before. The drain's own state is not changed and the drain is not ended, so the next `abcd drain --drive` carries on with it.
- **The lane in hand runs to its end.** Its waits are kept: a rate limit, an outage and the merge queue are waited out as they are today, inside the bounds the drive already has (`--until`, the eight hours on one wait). A wait that only precedes a lane that will now never open, the pace window among them, ends at once.
- **The drive ends** when no lane is left that it is driving: none in progress but lanes it passed over or set aside. It ends `TerminalAfterLane` (`"after-lane"`). A judgement still awaited is left unanswered and its hold is released as any end releases it. Where no lane was in hand when the ask came, the drive ends on its next pass, and the ask is in the log, the event and the state value only, since there is no run to record it on.
- **No new release is taken.** `AtBoundary` is not called once the ask is set. So the ask never has to cross a re-execution, and no hidden flag carries it.
- **Every other stop still wins.** A second interrupt, a person's stop file and `--until` end the drive as they do today, with their own endings.
- **It cannot be undone.** Ruling 3 allows no option that acts on the run beyond this one. A person who changes their mind lets the lane end and types `abcd drain --drive`, which carries on.

`renderDriveEnd` says `ended: stopped after its lane, as asked at the terminal at 09:17` (or `by an interrupt`, or `from the app`), with `to resume: abcd drain --drive`. The exit is 0, as it is for `--until`: both are bounds the person set, and nothing is left on a branch to take up.

**The state value and the state line.** `DriveState` gains `StopAfter`, absent or the source and the time, and the file's own version rises by one. The one composing function of spc-2611141617199772 puts it in the line's third part: `stops after this lane, set at the terminal 09:17` where the state names no act, and after the act where it names one. `abcd implement status` and the board show the composed line and so show it with no further change. The plain `state:` line, the log and the JSON always carry the whole. At a terminal the drawing package fits the part in three forms, the longest that fits: with source and time, with source, and `stops after lane`; a test holds that the source is still on the line at 50 columns.

### The two-step interrupt (ruling 6)

The drive has three stop levels, and each signal raises it:

| Level | What it does | Reached by |
| --- | --- | --- |
| 1, after the lane | `AfterLane.Ask("interrupt", now)`, which changes nothing where the ask is already set | the first interrupt |
| 2, now | today's first signal: `stop` is closed | a second interrupt; a termination or a hang-up from any level below 2 |
| 3, kill | today's second signal | any signal at level 2 |

- A termination and a hang-up keep today's meaning. Neither is a key a person presses to mean "finish this first", and a closing terminal or a `kill` from a script should not leave the drive running a lane for another hour.
- The first interrupt never stops the drive now, whatever was set before it. Where the stop after the lane was already set from the list or the app, the first interrupt sets nothing, says `already stopping after the lane in hand; Ctrl-C again to stop now`, and the second stops now. Ruling 6 gives the first interrupt one meaning, and a key whose effect turned on a choice made an hour earlier would cost a lane on one stray press.
- Before the loop's first move there is no lane in hand, so an interrupt during the start or the live proof is the stop it is today, with today's words and exits.
- The words: at level 1, `stopping after the lane in hand; Ctrl-C again to stop now`. At level 2, `stopping now: the agent in a call finishes that call, then the lane is saved and its reservation released; Ctrl-C again to kill it and exit at once`. At level 3, today's line.
- **Where the start says so.** The start keeps the seven lines of itd-2611141610192096. One line follows the yes, with the log's path: `Ctrl-C: stop after this lane; twice: stop now`. The full plan on `?` gains a `stop` line with the three levels, the same line is written to the log at every start, and the headless `hello` carries it. `commands/drain.md`, the brief page and the command's long help are rewritten where they describe the first and second signal.

This holds wherever the drive runs: at a terminal, with plain lines, and headless, where an app that wants to stop the drive now sends its child an interrupt twice or a termination once, or closes its pipes (below).

### The option list and its line (criteria 1, 2, 4, 5, 7)

`optionline.List` is an ordered list of options, each with an id, a label and a kind (`none`, `act` or `show`). The first is the rest option and must be of kind `none`; the constructor refuses a list that starts otherwise.

- `Space` shows the next option and wraps from the last to the first.
- `Enter` returns the option shown and puts the list back at rest, whatever was accepted. So a second Enter accepts the rest option and neither repeats nor undoes the first.
- Any other key puts the list back at rest and does nothing else.
- A read that holds more than one key is a paste or keys typed ahead. It is dropped whole and the list goes back to rest. Without this rule a pasted `one two` and a newline would show the next option and accept it.
- An option shown and not accepted goes back to rest after ten seconds without a key, so a Space pressed and forgotten does not leave a stop one stray Enter away.

`optionline.Line` composes `Space: next option   Enter: <label>`, cut to the window by the caller's frame. The option shown is told apart by its words. No colour is written, as in the footer.

The drive's list (`drain_drive_options.go`):

| Id | Label | Kind | What Enter does |
| --- | --- | --- | --- |
| `carry-on` | `carry on (no change)` | none | nothing |
| `stop-after-lane` | `stop after this lane` | act | `AfterLane.Ask`, one event line that says so and that Ctrl-C twice stops now |
| `show-last-event` | `show what needs you` | show | prints the full sentence of the last event that may need the person, wrapped at word breaks, or `nothing has needed you so far` |
| `show-log` | `show the log's path` | show | prints the log's path, as the two lines the start prints |

Once the stop after the lane is set, by any source, the list is rebuilt without that option and its rest label reads `no change (stop set)`. Every label is 21 columns or fewer, so the whole line is under 50, and a test holds each label to that.

One function, `applyDriveOption`, does what an option does and returns what a surface is to show. The key reader and the headless channel both call it. The last event that may need the person is kept in the writer's memory from the `Acts` events it has seen, so this spec does not wait on the attention file of the sibling spec's step 5.

### Reading keys (criteria 1, 2, 6, 7)

`term.StartKeys(f, hooks)` (`internal/term/keymode.go`) is a second session beside `StartRaw`, in the same package so the rule that no call site handles the terminal's modes still holds. It differs from raw mode in three ways, each for a reason the drive has:

- **It clears only line buffering and echo.** Keys still raise signals, so Ctrl-C is the same interrupt in every mode and goes through the one signal path above. Output processing stays on, so every writer of the drive, its standard error and any child that inherits the terminal are unaffected.
- **It relays no signal.** The drive's own handling owns the interrupt, the termination and the hang-up. The session watches only the stop and the continue: on Ctrl-Z it restores the terminal, stops the process as the key would have, and on the continue enters key mode again and calls the `Continued` hook, on which the drive draws its region afresh below what the shell wrote.
- **It refuses a background job.** It enters only when the process group is the terminal's foreground group. The session ignores the background-read signal while it lives, so a drive moved to the background gets an error from its read and not a stop; the reader then parks and looks again at each tick of the redraw, and reads again once the drive is back in the foreground.

It uses `syscall.Termios` with the per-platform request constants, as `isterminal_darwin.go` and `ptytest` do, so no dependency is added. On a platform with neither it reports that it cannot, and the drive runs without keys.

The terminal is restored on every way out: the drive's deferred guard on a return or a panic, before the kill's exit, before `driveReexec` (the new process enters key mode itself), and on Ctrl-Z.

Keys are read only when all of these hold, decided by one function behind a package variable that tests pin, beside `driveWindow`: the output is live (the sibling spec's `driveWindow`: a terminal, `TERM` set and not `dumb`, 20 columns or more), the standard input is a terminal, it is the same terminal as the output, and `StartKeys` succeeded. Where the output is not live, or the input is not that same terminal, the drive writes plain lines and no region, as the sixth criterion asks; this narrows the sibling spec's decision, which reads the output alone, and step 5 makes the change in that one function. Where only `StartKeys` fails (a platform without the key mode, a drive started in the background), the three lines are drawn with no fourth and no key is read. `NO_COLOR` is not read by it.

The reader (`drain_drive_keys.go`) is one goroutine: it reads, decodes with `ask.DecodeKeys`, maps a space and Enter onto the list's two keys and everything else onto "other", and hands the result to the writer under the writer's lock. The option line is the region's fourth line, drawn by `Live.Print` with the other three, so an event still lands above all four.

### Plain lines (criterion 6; ruling 5)

Where the output is not live, or the input is not the output's terminal, nothing here is drawn or read: no key, no option line, no control code. The drive writes the plain lines of itd-2611141610192096. The stop after the lane is then set by an interrupt, and the line after the yes says so. Nothing else is built for this case.

### The headless mode (criteria 8 to 11; rulings 1 and 2)

`abcd drain --drive --headless` is started by a program, which writes commands to the drive's standard input and reads messages from its standard output, one JSON object a line. `--headless` without `--drive`, with `--json`, or with a terminal on the standard input or output is refused with exit 2: at a terminal the terminal mode is the interface.

**Messages from the drive.** Each has a `type`. Times are RFC 3339 in UTC and durations are whole seconds.

```text
{"type":"hello","protocol":1,"abcd":"…","pid":4242,"interrupt":"…","options":[{"id":"carry-on","label":"carry on (no change)","kind":"none"},…]}
{"type":"plan","lanes":8,"runs":40,"ends":{…},"runs_on":"…","review":["…"],"full":[{"label":"…","text":"…"}],"awaiting":"start"}
{"type":"log","path":"…"}
{"type":"state","state":{"word":"working","since":"…","until":null,"on":"…","do":"","stop_after":null,"line":"…"},"lanes":{"cap":8,"opened":2,"done":1,"in_flight":1,"aside":0,"back":1},"lane":{"issue":"…","title":"…","stage":"implement","since":"…","agent":true}}
{"type":"event","at":"…","kind":"wait","issue":"…","run":"…","lane":"…","stage":"…","role":"…","title":"…","opened":2,"wait":30,"cause":"…","acts":false,"quiet":false,"sentence":"…"}
{"type":"options","options":[…]}
{"type":"reply","id":"7","ok":true,"result":{…}}
{"type":"dropped","events":12}
{"type":"end","ended":"after-lane","exit":0,"message":"…","counts":{…},"resume":"abcd drain --drive"}
```

- `state` is the three live lines as typed values: the state value, the progress of the lanes and the lane in hand. It is sent on every change and never on a tick; a client computes an elapsed time from `since`.
- `event` is the loop's typed event. A detail written for a host session is not sent, as it is not shown at a terminal.
- `options` is sent when the list changes, which is when a stop after the lane is set.
- `end` is the last message of every run, a refused start included, with the words and the exit code the process ends on.
- `protocol` is 1. A change that removes or renames a field or a type raises it; an added field does not.

**Commands to the drive.** A closed set of three:

```text
{"type":"start","id":"1"}
{"type":"decline","id":"2"}
{"type":"option","id":"3","option":"stop-after-lane"}
```

`start` and `decline` answer the plan, as `y` and anything else do at a terminal; with `--yes` the plan is sent and no answer is awaited. `option` accepts one option of the list by its id and is answered by a `reply` whose `result` is what `applyDriveOption` returned: nothing for `carry-on`, the ask's source and time for `stop-after-lane`, the sentence for `show-last-event`, the path for `show-log`. There is no command to show the next option: cycling is the terminal's way of choosing, and a client names the option it wants.

**The same log and the same state file.** A headless drive writes its log and its state file as any drive does, so `abcd implement status` and the board read it unchanged.

### The channel is a trust boundary

Ruling 2 says whom the drive trusts: its own parent, over the two pipes it was started with. That leaves four ways the channel could be misused, and each has a rule and a test of its own.

**What comes in is parsed as hostile, though the parent is trusted.** A bug in a client must not become a fault in a drive that holds reservations.

- A line is at most 4096 bytes. A longer one is discarded up to its newline without being held in memory, and counts as refused.
- A line is one JSON object, decoded with `jsonstrict.Decode` (`internal/core/jsonstrict`): a duplicate key, an unknown field, an unknown type, trailing data, text that is not valid UTF-8 and an option id not in the current list are each refused with a `reply` carrying a fixed code (`too-long`, `not-json`, `unknown-type`, `unknown-field`, `unknown-option`, `not-started`, `already-started`, `bad-id`) and no text taken from the input.
- An `id` is at most 64 characters of letters, digits, `.`, `_` and `-`. Any other id is refused and not echoed.
- No command names a path, a program, a record or free text, and none is passed to a shell, a file call or a git command. The only effects a command can have are the start, the decline and `applyDriveOption` on a listed id.
- After 100 refused lines in a row the drive takes no further command, says so once, and runs on. It goes on reading and discarding its input, unparsed, so that it still sees the input's end. Refused lines are counted in the log at most once a minute and never written to it, so a faulty client cannot fill the disk.
- A client that sends good commands and reads no reply cannot grow the drive's memory. Replies wait in a queue of their own of 64; while it is full the reader takes no further line, so the wait falls on the client's own writes and never on the drive's loop.

**What goes out is made safe for a reader that will draw it** (criterion 8). Every string the drive did not compose itself (a title, a cause, a reason, a path, a sentence) passes `termsafe.SanitizeLine` before it is encoded, because JSON's own escaping leaves the C1 range, bidirectional overrides and zero-width runes raw. One message is one line whatever the text holds: the encoder is `encoding/json`, which escapes a newline, and a test feeds a title that is itself a forged message line.

**Nothing but the drive writes to the channel, and nothing but the drive reads it.** A lane's agent is less trusted than the drive, and a child that inherited the drive's standard output could write a forged `state` or `end` to the app, while one that inherited its standard input could swallow a command. So the first thing a headless drive does, before it starts any process, is to move the two pipes to descriptors of its own that close on exec, point descriptor 0 at the null device and descriptor 1 at its standard error, and point the command's output at standard error too. A stray write to the standard output, by the drive's own code or by any child, then lands on standard error and never on the channel. Before `driveReexec` the two pipes are put back on 0 and 1 under `syscall.ForkLock`, so no child can be started in between, and the new process moves them away again at its start. Standard error is not part of the protocol, and the reference page tells a client to treat it as untrusted text.

**The drive opens nothing a third process could find.** No socket, no named pipe, no token and no file that carries a command. A drive started without `--headless` has no channel at all: it decodes no line of its input as a command and writes no message, so there is nothing for an app to join (ruling 1).

**The start is still the person's.** `--headless` changes none of `drivePreconditions`: a start under a host session's markers is refused as today, and so is one with a credential in the environment. A `start` message is as strong as `--yes` and no stronger, since whoever can start the process can type the flag. With no `--yes`, nothing starts and nothing is reserved until a `start` arrives, and an input that ends first is a decline.

### A client that is slow, silent or gone (criterion 11; ruling 1)

The drive never waits on its client, and it ends with the app that started it.

- Messages go through a queue of 256 with one writer goroutine. When the queue is full, a newer `state` replaces the unsent one, events are dropped and counted, and the next message written is `dropped` with the count. A `reply` and the `end` are never dropped: replies are bounded by the reader, as above, and the `end` is one message.
- At its end the drive gives the writer five seconds to send what is queued, then exits.
- **Slow or silent.** A client that holds both pipes open and reads nothing, or sends nothing, changes nothing: the queue drops what it must and the drive runs to its ordinary ends, as a drive with plain lines does.
- **Gone.** An input at its end, or an output whose write fails as closed, means the app has gone: both happen when the parent exits, and a client that closes either end on purpose is saying the same. The answer the product thinker chose for question 1 is the one whose process ends with the app, and ruling 1 lets no app join a drive afterwards, so a drive that ran on would be one no app could show or stop. The drive therefore takes it exactly as a hang-up, which is what a closing terminal sends a drive today: stop level 2, the agent in a call finishes that call, the lane is saved aside and its reservation released, and the drive ends `TerminalStopped` with today's exit. It says once on standard error and in the log that the channel closed. The broken pipe's own signal is already caught (`watchDriveSignals`), and the end's five-second wait is skipped, since nothing can be sent. Before the loop's first move it is the stop an interrupt is there. `abcd drain --drive`, or the app starting a drive again, carries on with the drain.
- A program that wants a drive to outlive it does not use `--headless`: it starts `abcd drain --drive --yes` with plain lines. The reference page says both.

## Technical decisions

Each was settled by the plan, with its reason. None changes a ruling.

| Choice | Settled as | Why |
| --- | --- | --- |
| What "stop now" is on the second interrupt | Today's first signal, the orderly stop; the kill moves to a third press | The intent's question 6 uses "stops at once" for today's first interrupt. The other reading would leave no orderly stop on the keyboard |
| A termination and a hang-up | Unchanged: stop now, then kill | Neither is pressed to mean "finish this lane first" |
| An interrupt when the stop after the lane is already set | Sets nothing and says how to stop now; the next one stops now | Ruling 6: the first interrupt has one meaning. One stray press must not leave a lane on its branch |
| An interrupt before the first move | Today's stop, unchanged | There is no lane in hand to finish, and the start's exits stay as they are |
| Where the ask to stop after the lane is kept | In the drive's memory, in each lane's record, and in the drive's state value | A field in the drain's state would raise its schema version, since its reader is strict. The ask need not outlive the drive: a person who starts the drive again wants it to run |
| How the ask survives a re-execution | It does not need to: no release is taken once it is set | The drive is about to end. A hidden flag to carry it would be one more thing to forge and to test |
| How "no further lane" is enforced | `DrainOptions.NoNewLanes`, in memory, as `PassedLanes` is | The cap already makes a move open no lane and finish those in progress. The drain itself must stay open for the next drive |
| The exit of a drive that stopped after its lane | 0 | As for `--until`: a bound the person set, with nothing left on a branch |
| Undoing the stop after the lane | Not offered | Ruling 3 allows one option that acts on the run. The cost is one command to start again |

## How the Acceptance Criteria are met

The criteria are numbered in the order the intent lists them. Criterion 12 is the two-step interrupt of ruling 6, which the planning appended to the intent as its twelfth.

1. **At rest the line names an option that changes nothing, and Enter leaves the drive as it was.** `optionline.List`'s first option is of kind `none` by construction (step 1), and the drive's reader applies it (step 5). Proved by `list_test.go` and by `drain_drive_keys_test.go`: after Enter at rest the loop's `AfterLane` is unset, the state file's bytes are unchanged and no event was written.
2. **Space names the next option and wraps to the first.** `List.Space` (step 1), drawn as the region's fourth line (step 5). Proved by `list_test.go` over lists of one to five options and by the pseudo-terminal test of step 5.
3. **Stop after the lane: the lane runs to its end, no lane opens, the drive stops, and the state line and the run's record say who set it.** `loop.AfterLane`, `DrainOptions.NoNewLanes`, `TerminalAfterLane`, the record line and `DriveState.StopAfter` (step 3), set from the list (step 5). Proved by `afterlane_test.go` on the loop's fixture worlds and by `drain_drive_options_test.go`.
4. **After an option is accepted the line shows the rest option.** `List.Enter` (step 1). Proved by `list_test.go` and by step 5's test that a second Enter after a stop sets nothing and prints nothing.
5. **At 50 columns or more the three lines are redrawn with every event above them, and the option line does not wrap.** The region of four lines through `Live.Print` (step 5), every label held to 21 columns (steps 1 and 5). Proved by `footer_test.go` and `live_test.go` at 50, 80 and 120 through the sibling spec's test terminal, which counts wrapped rows.
6. **Not a terminal, or `TERM=dumb`: no key is read, no option line and no control code is written.** The decision function of step 5. Proved by `drain_drive_keys_test.go` for a pipe on the output, a pipe on the input, `TERM=dumb` and `TERM` unset: `StartKeys` is never called (a counting seam), the input is never read, and the output equals the sibling spec's plain fixture byte for byte.
7. **`NO_COLOR`: no colour, the keys work, the option is told by its words.** No colour is written at all (steps 1 and 5). Proved by step 5's test with `NO_COLOR=1`: no `ESC [ … m` in the output, Space and Enter act, and every two labels of the list differ in their words.
8. **Text the drive did not write is made safe in the footer and over the headless interface.** The option line and the detail lines take masked text only (steps 1 and 5); the encoder masks every such string (step 6). Proved by `line_test.go`, by step 5's test of `show what needs you` over a sentence with an erase-screen code and a bidirectional override, and by `encode_test.go`.
9. **A headless client reads the three lines as typed values and sets each option, with the same effect and the same record.** The `state` message (steps 6 and 7) and the `option` command through `applyDriveOption` (step 8). Proved by `drain_drive_headless_commands_test.go`: for each option, the loop's state, the run's record line and the state file after the command equal those after the same option accepted at a terminal, but for the source.
10. **A headless run and a terminal run of one recorded fixture agree in every value.** Both consume the same `loop.DriveEvent` and `loop.DriveState` (step 7). Proved by `drain_drive_headless_parity_test.go`: the plain lines the drawing package composes from the decoded messages equal the plain run's lines byte for byte, and the three region lines composed from the last `state` equal the terminal run's last region.
11. **A client that is slow or silent is waited on by nothing, and the run works as a drive with plain lines does; a client that has gone ends the drive.** The queue (step 6) and the closed-pipe rule (step 7). Proved by step 7's tests: with a client that never reads and one that never sends, the fixture run ends as the plain run does, in the same time on a fixture clock; with a client that closes either end, the drive stops as on a hang-up. The criterion's "no client connected" predates ruling 1; the notes above give the records agent its two halves.

12. **The first interrupt stops the drive after the lane in hand and says how to stop now, and a second stops it now (ruling 6).** The three levels (step 4) over `AfterLane` (step 3). Proved by `drain_drive_signal_test.go`.

# A drive keeps its own pull requests and its own checkout moving

## Summary

This spec delivers itd-2611141610201875. A pull request the merge queue removed is armed again by the loop, at most three times at one head, and the drive says so on one line. Past that bound the lane is handed back with the failed check, the command that re-runs it and the command that arms the pull request again. The drive fast-forwards its own checkout to origin's default branch at its start and whenever a lane ends, where that is safe. Where it is not, the checkout is left exactly as it was and the drive says what blocks it.

The product thinker answered the intent's first four questions on 2026-11-15 (decisions 1 to 4). The fifth was settled on 2026-11-25: a declined fast-forward is one event line, it is named in `abcd implement status`, and the view of a person's drives across machines carries it. It is not on the state line. The second criterion was widened the same day to the drive's start. Decision 1 left the number of re-arms to the run, and this spec proposes three.

The fast-forward is the one write this spec makes outside the run's own worktrees. It moves the person's checkout. Its rule is that it never discards local work and never moves a branch the person has taken elsewhere, and steps 4 and 5 test that rule case by case.

Nothing here adds a command or a flag. One step raises the run-state schema version by one (step 1). The drive's state file gains one field (step 6). Nothing is published to origin: the view by login is an intent of its own, and step 6 only shapes the field it will carry.

The lab on drive operations (lab-261114145658-67e1f9b) measured the removals (F-6, F-10, F-18) and the fast-forward (F-12, F-19) on fixtures and built neither. So every step here is new code with no prototype.

## Approach

### What is on the default branch today

All paths are under `internal/core/implement/loop/` unless they say otherwise.

- **The watch.** `watchQueue` (`queue.go`) reads an armed lane's pull request through `QueueStateQuery`. One that is open, outside the queue and no longer armed goes to `droppedRefusal`, which waits while a release's hold stands and otherwise refuses with `outOfQueue` set. The refusal names the forge's reason, the failed checks of the last merge group (`failedGroupChecks`) and the arming command (`rearmArgs`). It arms nothing: the file's header says a removed pull request is "never re-queued into the same failure". The same file already arms again in one case. A pull request that sits armed and CLEAN outside the queue is queued, and where the forge refuses that, `toggleArming` withdraws and re-arms it, at most `maxToggles` (three) times at one head, counted in `Landing.Toggles` (`land.go`). Before it does, it asks the reservation's fence (`fence`) and the merge gate (`askMergeGate`).
- **A drain's parked lanes.** `watchParked` (`drain_finish.go`) takes the landing step of a lane parked on its pull request. A refusal with `outOfQueue` sets the lane's state to `ParkedDropped` with the refusal as its note. The lane stays parked and is watched again at every move.
- **What the drive says of them.** `terminal.sayMove` (`terminal.go`) says a judgement, each routed hand-back, each finished lane and an opening. It says nothing of a parked lane's note, so a line the watch records reaches the run's record and not the terminal.
- **The records a drive writes into the checkout.** `routeHandBack` (`drain.go`) makes two writes, both uncommitted: for a user moment, `capture.Promote` writes an intent draft and the issue's `related_intents`; for a trust rule, `markDecisionNeeded` writes `decision_needed:` onto the open issue. A move planned from origin makes neither where the checkout does not hold the record as origin does (`notHeldAsOrigin`); it then routes the hand-back `home` and names `abcd capture promote <iss>`. The hand-back itself is published on origin as the tombstone of the reservation's release. These two writes are the 28 drafts and 44 back-links of the incident note's event 6.
- **The hold.** `terminal.run` reads what the drive holds once (`startHold`: `readRemoteIdentity`, then `proveCheckoutHooks`, which compares the checkout's in-tree hooks with origin's tip). Every pass and every hooked git command compares it again (`heldBeforeGit`, `heldBeforeGitIn`), and a difference ends the drive. `startHooksRefusal` (`remoteid.go`) refuses the start when the checkout is behind a tip that holds other hooks (`behindTip`), and its remedy is a hand-typed `git pull --ff-only`. `proveCheckoutHooks` also refuses when the repository does not hold origin's tip yet, with `git fetch origin` as the remedy.
- **The boundary.** `terminal.boundaryDue` is set after every move. `TerminalOptions.AtBoundary` is called there once nothing is in hand (`boundaryHeld`, `inHand`), and a release build uses it to take a new release by starting itself again (`internal/surface/cli/drain_drive_update.go`).
- **Nothing moves the checkout.** No code in the loop merges, pulls or fast-forwards the checkout the drive runs from.

### Arming a removed pull request again (criterion 1; decision 1)

A new function `rearmDropped` in `queue.go` stands between `watchQueue` and `droppedRefusal`. It arms the pull request again when all of these hold, and otherwise falls through to the refusal:

1. No release's hold stands, and the holds were read. This is the check `droppedRefusal` makes today, and a held lane waits as it does today. Where the holds cannot be read, `droppedRefusal` goes on to its report with a clause saying so; `rearmDropped` arms nothing then and falls through to that report, since a release's withdrawal is not ruled out.
2. The forge records a removal, and its actor is the forge's own merge queue. `QueueStateQuery` gains `actor{__typename login}` on the removal event, and the rule is that the type is `Bot` and the login is `github-merge-queue`. A removal with a person as actor, with another application as actor (an application is a `Bot` too, and one that takes a pull request out of the queue was told to by someone), with no actor, or a pull request with no removal on record (its arming was withdrawn) is not re-armed. On this repository's history the queue's removals read `actor: {__typename: Bot, login: github-merge-queue}` with `reason: failed_checks` (#839, #1011). What a person's removal reads as was not observed, which is why the rule names the one shape that is re-armed and refuses the rest. A forge that names its queue otherwise re-arms nothing, which is today's behaviour.
3. The removal is later than the loop's own last arming of the pushed head. `Landing` gains `armed_at`, the run's time when the loop last armed this head: set by the landing's arming (`land.go`), by a toggle and by a re-arm. The query reads the last removal on record, whatever head it was at, so without this a removal by the queue from before a resync, or from before a person armed the pull request again after a hand-back, would read as new once anyone withdrew the arming, and the loop would arm a pull request a person had just taken out. A landing with no `armed_at` (one armed before this version) is not re-armed.
4. The removal is later than the one the landing last re-armed for. `Landing` gains `rearmed_removal`, the forge's time of that removal. A pull request found disarmed with no newer removal was disarmed by someone after the loop's re-arm, and that stands. This is the exact guard for the loop's own re-arms, since condition 3 compares the run's clock with the forge's.
5. The landing has re-armed fewer than `maxRearms` times at the pushed head. `Landing` gains `rearms`. `maxRearms` is three, a constant beside `maxToggles`.
6. The pushed head is a full object name and the ruleset mirror names a merge method, as the toggle requires; otherwise nothing is armed and the report is today's.
7. The fence and the merge gate pass, asked as `watchQueue` asks them before it queues or toggles. A gate that refuses the head leaves the pull request open with the gate's reason, a gate that cannot be read is a wait, and a reservation that is no longer this person's refuses, each as in the toggle's path.

One case stays open and is stated on the page: a pull request the queue removed while no step was looking, which a person then armed by hand and withdrew again before the next step. The removal is later than the loop's arming and was never re-armed for, so the loop arms it once; a second withdrawal stands (condition 4). Closing it needs the forge's own record of armings on the pull request's timeline, whose shape was not observed, so it is left to an issue of its own and not guessed here.

The arming is `rearmArgs`: the ruleset mirror's merge method, pinned to the pushed head. The count is raised and the removal's time and `armed_at` stored only once the forge took the arming. A lost network is the existing `netFailure` refusal and is not counted. A forge that refuses the arming is the dropped refusal with the forge's reason.

The outcome's note is one sentence: the pull request, that the queue removed it and the forge's reason, and "armed again, 2 of 3 at this head". `resyncLane` (`sync.go`) clears `rearms` where it clears `Toggles`, since a new head is a new count. It keeps `rearmed_removal`, and the arming that follows the resync sets `armed_at` anew.

The header of `queue.go`, which says a removed pull request is never queued again, and the comment on `ParkedDropped` (`drain_finish.go`) are rewritten to the new rule in the same step.

The removal's reason is never used to choose. Decision 1 is that the drive always re-arms, because the forge data cannot tell the change's own failure from another (F-10). The reason is printed and nothing more.

**The schema.** Three new landing fields (`rearms`, `rearmed_removal`, `armed_at`) are a new run-state version (`state.go`). The default branch is at 31 (`state.go`, `SchemaVersion`), so this step takes 32. No other work planned beside it claims that number: the remaining steps of spc-2611201455051897 add no run-state field (its plan says a lane that finds it needs one stops and reports), spc-2611141617199772 raises nothing, the specs for itd-2611141610192096 and itd-2611150636498012 raise nothing, and the spec for the drives across machines raises the drain state's version, which is a different number in a different file. If a lane of another spec does raise the run state first, it takes 32 and this step takes 33; the rule is the number free on the default branch when the step is cut, and the lane says in its pull request which it took. The version before it is its strict subset, read as a run that has re-armed nothing and whose landings carry no `armed_at`, and written back at the new version by its next mutation. A file of an earlier version that carries any of the three fields is refused, as the package does for every field it added.

### The hand-back names the check and the commands (criterion 1)

Past the bound, `droppedRefusal` refuses as it does today, with three changes to what it says:

- `mergeGroupRunsFilter` keeps each run's `id`. Where a failed check of the last merge group is a workflow run in that listing, the remedy names `gh run rerun <id> --failed`. The id must be all digits before it is put in a command.
- The remedy's order is the check, the re-run command, the arming command, then `abcd drain --drive` for a drive's reader or `abcd implement step` for a host session's.
- The reason says how many times the loop armed it again at this head, so a person knows a re-arm was already tried.

Where the forge names no failed run, the remedy says so and gives the arming command alone. A check the forge refuses to re-run is out of the intent's scope.

The lane is not discarded. It stays parked, in the state `dropped`, and the watch goes on reading it. Once a person has re-run the check and armed it, the next move reads it as armed.

### The drive says a parked lane's line (criterion 1)

`terminal.sayMove` gains two notes of a move's parked lanes (`DrainResult.Parked`), and no other: the line of an act the watch made on a lane (`watchParked` returns the record's line after an arming made again, a queuing or a toggle), and the report of a lane read `dropped`. Each is said once when it changes, kept apart per run as `notedFinish` keeps a finished lane's. A parked lane's ordinary reading (waiting, conflicting, syncing, unread) is not said: its note changes with the queue's every move and is the listing's, not an event. To tell the two apart without reading a sentence, `DrainParked` gains an unexported mark that `finishMerged` (`drain_finish.go`) sets where the watch acted; it is not in the `--json` shape. That is the one line for an arming made again and the one paragraph for a hand-back. It is `terminal.say`, so where the typed event of itd-2611141610192096 is on the default branch it is a `note`, and the hand-back's line sets `Acts`.

### The drive's records stay outside the checkout (criterion 2's premise; decision 2)

`DrainOptions` gains `RecordsOutside`, set by the drive's front door where it builds its drain options (`internal/surface/cli/drain_drive.go`). With it set, `routeHandBack` makes neither write in the checkout. It writes one note per hand-back and routes the hand-back `home`.

- **The store.** `~/.abcd.noindex/handbacks/<root-sha>/<issue>.json`, through `abcdhome.Path`, keyed on the root commit as the worktree store is. The directory is the account's alone (mode 0700, files 0600), and a file is written whole, by rename. A note carries its own version, the issue, the hand-back's kind, reason and question, whether it came from a lane or the judgement, the blob of the issue's record the judgement read (`judgedBlob`), the commit of origin it planned from and the time.
- **The route.** `Wrote` says "a note in the account's abcd folder; nothing in this checkout". `Home` names the way in: `abcd capture promote <iss>` for a user moment; for a trust rule, the next `abcd drain` a person runs outside a drive.
- **A note is read as untrusted.** The store is in the account's home, where any process of the account can write, and a note's fields end in a tracked record. So the reader takes a note only where the store's directories are real directories of this account (`fsutil.EnsureRealDirAll`, as the drive's log does), the file is a regular file within a fixed size, its name is its issue's id, the id has the shape of an issue id, and the kind is one of the two the drive writes. The reason and the question pass the same masking and bound a hand-back's do today before either is written anywhere. A note that fails any of these is left where it is and named on stderr; nothing is written for it.
- **Taking them in.** A move of `abcd drain` made without `RecordsOutside`, which is a person's own or their host session's, reads the store before it plans. For each note whose issue this checkout holds as origin's default branch does, at the blob the note names, it makes the write `routeHandBack` makes today (the promotion, or the marker with the note's question), names it among the move's routes, and removes the note. A note whose record this checkout does not hold as origin does is kept. `abcd capture promote <iss>` typed by hand is unchanged and needs nothing from the note.
- **Nothing to clear.** Every move that plans, a drive's included, removes a note whose issue is no longer open on origin's default branch, whose record's blob there is no longer the one judged, or which origin already shows promoted or marked. The move says so in one line.
- **What a drive no longer does.** It never calls `capture.Promote` or `capture.MarkDecisionNeeded`. A test holds that: a drive's whole run over a fixture ledger leaves `git status --porcelain` in the checkout as it found it.

Drafts and back-links an earlier drive left uncommitted in a checkout stay there. They are the person's to commit or drop, and until then they block a fast-forward only where an incoming commit changes the same path, which the drive says.

### The fast-forward: what must hold, and what it runs (criterion 2; decision 3)

A new file `checkoutff.go` holds the whole of it: one function that judges, one that acts, and the list of git argument vectors both may use. The loop calls it at two places (below). It returns one of three results: nothing to do, moved (from, to, the count of commits), or declined (a kind, a sentence, and up to five repository-relative paths).

**The tip** is what origin itself reports for its default branch when the drive asks it (`remoteHeadTip`, the ask `proveCheckoutHooks` makes at the start), and never what `refs/remotes/origin/<default>` names. A tracking ref is a file in the repository that any process of the account can move, a lane's agent included. A fast-forward to it would move the person's checkout onto a commit origin never held, and the hold read again after it (below) would take that commit's hooks as the default branch's. The tip must be a full object name that the repository holds as a commit, and the merge names that object, never a ref. A tip the repository does not hold yet is nothing to do at this boundary: the next fetch brings it.

**It is declined, and nothing is run, when any of these holds:**

| Kind | The case |
|---|---|
| `other-branch`, `detached` | HEAD is not a symbolic ref to the default branch. The default branch's own ref is never moved while it is not checked out here |
| `diverged` | HEAD is not an ancestor of the tip: the checkout's branch holds commits origin's does not |
| `in-progress` | A merge, rebase, cherry-pick, revert or bisect is in progress, the index holds unmerged entries, or the index is locked |
| `staged` | The index differs from HEAD on any path |
| `dirty-path` | A tracked file with unstaged changes is among the paths the range changes, deletes or renames |
| `in-the-way` | For a path the range adds: the path, or any directory above it, stands in the working tree as a file or a symbolic link that HEAD does not track at that exact path; or the path stands as a directory holding any file HEAD does not track. Ignored files count in both: git treats an ignored file as one it may overwrite or remove. An index entry added with intent to add at such a path counts too |
| `hidden-change` | An index entry on a path the range changes is marked assume-unchanged or skip-worktree. Git does not look at such a file before it overwrites it |
| `submodule` | The range changes the gitlink of a submodule that is checked out here |
| `too-large` | The list of the range's paths is past the read's bound, so the drive cannot judge it |
| `lane-in-progress` | A lane of any run in the checkout is in progress: one the drive set aside, one it passed over, or another session's. A lane parked on its pull request does not count. It is said and stored like every other kind, naming the run. The function is called only where the drive has no lane of its own in hand, so a lane found in progress there is never the one the drive is stepping, and it may stand for hours |

The kinds are a fixed list, since the view by login publishes the kind as one word (below). A checkout level with the tip, or ahead of it, is nothing to do and says nothing.

**The act** is one command: `git merge --ff-only --no-overwrite-ignore --no-autostash <sha>`, with `core.hooksPath` set to the null device, `merge.autoStash=false`, `submodule.recurse=false` and an empty `branch.<default>.mergeOptions` for that command alone. The two flags are on the command line because a person's `branch.<default>.mergeOptions` is read as arguments, which a `-c` setting does not outrank: one that held `--autostash` would stash and re-apply the person's work. It goes through the gitutil runner that asks the drive's hold first, so the hold is compared immediately before it; at the start that is the reading the start has just made (below).

Git is the final judge of every case it judges, and `--no-overwrite-ignore` makes an ignored file in the way one of them: without it git overwrites the file and says nothing, and a file made between the drive's reading and the act would be lost. If git refuses, for a file that became dirty, an ignored file that appeared or a commit a person made in that gap, the result is declined with the kind `git-refused` and git's words, bounded and redacted. A fast-forward merge that git refuses changes nothing. Git does not look at a file marked assume-unchanged or skip-worktree, so for that one kind the drive's own reading is the only check, and a mark set in the gap is not caught; the page says so.

A fast-forward that moves writes what any merge writes beside the files: the branch's reflog and `ORIG_HEAD`.

**What it never runs.** The file's argument vectors are one table, and a test reads the table: no `reset`, `checkout`, `restore`, `stash`, `clean`, `rebase`, `pull`, `update-ref`, `branch`, `read-tree`, and no `--force`, `-f` or `--autostash`. No file is moved aside. A dirty file that is byte for byte what origin holds is still a dirty file, and the fast-forward is declined (F-19). The drive no longer writes such files (decision 2), so the ones that remain are a person's.

**What the lines say.** Moved: "fast-forwarded this checkout to `<sha>` (`<n>` commits)". Declined: "this checkout is `<n>` commits behind origin/`<default>` and was not fast-forwarded: `<sentence>`", said once when the reason first stands and again only when the reason changes. A declined fast-forward never ends the drive and never holds a lane.

### At the start (criterion 2 as widened)

Each try of `startHold` in `terminal.run` takes these in order:

1. It reads what the drive holds (`readRemoteIdentity`), as today.
2. It asks origin for its default branch's tip, once, through the run's shared outage: a lost network is the start's existing wait. Today that ask is made only where the checkout has hooks in its tree; it is now made wherever the repository has an origin.
3. It fetches origin's default branch where the repository does not hold that tip.
4. It calls the fast-forward with that tip. The start has registered no check with gitutil yet, so the function compares the reading of 1 itself immediately before the merge (`heldBeforeGit`), and a difference refuses the start.
5. Where the checkout moved, it reads what the drive holds again. As at a boundary (below), the two readings may differ only in what the range changed.
6. It proves the checkout's hooks against the same tip (`proveCheckoutHooks`, given the tip and making no ask of its own). One ask serves the fast-forward and the proof: with two, a pull request merged between them would leave the checkout behind the second answer and refuse a start that had just caught up.

The fetch of 3 is iss-2611251741261124 (a drive's start refuses on a tip the repository does not hold yet), which a session is fixing in a worktree of its own as this spec is written. Step 4 is cut after that change is on the default branch and reuses its fetch; if the issue is still open when step 4 is cut, step 4 resolves it in the same change.

Two refusals change. A repository that does not hold origin's tip no longer refuses the start, since the fetch brought it. A checkout behind a tip with other hooks (`behindTip`) is fast-forwarded where that is safe, and the start then proves its hooks against the tip as it does today. Where the fast-forward was declined, `startHooksRefusal` keeps its refusal and its remedy names what blocked it, a lane in progress included, before `git pull --ff-only`.

A drive that goes on from an interrupt may have a lane in progress, read from the runs' state on disk. The start then makes no fast-forward, and says so in the one line. Step 1 of spc-2611141617199772 adds `takeEarlier` before the first move; the fast-forward is before it.

The person's yes comes before all of this (`driveConsent`, in the front door), so a start's fast-forward can change a hook or a setting after the yes, as every boundary's can under decision 3. The line the start says for a fast-forward that moved names the count of commits, and the third note under Open Questions puts the order to the product thinker.

### Between lanes, and the hold read again (criterion 2; decision 3)

At the top of a pass, after `heldBeforeGit` has passed and where `boundaryDue` is set and nothing is in hand, the drive asks origin for its default branch's tip and calls the same function with the answer. It does so whether or not `AtBoundary` is set: a source build sets none, and its checkout is fast-forwarded all the same. The ask is one `ls-remote` at a boundary, made through the run's shared outage. A lost network, or a tip the repository does not hold yet, makes no fast-forward and holds nothing: the pass goes on and the next boundary asks again. No fetch is added here, since every move planned from origin fetches the default branch already.

After a fast-forward that moved the checkout, the drive reads its hold again, as it does at its start (`readRemoteIdentity`, then `proveCheckoutHooks` against the tip it fast-forwarded to, with no second ask of origin), and swaps it in. A tip origin has moved to since is the next boundary's: proving against a fresh answer would end the drive whenever a pull request merged in the gap, its own included. `Options.remote` and the check registered with `gitutil.SetBeforeHookedGitAt` both read the hold through the terminal, not through a value captured at the start. A read that waits on origin waits as the start's does. A read that refuses ends the drive with the start's refusal.

The new hold may differ from the old only in what the fast-forwarded range changed. The drive compares the two readings (`remoteIdentity.changed`) and checks each name that differs against the range's paths, the range being the old HEAD to the tip origin reported. A difference anywhere else, a setting in git's own configuration or a hook outside the tree, ends the drive with today's refusal (`heldBeforeGitRefusal`). So decision 3 is what is built and no more: the guarantee becomes that nothing the drive's git runs changed since the last boundary, except by a commit of the default branch. Two properties are tested for it. A held value changed before the boundary ends the drive at `heldBeforeGit`, and no fast-forward is made. No agent runs between that comparison and the new reading.

The order with a new release is: fast-forward, then `AtBoundary`. A drive that starts itself again for a release reads its hold at its own start.

### Where a declined fast-forward shows (criterion 2; question 5 as settled)

- **The event line.** Above: once per reason, through `terminal.say`. Where the typed event of itd-2611141610192096 is on the default branch, the declined line sets `Acts` and is added to that spec's list of lines a person may have to act on.
- **`abcd implement status`.** `DriveState` (`drivestate.go`, step 4 of spc-2611141617199772) gains `Checkout`: the count of commits behind, the tip, the kind, the sentence, the paths and since when. The drive sets it when a fast-forward is declined and clears it when one succeeds or the checkout is level. `abcd implement status` (`internal/surface/cli/build.go`) prints it as a line of its own under the state line, "checkout: `<n>` behind origin/`<default>` since `<time>`, not fast-forwarded: `<sentence>`", and `--json` carries the field. The function that composes the state line does not read it, and a test holds the state line unchanged with the field set. A new field is a new version of the state file, by the rule step 4 of spc-2611141617199772 sets for it; the specs for itd-2611141507299828 and itd-2611150636498012 each raise the same version for a field of their own, so each takes the number free on the default branch when it is cut. The reader (`ReadDriveState` in `drivestate_read.go`, step 5 of spc-2611141617199772) takes the new version and reads a file of the one before as a drive with no block.
- **The view by login.** Not built here. The view of a person's drives across machines is an intent of its own (the ruling of 25/11 on the planning note's third question), and it publishes each drive's stored state. `Checkout` is a field of that value, so the view carries it: that intent's spec maps the count and the kind to one published field and a kind it does not know to `other`, so a kind added here later needs no change there. The kind and the count are kept apart from the sentence and the paths so that a published line can say "behind, blocked by a dirty path" without naming a file of the person's on a branch anyone with access to the repository can read.
- **The board** does not show it. The ruling names the event line, the status command and the view by login.

## How the Acceptance Criteria are met

The criteria are numbered in the order the intent lists them.

1. A removed pull request is armed again fewer than three times at one head, and the drive says so on one line: `rearmDropped`, its three landing fields, and the parked lane's line in `sayMove` (steps 1 and 2). Past the bound the lane is handed back naming the check, `gh run rerun <id> --failed` and the arming command (step 1). Shown wrong by a fourth arming at one head, which a test counts on a fixture forge, and by an arming made over a person's removal or a person's withdrawal, which the tests of step 1 hold case by case, the removal from before the loop's own arming among them.
2. The checkout is fast-forwarded at the drive's start and when a lane ends, where no dirty path is one an incoming commit changes and no lane is in progress (steps 4 and 5), to the tip origin itself reports and never to a ref in the repository, over a commit that changes a hook or a setting the drive holds, after which the drive reads its hold again (step 5). Where a dirty path is in the way it is not fast-forwarded and the drive says what blocks it: one event line (steps 4 and 5), a line in `abcd implement status` and a field the view by login carries (step 6). The records the drive writes are outside the checkout (step 3). Shown wrong by any test of step 4 in which a byte of the person's working tree, the index or a branch they moved differs after the call.

## Open Questions

None blocks a step. Three notes are for the product thinker to see.

- **The start's fast-forward comes after the yes.** The start screen asks once, and the fast-forward at the start runs after the answer. A commit it takes in can change a hook or a setting the drive then holds, which is what decision 3 allows at every boundary, and the widened criterion puts the start among them. The plan keeps that order and says the fast-forward on one line. If the product thinker wants the yes to cover exactly what the drive starts with, the fast-forward moves before the start screen, which is a change to the front door and to the screen's lines.

- **How records are taken in.** Decision 2 keeps the drive's records in the account's own abcd folder until a person takes them in, and the intent adds no command. This plan takes them in through two commands that exist: `abcd capture promote <iss>` for one, and a person's own `abcd drain` for every note the checkout can hold. A person who only ever runs drives takes none in. Their hand-backs still reach origin as tombstones and still show in every drain's summary, and the drafts are made when they promote an issue. If the product thinker wants a drive's notes taken in without either command, that is a new surface and a question for them.
- **Other sessions in the same checkout.** A fast-forward changes files under any host session working in the drive's checkout. Its uncommitted edits are safe, because a dirty path the range changes declines the fast-forward. A preflight running there loses its receipt, since the receipt is minted only for a tree that matched HEAD at both ends; the cost is one run's time and no wrong receipt. The intent's conditions name no other session, so no condition is added for one.

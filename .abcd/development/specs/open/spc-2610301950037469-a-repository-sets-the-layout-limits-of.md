# A repository sets the layout limits of abcd's questions

## Summary

Delivers itd-2610301914350541, which builds on itd-2610230756259215. Three keys in a repository's `.abcd/config.json`, `question.rows`, `question.label_words`, and `question.description_sentences`, set the rows a question may take, the words a label may run to, and the sentences a description may say. One resolver in `internal/core/layered` reads them over `question.Default`, with inclusive bounds stated once in `internal/core/question`, and returns one of three states: The defaults, the limits in force with the file that set them, or a refusal naming the key, the value, the bounds, and the file. Every reader of a limit takes it from that resolver: The question gate in the hook, the `abcd guard question` verb, the plain-Terminal interviews' checks, the install's README fit, and the GRILL domain the rules loader generates, which gains a `LoadWith` form the two front doors feed. A value outside its bounds, of the wrong type, under a key the namespace does not claim, or set in the machine's file is refused and nothing falls through: The hook refuses every question carrying abcd's header, the verb exits 2 with `refused`, and the asking rules are rendered at the defaults with the refusal written in. A file the resolver cannot read fails open and loud, in the gate's own `NOT CHECKED` form. The shipped page blocks keep stating abcd's defaults and point the writer at the check's new `limits` field.

This spec runs after spc-2610301917245442's verb exists. It extends that verb's `abcd/question-check/v1` JSON with three additive fields, `limits`, `limits_source`, and `refused`, and adds one more cause of exit 2, a refused value, beside the parent's unreadable input and unread store; the parent spec's approach 5 and its step 1 are edited to list them in the change that lands step 2 here, so the verb's contract stays stated once (the intent's decision 15). Which parent steps each step here waits for is said under each step.

### Approach

1. **The bounds, stated once.** `internal/core/question/limits.go` gains `Bound{Key string; Floor, Ceiling int}` and `Bounds`, three values beside `Default`: `question.rows` 24 to 60, `question.label_words` 4 to 8, and `question.description_sentences` 2 to 4 (the intent's decision 3). `Bound.String()` renders "24 to 60", `Bound.Admits(n int) bool` judges inclusively, and `Bounded(l Limits, rows, labelWords, sentences int) Limits` returns `l` with the three fields replaced and every other field unchanged. `Floors(l)` and `Ceilings(l)` are test helpers in the same file. Nothing else in the tree writes a bound: The resolver's refusal, the loader's note, and the generated page sentence all render `Bounds`.
2. **The resolver.** `layered.QuestionLimits(r Roots) (Value[question.Limits], error)` in a new `internal/core/layered/question.go`, beside `InterviewList`. It loads `Config`, claims the `question` namespace with the three keys, so `question.options`, `question.columns`, `question.tabs`, or a misspelt key is refused by `Claim` naming the key and the file. It then looks each key up; a key found in the machine layer is refused in `InterviewList`'s form inverted, naming the repository's `.abcd/config.json` as the one place the limits are set (decision 5). Each repository value is decoded as an `int` through `Decode`, so a fraction, a string, or `null` is refused, and judged by its `Bound`; a value outside it is a `*layered.KeyRefusedError{Key, Value, Bounds, Origin}`, whose `Error()` is `Get`'s form: `.abcd/config.json (repo layer): question.rows is 100: outside 24 to 60`. No key set returns `Default` with `Layer` `Bundled` and `Origin` `bundled`; any key set returns `Bounded(Default, ...)` with `Layer` `Repo` and `Origin` `.abcd/config.json`, the path `limits_source` reports. The root is the one `RootsFor` resolves (the rules root), so the injected domain and the hook's check read one file; a front door that has already resolved that root through `rulesRoot` builds the same `Roots` from `HomeRoots` and that root, so git is asked once.
3. **An unreadable layer is told apart from a refused value.** `LoadContext` wraps every fault of a layer it could not read or parse, the repository read (lines 298 to 304), the machine read (lines 313 to 319), and the unresolved home (lines 283 to 285), in `*layered.UnreadError{Origin string; Err error}`, whose `Error()` is the text today, so no caller's message changes. Everything after a successful load, `Claim`'s unknown key, the machine-layer refusal, and `KeyRefusedError`, is a refusal. A caller tells the two apart with `errors.As` and never by reading words (decision 8). The hook, the verb, and the binary's composers take two paths from them: A refusal is fail-closed (the question is not asked), and an unread layer is fail-open and loud (the question runs at the defaults, and one line names the file).
4. **The check reports and the hook reads.** `questionState` (the parent's one store reader) resolves the limits through approach 2 and puts the outcome on `question.State`: `Limits`, `LimitsSource`, `Refused *LimitsRefusal{Key, Value, Bounds, File}`, or an `unread` entry naming the file and the three rules the keys decide. `Decide` keeps the parent's order, away first, then the header test, then the limits: A call with no header in abcd's grammar is `admit-unchecked` whatever the configuration says; a call in the grammar with `Refused` set is `refuse` with `findings` empty and `Verdict.Refused` carrying the refusal; one with the layer unread is `unchecked`, `partial` with that `unread` entry. The hook denies a `refuse` with `Refused` by one head line and the refusal line, naming the key, the value, the bounds, and the file and no asking rule, then the parent's pointer line; for `unchecked` it writes `questionFailOpen` naming the file. Every admitted question is checked with `State.Limits`, so a tab of 30 rows under `question.rows` 40 gets no rows note and one of 41 gets the note naming 40. The limits reach `ChipRole` and the parent's `IsAbcds` the same way. The mode store keeps its own root (`mode.Root`, git's toplevel); the limits follow the rules root, as decision 6 says.
5. **The verb's JSON.** `abcd/question-check/v1` gains `limits` (`rows`, `label_words`, `description_sentences`), `limits_source` (`bundled` or `.abcd/config.json`), and `refused` (`key`, `value`, `bounds`, `file`) on the refusal path; `rows_limit` stays and equals `limits.rows`. Exit 2 for a refused value, with no `ready`, and exit 2 for an unread layer, the parent's partial result naming the file. The text render prints one line after the outcome: `limits: 40 rows, 5 label words, 2 description sentences (.abcd/config.json)`, or the refusal line. The parent spec's approach 5 and step 1 are edited in the same change to list the three fields and the new exit-2 cause, as decision 15 requires.
6. **The binary's own composers.** `Written` gains `Limits question.Limits` and `LimitsNote question.LimitsNote`, set by its front door from the resolver; `checkAsk` measures with `w.Limits`, and the brief renders `AskingRulesFrom(w.Limits, w.LimitsNote)` (approach 7). `ahoy install` resolves once before its first question and threads the limits to `fitsLimits` and `fitLines`, which lose their `Default` reads. In both, a refusal is the run's refusal before any question, exit 2 naming the key, the value, the bounds, and the file, and an unread layer prints the gate's fail-open line and goes on at the defaults. The composers that only build fixed questions (setup, connect guide, source, sessions) read `Default.LaterLabels`, `Default.NotApplicable`, and the prefixes, which stay the binary's (decision 2), and are held at the floors by tests (approach 10). A tree test lists the call sites still allowed to pass `question.Default` to `CheckLimits`, `AskingRules`, `AskingRulesFrom`, `ChipRole`, `IsAbcds`, `Rows`, or the asking-sync renderers, or to read `Default.Rows`, `Default.LabelWords`, or `Default.MeaningSentences`: The resolver, `cmd/asking-sync/main.go`, the rules package's one bundled-layer statement (the init-time GRILL in `grill.go`, which `rules.Load`'s one-line body delegates through), and tests.
7. **The asking rules carry the source.** `question.LimitsNote{SetBy string; Refused string}` and `AskingRulesFrom(l Limits, n LimitsNote) []string`; `AskingRules(l)` becomes `AskingRulesFrom(l, LimitsNote{})` and renders byte for byte as today. With `SetBy` set, the layout rule ends with one sentence naming `.abcd/config.json` as having set the rows, label words, and description sentences it states. With `Refused` set, it says that the figures stated are abcd's defaults, which key is refused and why, and that abcd's question check refuses every abcd question until the file is fixed. A new sentence in the same rule, rendered in every repository from `Bounds`, says the three keys a repository may set and their bounds. The parent's step 4 revises the same rules; this step lands after it, so the two never edit one sentence at once.
8. **The loader takes the limits as an argument.** `rules.LoadWith(repoRoot string, l question.Limits, n question.LimitsNote) (RuleSet, error)` regenerates `rs.Domains[GrillDomain]` on the base, after `withRepoShellDomain` and before any layer lands, from `AskingRulesFrom(l, n)`; a non-empty `n.Refused` is appended to `rs.notes` as one line, so `abcd rules` prints it on stderr and the hook's diagnostic carries it. `rules.Load(repoRoot)` is `LoadWith(repoRoot, question.Default, question.LimitsNote{})`, the form every test and every caller outside a repository keeps. The domain's `Source` stays `bundled`, because no override layer named it, and `rulesFrom` is left unset: Setting a figure is not replacing the rules (decision 11). A repository that overrides GRILL's rules through `.abcd/rules.json` still wins, since the layers land after the regeneration. The changed text changes `Signature`, so the dedup ledger injects the domain again on the next prompt that recalls GRILL, with no new mechanism.
9. **The two front doors.** The prompt hook (cli.go line 1865) and `abcd rules` (line 2646) resolve the limits before loading the rules: In force, `LoadWith(root, l, LimitsNote{SetBy: origin})` with `SetBy` empty for `bundled`; refused, `LoadWith(root, question.Default, LimitsNote{Refused: err.Error()})`; unread, `LoadWith(root, question.Default, LimitsNote{})` with one diagnostic line on stderr naming the file in the resolver's words. So every other domain loads as before, and a configuration fault never injects nothing.
10. **The pages, the brief, and the labs.** `render` and `renderDrafter` keep rendering from `question.Default` (decision 12) and each gains one sentence, composed in `question` from `Bounds`: These figures are abcd's defaults; a repository sets rows, label words, and description sentences in `.abcd/config.json` under `question`, within the bounds named; `abcd guard question` reports the values in force in its `limits` field, and the writer takes them from there and never from the configuration file. The writer's hand-written part says that a hand count, made only where the host gives it no shell, is made at abcd's defaults and that the repository's values were not read, and its output says so (decision 10). The configuration chapter gains `### The question keys` after the interview key, with a JSON block naming the three keys, their defaults, their bounds, and the repository layer alone; the guard chapter's `question` row and "What a person gets back" name the exit 2 for a refused value, and its question gate section says the limits are the resolver's; `commands/guard.md`'s `question` section says where the limits are set and that the check reports them.

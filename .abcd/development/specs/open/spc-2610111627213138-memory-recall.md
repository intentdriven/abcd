# memory-recall

## Summary

This spec delivers the memory-recall bundle: memory notes
([itd-2610091918433290](../../intents/planned/itd-2610091918433290-an-agent-working-in-an-abcd-managed.md))
and memory pages recalled at the right moment
([itd-39](../../intents/planned/itd-39-scope-aware-memory-retrieval.md)).
An agent keeps short notes with `/abcd:memory`, and the loader that already
brings in the project's rules brings a note, and any longer memory page that
matches, back into the session when a prompt matches their words. Notes start
on the person's machine and reach the project's record only when a person
promotes them in a review.

The approach, in plain words:

- **A `memory.json` beside each `rules.json`.** The machine's
  `~/.abcd.noindex/memory.json` holds personal notes and the project's
  `.abcd/memory.json` holds promoted ones (the facilitator's ruling of
  2026-10-11). The loader reads both with the trust checks it already applies
  to the two `rules.json` layers. Agents write `memory.json`; people curate
  `rules.json`, so no agent's note ever edits the file that holds reviewed
  conventions (one-writer-per-file).
- **Write first, review later.** An agent writes any note without asking. Each
  note is stamped with who wrote it, when and in which session, and the
  redactor and the private-names banlist refuse a note that would hold a
  secret, a private name or a network address (adr-2610091918443997).
- **One recall for notes and pages.** The prompt hook recall-matches the
  prompt against rules, notes and pages in one pass. Notes and pages come back
  together in one block after the rules, deduplicated per session the way rules
  are.
- **Recall shrinks as the session fills.** One set of context brackets decides
  whether matched items come back in full, as one line each, or not at all,
  and a relevance ranking chooses which ones survive when only some fit. The
  loader has no brackets today (see Design, "Context brackets"), so this
  bundle builds them once, in the loader, for every payload that uses them.
- **Promotion is a person's act.** The binary refuses a promotion an agent
  attempts, the way it refuses an agent's flip of a source-ledger line under
  adr-41, and a promotion lands in the project's committed record through the
  same review as any other change.

How each acceptance criterion is met. N1 to N10 are the notes intent's, in the
order it lists them; P1 to P5 are itd-39's.

| Criterion | Met by |
|---|---|

Where the two intents' criteria overlap (the brackets in N10 and P2; the host's

Parts of itd-39's body predate the shipped loader and the verb split, and this
spec reads them as follows without editing the intent: its

rejection of a personal `rules.json` is moot, since the machine layer
`~/.abcd.noindex/rules.json` has since shipped.

## Design

### The `memory.json` file and its two layers

One schema serves both layers. The machine layer is
`~/.abcd.noindex/memory.json`; the repository layer is `<repo>/.abcd/memory.json`.

```json
{
  "schema_version": 1,
  "last_review": "2026-10-11T09:30:00Z",
  "notes": [
    {
      "id": "mem-2610111200001234",
      "title": "The tests need the race flag",
      "body": "Run go test -race ./internal/... before saying the tests pass; the plain run misses the data race in the hook tests.",
      "recall": ["test", "tests", "race"],
      "root": "<the repository's root commit, full object name>",
      "origin": "agent",
      "written_by": "Claude:claude-opus-5-5",
      "written_at": "2026-10-11T12:00:00Z",
      "session": "<the host's session id>",
      "reviewed_at": null
    }
  ]
}
```

- `id` is minted through the shared record-id seam (`recordid.Minter`,
  adr-45) with the family `mem`, so two sessions writing at once never collide
  and no coordination is needed.
- `title` is one line of at most 120 characters, `body` at most 2 KiB, and
  `recall` one to twelve words or short phrases, matched by the loader's own
  term rule (word boundary, stems, multi-word phrases). The figures are this
  spec's, set in one place, and a write past them is refused naming the limit.
- `root` binds a personal note to the repository it was written in, so a note
  about this project's tests is not recalled in another project. A note written
  with `--everywhere` carries `"root": null` and is recalled in every
  repository on the machine (open question 8). The repository layer carries no
  `root`: the file is already the project's.
- `origin` is `agent` or `host-memory-move` (the manual move, below).
- `written_by` takes the shape of the `Assisted-by:` trailer
  (`<Vendor>:<model-version>`), so who wrote a note reads the same way as who
  assisted a commit.
- `last_review` and `reviewed_at` are the review's markers: a note whose
  `reviewed_at` is null, or older than its last edit, is one the next review
  shows.
- A promoted note in the repository layer also carries `promoted_by`,
  `promoted_at` and `agreed_by` (Review and promotion, below).

Reading follows the `rules.json` layers exactly. The machine file is read only
through `fsutil.ReadHomeDeclaration`: a regular file this account owns that no
one else can write, within 256 KiB, never behind a symlinked
`~/.abcd.noindex`; a file failing those checks or failing to parse is a loud
error naming the file in tilde form, and the hook then recalls no notes from
it, while rules still inject. Absent, it costs nothing and nothing is created.
The repository file is read through the repository layer's guarded read, from
the root the rules loader resolved (a refused foreign-uid root reads no
`.abcd/memory.json` above the working directory, as with `rules.json`). The
kill switch in either `rules.json` silences note and page recall as well as
rules: it is the loader's switch, and recall is the loader's.

Writing touches the machine layer only (step 1), except promotion (step 7).
A write takes an exclusive `flock(2)` on the home scope's directory
descriptor, re-reads the file under the lock, applies the change, and writes
through `fsutil.WriteFileAtomicInRoot` with mode 0600, so two agents writing at
once both land. The machine file is never created by a read and is created
0600 by the first write.

### The write gate: redaction, banlist and stamps

Every note write, to either layer, passes one gate in `internal/core/memnote`
before anything is written:

1. **The shared scanner** (`internal/adapter/scanner`), the one canonical
   detector capture, history and the memory-page writer already route through,
   reached through the memory-page writer's own redactor, exported for it.
   The gate refuses on a degraded scanner, then scans the note's title, body
   and each recall word, and refuses on any span the memory-page writer would
   have to rewrite: any hard-fail secret, any identity or network span whatever
   its severity (`scanner.BlockingResidual`), and the literal home-directory
   backstop. Unlike the page writer, it never redacts and writes: the refusal
   names the kind of span and the field, never the span, and the agent
   rewrites the note in its own words, since a lesson with a span cut out of it
   may say something wrong.
2. **The private-names banlist**, through `banlist.MatchPrivate`, which the
   implement loop already uses. A store that cannot be read is treated as a
   match, as that function's contract requires.
3. **The stamps.** `written_at` comes from the clock, never from the caller.
   `written_by` and `session` come from the caller (step 2's page), are
   shape-checked, and are judged by the gate like any other field.

The gate is the only path into either file. Promotion runs it again against the
repository's own scanner configuration, since the repository may declare
patterns the machine does not.

### One recall for notes and pages

A new package, `internal/core/recall`, holds what notes and pages share:
candidate items, matching, ranking, brackets and rendering. The prompt router
calls it once per prompt, after `rules.Inject`, with the items both note layers
and both page scopes yield. It returns one block, headed `## MEMORY`, appended
after the rules block in the same hook output.

- **Matching** is the loader's. `internal/core/rules` exports its prompt index
  and term rule (`indexPrompt`, `termHit`, the stemmer) as one small function,
  so a note's recall word and a rule domain's recall word hit on exactly the
  same prompts. An item is a candidate when any of its recall words hits; the
  ranking orders candidates and never adds one.
- **Items.** A note yields its title, body and recall words. A page yields its
  filename, its `index.md` summary line as its title, its body, and its
  `recall:` frontmatter list, which the memory-page schema already carries
  (`internal/core/memory/schema.go`). A page without a `recall:` list is never
  a candidate, so pages already written are silent until a recall list is
  added.
- **Scopes.** Pages are read from the checkout's `.abcd/memory/` and, when it
  exists, the machine's `~/.abcd.noindex/memory/` (read only, through
  `fsutil.OpenHomeScope`; nothing in this bundle writes it). When a recall word
  hits a page in both scopes with the same `<type>_<domain>_<slug>` name, the
  workspace page is the candidate and the machine page is suppressed (P4).
  Notes follow the same rule: a promoted note and a personal note with the same
  id cannot both exist, since promotion moves the note.
- **Dedup.** The session ledger gains a second map, `recalled`, keyed by item
  (`mem-…` or `page:<filename>`) with a signature of its rendered text. It is
  separate from the rules ledger because `rules.Inject` prunes any ledger name
  that is not an active domain, which would forget every item each turn. The
  same resets apply: `SessionStart` and `PreCompact` clear both maps, and the
  fixed backstop clears both on the same prompt (P3).
- **Budget.** Rules and memory share the loader's 64 KiB per-turn injection
  budget. Rules render first and memory takes what remains; an item that does
  not fit is not recorded in the ledger, so it is retried next turn, as a
  truncated rule domain is today.
- **The host's memory files** are never among the paths the recall opens. The
  recall reads exactly four places: the two `memory.json` layers and the two
  page scopes. A test runs the recall through a filesystem seam that records
  every open, with a home directory holding a host memory directory full of
  matching text, and asserts the recorded opens are only those four (P5).

The `--json` envelope of `hook prompt-router` gains a `recalled` list naming
each item injected, beside `injected` for domains, so a reader can tell what
came back and why.

### Ranking

When only some matched items fit, a relevance ranking chooses which ones stay,
as the facilitator ruled. The ranking is BM25 with per-field weights (BM25F),
computed in about a hundred lines of standard-library Go, with no new
dependency.

- **Query terms** are the prompt's stemmed tokens, from the same prompt index
  the matcher builds.
- **Fields and weights.** A term found in an item's recall words counts three
  times, in its title twice, and in its body once. The weighted frequencies are
  summed per term before saturation, as BM25F prescribes.
- **Score.** For each query term t present in the item,
  `idf(t) · tf_w / (tf_w + k1 · (1 − b + b · len / avg_len))`, summed over the
  terms, with `k1 = 1.2`, `b = 0.75`, and
  `idf(t) = ln(1 + (N − n_t + 0.5) / (n_t + 0.5))` over every note and page in
  reach (N items, n_t of them holding t). A word every item shares counts for
  little; a rare word that matches counts for a lot.
- **Ties** break, in order, on the narrower scope (repository before machine),
  then the more recent `written_at` (or page modification), then the id, so the
  order is the same on every machine and every run.
- **Explainable.** `abcd memory recall "<prompt>" --explain` prints, for each
  candidate, its score, each matched term with its field and its contribution,
  the bracket in force, and whether it came back in full, as one line, or not
  at all. Nothing about the choice is hidden.

Prior art: BM25 is the probabilistic relevance framework's ranking function
(Robertson and Zaragoza, "The Probabilistic Relevance Framework: BM25 and
Beyond", 2009), and BM25F its multi-field extension (Robertson, Zaragoza and
Taylor, "Simple BM25 Extension to Multiple Weighted Fields", 2004). It is the
default similarity in Lucene since version 6 and the ranking SQLite's FTS5
`bm25()` exposes, with per-column weights. The fit challenge the prefer-sota
principle asks for set aside the two stronger-sounding options: dense
embeddings need a model or a network call inside a hook that runs on every
prompt, against the host-delegated and minimal-dependency stances and the
hook's fail-closed, never-blocking contract; a learned re-ranker needs
training data abcd does not have. A raw count of matching words, the order
`library ask` uses today, is what the ruling rejected: it lets a common word
outrank a rare, telling one. `library ask` keeps its order; changing it is not
in this bundle.

### Context brackets

The facilitator ruled that memory recall shares the rules loader's context
brackets (itd-3) and has no thresholds of its own. The shipped loader has no
brackets: it has a fixed per-turn byte budget, and nothing in it reads how full
the session is. The brackets exist only in itd-39's design (the brief's
`05-internals/07-memory.md` § 9). So this bundle builds one bracket table in
`internal/core/rules`, beside the byte budget, and recall reads it from there,
so a later payload cannot grow thresholds of its own. Whether rules injection
itself is gated by the table is open question 1.

The table starts from itd-39's figures, read as the fraction of the context
window still free:

| Bracket | Free | Notes and pages |
|---|---|---|
| Fresh | 70% or more | Every candidate in full, in ranked order, within the budget. |
| Moderate | 40% to 70% | The top-ranked candidates in full within 8 KiB, the rest as one line each. |
| Depleted | below 40%, down to the floor | One line each (a note's title and id, a page's index line), the top-ranked lines within 2 KiB. |
| Exhausted | below the floor | Nothing. |

The 8 KiB and 2 KiB figures are this spec's starting points, set beside the
thresholds in one place. The floor that separates one line from nothing is not
recorded anywhere and is open question 3. How the hook learns how full the
session is, and what it does when it cannot tell, is open question 2: the
prompt hook's payload carries no measure of the context window today.

### The `/abcd:memory` agents' command

`/abcd:memory` is an agents' page under the verb split's rules
(itd-2610090831227812): `block: agents`, `user-invocable: false`, kept in the
flat `commands/` directory, named on an agents-block line of
`abcd --help --agent`, and held there by `TestCommandPagesMatchTheMenu`. The
binary verb is `abcd memory`, placed in `groupAgents` naming
`commands/memory.md`. Every sub-verb writes only through the core in
`internal/core/memnote`; the page carries the judgement half.

| Sub-verb | What it does | Writes |
|---|---|---|
| (bare) | Counts personal notes for this repository and everywhere, promoted notes, notes awaiting review, and the date of the last review; names any layer that could not be read and why. | nothing |
| `add` | Writes one note to the machine layer: `--title`, `--recall` (repeatable), the body on stdin, `--by <Vendor>:<model>`, `--session <id>`, optional `--everywhere` and `--moved-from-host`. Prints the minted id. | the machine layer |
| `list` | Lists notes from both layers with their stamps; `--unreviewed` narrows to those the next review shows. | nothing |
| `remove <mem-id>` | Removes a personal note the agent wrote in error. A promoted note is removed by editing the project's record in a reviewed change, never by this verb. | the machine layer |
| `recall "<prompt>"` | The diagnostic: which notes and pages this prompt would bring back, in which bracket, and why (`--explain`). Open question 9 places it. | nothing |
| `review` | Renders every note since the last review, with its stamps, and applies the person's keep and discard decisions. | the machine layer |
| `promote <mem-id>` | The person's act: moves a note into the project's record. | both layers |

The page tells the agent when to write a note (a lesson it would otherwise
relearn: a flag the tests need, a preference the person stated, a trap in the
tooling), to choose recall words a later prompt would actually use, to keep one
lesson per note, and never to put a secret, a private name or a network address
in one, since the binary refuses it. It tells the agent to pass the host's
session id and its own vendor and model as `--session` and `--by`.

### The manual move from the host's memory files

The person points at a lesson in the host's own memory files, or pastes it.
The agent, at that word and only then, reads the passage the person named with
the host's own tools, and files it with
`abcd memory add --moved-from-host`, the text on stdin. The binary stamps
`origin: host-memory-move` and judges it through the same gate. The binary
takes no path operand on `add`, so it never opens the host's files at all, on
this verb or any other; the page tells the agent never to scan those files for
candidates, and never to edit or delete the original. Removing it there is the
person's choice, in the host. abcd's ruling of 2026-10-05, that abcd never
touches the person's host configuration folder, stands unchanged.

### Review and promotion

**The review** is where trust is earned (adr-2610091918443997). `memory review`
renders every note whose `reviewed_at` is null or stale, for this repository
and for everywhere, oldest first, each with its id, title, body, recall words,
who wrote it, when and in which session. The person decides each note:

- **Keep**: stamps `reviewed_at`; the note stays personal.
- **Discard**: removes the note from the machine layer.
- **Promote**: the person runs `memory promote` for it (below).

At a terminal, `memory review` asks note by note. Off a terminal it renders the
list and applies decisions given as `--keep <id>` and `--discard <id>`
(repeatable), which is how an agent relays the person's answers given through
the host's question tool. When every listed note is decided, `last_review` is
stamped. Where the person runs the review, given that `/abcd:memory` is an
agents' command, is open question 6.

**Promotion** moves one note from the machine layer into the working tree's
`.abcd/memory.json`, stamps `promoted_by` (the checkout's git user name, never
an email, which the gate would refuse) and `promoted_at`, re-runs the gate
against the repository's scanner configuration, and removes the note from the
machine layer. The write is a change to a committed file, so it lands the way
every change to the record lands: in a commit authored by the person, through
the repository's review.

Only a person promotes, enforced twice, as the source ledger's flip is:

- **A guard entry**, `abcd-memory-promote`, at blocker tier in
  `internal/core/guard/defaults/guard.json`, matching `abcd memory promote` in
  every spelling, with known-bad and known-good fixtures. Its `why` says a
  promotion an agent makes writes a false record of who decided; its
  `successor` tells the agent to name the note and why it is ready, and let
  the person run the command. The SHELL rule domain follows from the registry.
- **A terminal check.** `memory promote` refuses off a terminal, naming the
  person's act, so a host without the guard hook still cannot promote through
  an agent's shell.

**Another maintainer's agreement** where the repository has more than two
maintainers. abcd does not record how many maintainers a repository has, and
the forge is the only place that knows. Open question 4 asks where the count
comes from, and open question 5 how the agreement is recorded and checked. The
design either answer slots into: `promote` reads the count; with more than two
maintainers, the promoted note carries an empty `agreed_by` and a record-lint
rule (`memory_promotion_agreed`) refuses a `.abcd/memory.json` holding a note
whose `agreed_by` does not name someone other than `promoted_by`, so the change
cannot land until the agreement is recorded. With two maintainers or fewer, no
agreement is needed and the rule passes.

### Provenance

Every note answers who, when and in which session, in the file, in `list`, in
`review` and in the `--explain` output. `written_by` and `session` are the
writer's stamps; `promoted_by`, `promoted_at` and `agreed_by` are the
promotion's. The stamps are never rewritten after the fact: a kept note keeps
its first author and session, and promotion adds its stamps beside them. The
session id is the host's identifier for the session, never a link to it, so it
carries no session URL into the committed record.

## Decisions

The rulings this spec carries, all of 2026-10-11 and recorded in the intents'
Decisions and adr-2610091918443997:

- Agents capture notes automatically, every note is stamped, and the product
  thinker or the technical facilitator reviews them (product thinker).
- Only a person promotes, in a review; above two maintainers another must agree
  (product thinker).
- Notes and pages are built together and share one recall (product thinker).
- The host's memory files move by hand only, and abcd never reads or writes
  them on its own (product thinker).
- A `memory.json` beside each `rules.json` layer (technical facilitator).
- Recall shares the loader's brackets, with no thresholds of its own
  (technical facilitator).
- A relevance ranking chooses the survivors, with no new dependency unless the
  person signs off (technical facilitator).
- Release placement no longer waits on itd-36 (settled on the record).
- A note never holds a secret, a private name or a live network identifier
  (settled on the record).

Design choices this spec makes inside those rulings, each with its grounds and
each open to the facilitator's veto at review:

- **BM25F with recall words weighted three, title two, body one.** Grounds: the
  prior art above; standard library only; deterministic and explainable.
- **The gate refuses rather than redacts a note.** Grounds: a lesson with a span
  cut out of it may say something wrong, and the agent can always rewrite it.
- **The bracket table lives in `internal/core/rules`.** Grounds: the ruling's
  "share the brackets" read literally, so no payload can grow a second set.
- **Rules and memory share the 64 KiB per-turn budget, rules first.** Grounds:
  the budget is the loader's flood guard, and a second budget would double it.
- **A separate `recalled` ledger.** Grounds: the rules ledger is pruned to
  active domains every turn.
- **Promotion is refused to an agent by a guard entry and a terminal check.**
  Grounds: the precedent of the source ledger's flip (adr-41), the one existing
  person's-act-only write.
- **The figures** (120-character titles, 2 KiB bodies, twelve recall words,
  the 8 KiB and 2 KiB bracket budgets) are starting points, each set in one
  place.

## Open Questions

1. **Do the brackets gate rules too, or only notes and pages?** (technical
   facilitator) The ruling said memory recall shares the rules loader's
   existing brackets, but the shipped loader has none: it has a 64 KiB per-turn
   byte budget and reads nothing about how full the session is. Step 6 builds
   one bracket table in the loader either way.
   - (a) The table gates notes and pages only; rules inject as they do today.
   - (b) The table gates rules too, with the same thresholds: a domain comes
     back as its heading and first rule in the moderate bracket, and so on.
   - (c) The table gates rules only in the exhausted bracket, where nothing
     else is injected either.
2. **How does the hook learn how full the session is, and what does it do when
   it cannot tell?** (technical facilitator) The prompt hook's payload carries
   no measure of the context window. The status line's payload does
   (`context_window.used_percentage`), but the status line writes nothing today
   and runs only where the person consented to it.
   - (a) Read the token usage of the last assistant turn from the transcript
     the hook's payload names, a bounded read of its tail, against a window size
     declared per model; reading that file at the host's hand-off has precedent
     in the transcript capture.
   - (b) Have the status line record the used percentage per session in abcd's
     state directory, and have the hook read it; recall falls back where the
     status line is not installed.
   - (c) Both: the status line's figure when present, the transcript read
     otherwise.
   - For an unknown fill: treat it as fresh, as moderate, or as depleted.
3. **Where is the floor between one line and nothing?** (technical facilitator)
   itd-39's press release and N10 both promise "then nothing", but no record
   gives the threshold below 40% free where recall stops.
   - (a) Below 15% free.
   - (b) Below 10% free.
   - (c) Only when the host reports the session is about to compact.
4. **Where does abcd learn how many maintainers a repository has?** (technical
   facilitator) The more-than-two rule needs the count, and abcd records none.
   - (a) The distinct owners in the CODEOWNERS file the forge reads.
   - (b) A `maintainers` list in `.abcd/config.json`, which `ahoy install`
     asks for and a person edits.
   - (c) The forge's own list of people with maintain or admin rights, asked at
     promotion (a network call).
   - (d) The required approving-review count in the branch ruleset mirrored
     under `.abcd/work/rulesets/`.
5. **How is another maintainer's agreement recorded and checked?** (technical
   facilitator)
   - (a) As the forge's approval of the pull request that carries the
     promotion, required by the repository's ruleset; abcd checks nothing itself.
   - (b) As an `agreed_by` stamp the other maintainer adds by running
     `abcd memory agree <mem-id>` in their own checkout, which the
     `memory_promotion_agreed` record-lint rule requires before the change
     lands.
   - (c) Both.
6. **Where does the person run the review and the promotion?** (product
   thinker) `/abcd:memory` is an agents' command, hidden from the person's
   menu, but reviewing and promoting are a person's acts, and the verb split
   ruled that a command a person needs to do their job is a person's command.
   - (a) The person asks the agent, which renders the review and relays the
     person's keep and discard answers through the host's question tool; the
     person runs `abcd memory promote` in a terminal, as with a ledger flip.
   - (b) `review` and `promote` move onto a command on the person's menu, such
     as the library or the board.
   - (c) The person runs the whole review in a terminal, with
     `abcd memory review` asking note by note.
7. **Where does a note's session id come from?** (technical facilitator) A
   verb an agent runs from its shell does not know which session it is in;
   only the hooks receive the session id.
   - (a) The page passes the host's own substitution of its session id, if the
     host offers one, confirmed in step 2's live trial; a host without it
     records the session as unknown, said so on every write.
   - (b) The prompt hook records the session id it last saw per working
     directory, and `add` reads it, refusing when two sessions share the
     directory.
   - (c) Both, the substitution first.
8. **Is a personal note bound to the repository it was written in?**
   (technical facilitator) The ruling put personal notes in the machine's
   file, which every repository on the machine reads.
   - (a) Bound by default, recalled everywhere with `--everywhere`, as designed
     above.
   - (b) Recalled everywhere by default, bound with a flag.
   - (c) Always bound; a lesson for every project is promoted into each.
9. **Which command carries the recall diagnostic?** (technical facilitator)
   itd-39 named `abcd memory recall`, the brief's `05-internals/07-memory.md`
   names a `library recall` design target, and since the verb split `memory` is
   the agents' notes command and `library` the person's.
   - (a) `memory recall`, showing notes and pages together, as designed above.
   - (b) `library recall` for pages and `memory recall` for notes.
   - (c) `rules --prompt "<text>"`, showing rules, notes and pages for one
     prompt.

# memory-recall

## Summary

This spec delivers the memory-recall bundle: memory notes
([itd-2610091918433290](../../intents/planned/itd-2610091918433290-an-agent-working-in-an-abcd-managed.md))
and memory pages recalled at the right moment
([itd-39](../../intents/planned/itd-39-scope-aware-memory-retrieval.md)).
An agent keeps short notes with `/abcd:memory`, and the loader that already
brings in the project's rules brings a note, and any longer memory page that
matches, back into the session when a prompt matches their words. Notes start
on the person's machine. Reviewing them and promoting one into the project's
record are a later dashboard's
([itd-2610111655362931](../../intents/drafts/itd-2610111655362931-on-abcd-s-dashboard-the-product-thinker.md),
the product thinker's ruling of 2026-10-11); until it ships, the review is
`memory list` and `memory remove`, and this bundle reads a note in the
project's file wherever one is.

The approach, in plain words:

- **A `memory.json` beside each `rules.json`.** The machine's
  `~/.abcd.noindex/memory.json` holds personal notes and the project's
  `.abcd/memory.json` holds promoted ones (the facilitator's ruling of
  2026-10-11). The loader reads both with the trust checks it already applies
  to the two `rules.json` layers. Agents write the machine's `memory.json`;
  people curate `rules.json`, so no agent's note ever edits the file that holds
  reviewed conventions (one-writer-per-file).
- **Write first, review later.** An agent writes any note without asking. Each
  note is stamped with who wrote it, when and in which session, and the
  redactor and the private-names banlist refuse a note that would hold a
  secret, a private name or a network address (adr-2610091918443997). Notes
  ship before the dashboard's review: until then, the review is `memory list`
  and `memory remove`, which removes any personal note, run by a person or by
  an agent at a person's request (the product thinker's ruling of 2026-10-11).
- **One recall for notes and pages.** The prompt hook recall-matches the
  prompt against rules, notes and pages in one pass. Notes and pages come back
  together in one block after the rules, deduplicated per session the way rules
  are.
- **Everything shrinks as the session fills, and nothing goes silent.** One
  table of context brackets in the loader serves rules, notes and pages. Notes
  and pages come back in full, then as one line each, and stay at one line to
  the end of the session; a rule domain comes back in full, then as its heading
  and first rule. A relevance ranking chooses which items survive when only
  some fit. The hook learns how full the session is from the status line's
  fill file when there is one (the one file the status line may write, by the
  product thinker's ruling of 2026-10-11), and otherwise from a bounded read
  of the transcript's tail. When neither tells it, rules come in full, as
  today, and notes and pages as one line each. The loader has no brackets
  today (see Design, "Context brackets"), so this bundle builds them once, in
  the loader.
- **One diagnostic.** `abcd rules --prompt "<text>"` shows the rules, notes
  and pages one prompt would bring back, with the ranking's reasons.
- **No promotion here.** This bundle has no promote operation, in the store or
  on the verb, so there is nothing an agent could promote with; the dashboard
  intent carries promotion and its person's-act rule.

How each acceptance criterion is met. N1 to N8 are the notes intent's, in the
order it lists them since its review and promotion criteria moved to
itd-2610111655362931; P1 to P5 are itd-39's.

## Design

### The `memory.json` file and its two layers

One schema serves both layers. The machine layer is
`~/.abcd.noindex/memory.json`; the repository layer is `<repo>/.abcd/memory.json`.

```json
{
  "schema_version": 1,
  "notes": [
    {
      "id": "mem-2610111200001234",
      "title": "The tests need the race flag",
      "body": "Run go test -race ./internal/... before saying the tests pass; the plain run misses the data race in the hook tests.",
      "recall": ["test", "tests", "race"],
      "root": "<the repository's root commit, full object name>",
      "origin": "agent",
      "written_by": "Claude:claude-opus-5-5",
      "written_at": "2026-10-11T12:00:00Z",
      "session": "<the host's session id, or null where the host supplies none>"
    }
  ]
}
```

- `id` is minted through the shared record-id seam (`recordid.Minter`,
  adr-45) with the family `mem`, so two sessions writing at once never collide
  and no coordination is needed.
- `title` is one line of at most 120 characters, `body` at most 2 KiB, and
  `recall` one to twelve words or short phrases, matched by the loader's own
  term rule (word boundary, stems, multi-word phrases). The figures are this
  spec's, set in one place, and a write past them is refused naming the limit.
- `root` ties a personal note to the repository it was written in: it is
  recalled only in that repository. A note written with `--everywhere` carries
  `"root": null` and is recalled in every repository on the machine (the
  facilitator's ruling of 2026-10-11). The repository layer carries no `root`:
  the file is already the project's.
- `origin` is `agent` or `host-memory-move` (the manual move, below).
- `written_by` takes the shape of the `Assisted-by:` trailer
  (`<Vendor>:<model-version>`), so who wrote a note reads the same way as who
  assisted a commit.
- `session` is the host's own identifier for the session, which the command
  page passes (below). Where the host supplies none it is `null`, rendered
  "session unknown" wherever the note is shown.
- The review's markers (when a note was last reviewed) and the promotion's
  stamps (who promoted it and who agreed) are not in this schema. The dashboard
  intent adds them, under a `schema_version` the reader then accepts.

Reading follows the `rules.json` layers exactly. The machine file is read only
through `fsutil.ReadHomeDeclaration`: a regular file this account owns that no
one else can write, within 256 KiB, never behind a symlinked
`~/.abcd.noindex`; a file failing those checks or failing to parse is a loud
error naming the file in tilde form, and the hook then recalls no notes from
it, while rules still inject. Absent, it costs nothing and nothing is created.
The repository file is read through the repository layer's guarded read, from
the root the rules loader resolved (a refused foreign-uid root reads no
`.abcd/memory.json` above the working directory, as with `rules.json`). The
kill switch in either `rules.json` silences note and page recall as well as
rules: it is the loader's switch, and recall is the loader's.

Writing touches the machine layer only; nothing in this bundle writes the
repository layer. Until the dashboard's promotion ships, a note reaches the
project's file only through a person's change to it, reviewed like any other
change to a committed file, and the loader recalls whatever valid notes that
file holds. A write opens `~/.abcd.noindex` in one walk from the home's
descriptor (`fsutil.EnsureHomeScope`), takes an exclusive `flock(2)` on the
directory at that path (`fsutil.WithDirLock`, which opens it `O_NOFOLLOW` and
leaves no lock file), re-reads the file under the lock relative to the
descriptor the walk opened (`rules.ReadUserLayerFileIn`), applies the change,
and writes through that same descriptor with `fsutil.WriteFileAtomicInRoot`
with mode 0600, so two agents writing at once both land. A directory renamed
after the walk makes the re-read refuse, so nothing is written rather than one
directory's notes replacing another's. The machine file is never created by a
read and is created 0600 by the first write.

### The write gate: redaction, banlist and stamps

Every note write passes one gate in `internal/core/memnote` before anything is
written:

1. **The shared scanner** (`internal/adapter/scanner`), the one canonical
   detector capture, history and the memory-page writer already route through,
   reached through the memory-page writer's own redactor, exported for it.
   The gate refuses on a degraded scanner, then scans the note's title, body
   and each recall word, and refuses on any span the memory-page writer would
   have to rewrite: any hard-fail secret, any identity or network span whatever
   its severity (`scanner.BlockingResidual`), and the literal home-directory
   backstop. Unlike the page writer, it never redacts and writes: the refusal
   names the kind of span and the field, never the span, and the agent
   rewrites the note in its own words, since a lesson with a span cut out of it
   may say something wrong.
2. **The private-names banlist**, through `banlist.MatchPrivate`, which the
   implement loop already uses. A store that cannot be read is treated as a
   match, as that function's contract requires. The banlist's private layer
   is per checkout (`.abcd/.work.local/private-names.txt`); in a linked
   worktree the gate also judges the note against the primary checkout's
   store, found through `banlist.PrimaryWorktreeRoot`, which is the layer the
   committed guard enforces there. There is no machine-wide banlist layer, so
   a note written with `--everywhere`, recalled in every repository, has been
   judged against the writing checkout's names only. `add --everywhere` says
   so on every write, and the command page says it too. Judging it against
   every checkout's names instead would need a machine-wide banlist layer that
   does not exist, which is a banlist change outside this bundle.
3. **The stamps.** `written_at` comes from the clock, never from the caller.
   `written_by` and `session` come from the caller (step 1's page), are
   shape-checked (a session that looks like a link is refused, so no session
   URL can enter a note), and are judged by the gate like any other field.

The gate is the only path into the machine file. How the dashboard's promotion
judges a note entering the project's file is that intent's to plan.

### One recall for notes and pages

A new package, `internal/core/recall`, holds what notes and pages share:
candidate items, matching, ranking and rendering. The prompt router calls it
once per prompt, after `rules.Inject`, with the items both note layers and both
page scopes yield. It returns one block, headed `## MEMORY`, appended after the
rules block in the same hook output.

- **Matching** is the loader's. `internal/core/rules` exports its prompt index
  and term rule (`indexPrompt`, `termHit`, the stemmer) as one small function,
  so a note's recall word and a rule domain's recall word hit on exactly the
  same prompts. An item is a candidate when any of its recall words hits; the
  ranking orders candidates and never adds one.
- **Items.** A note yields its title, body and recall words. A page yields its
  filename, its `index.md` summary line as its title, its body, and its
  `recall:` frontmatter list, which the memory-page schema already carries
  (`internal/core/memory/schema.go`). A page without a `recall:` list is never
  a candidate, so pages already written are silent until a recall list is
  added.
- **Scopes.** Pages are read from the checkout's `.abcd/memory/` and, when it
  exists, the machine's `~/.abcd.noindex/memory/` (read only, through
  `fsutil.OpenHomeScope`; nothing in this bundle writes it). When a recall word
  hits a page in both scopes with the same `<type>_<domain>_<slug>` name, the
  workspace page is the candidate and the machine page is suppressed (P4).
  Notes follow the same rule: an id is minted once, so a note in the project's
  file and one in the machine's share an id only if someone copied it by hand,
  and then the project's is the candidate and the machine's is suppressed.
- **Dedup.** The session ledger gains a second map, `recalled`, keyed by item
  (`mem-…` or `page:<filename>`) with a signature of the item's content, not of
  the form it was rendered in, so a bracket change never sends again an item
  already sent in any form (Context brackets, below). It is separate from the
  rules ledger because `rules.Inject` prunes any ledger name that is not an
  active domain, which would forget every item each turn. The same resets
  apply: `SessionStart` and `PreCompact` clear both maps, and the fixed
  backstop clears both on the same prompt (P3).
- **Budget.** Rules and memory share the loader's 64 KiB per-turn injection
  budget. Rules render first and memory takes what remains; an item that does
  not fit is not recorded in the ledger, so it is retried next turn, as a
  truncated rule domain is today. Until step 4's ranking lands, the
  candidates that fit are taken in id order (`mem-…` before `page:…`), and
  step 4 replaces that order with the ranking.
- **The host's memory files** are never among the paths the recall opens. The
  recall reads exactly four places: the two `memory.json` layers and the two
  page scopes. A test runs the recall through a filesystem seam that records
  every open, with a home directory holding a host memory directory full of
  matching text, and asserts the recorded opens are only those four (P5). Step
  5 extends the same test to the fill reader, whose opens are the status line's
  fill file and the one transcript the hook's payload names, and nothing
  under the host's memory directory.

The `--json` envelope of `hook prompt-router` gains a `recalled` list naming
each item injected, beside `injected` for domains, and (step 5) a `fill`
object naming the fill and where it came from, so a reader can tell what came
back and why.

### Ranking

When only some matched items fit, a relevance ranking chooses which ones stay,
as the facilitator ruled. The ranking is BM25 with per-field weights (BM25F),
computed in about a hundred lines of standard-library Go, with no new
dependency.

- **Query terms** are the prompt's stemmed tokens, from the same prompt index
  the matcher builds.
- **Fields and weights.** A term found in an item's recall words counts three
  times, in its title twice, and in its body once. The weighted frequencies are
  summed per term before saturation, as BM25F prescribes.
- **Score.** For each query term t present in the item,
  `idf(t) · tf_w / (tf_w + k1 · (1 − b + b · len / avg_len))`, summed over the
  terms, with `k1 = 1.2`, `b = 0.75`, and
  `idf(t) = ln(1 + (N − n_t + 0.5) / (n_t + 0.5))` over every note and page in
  reach (N items, n_t of them holding t). A word every item shares counts for
  little; a rare word that matches counts for a lot.
- **Ties** break, in order, on the narrower scope (repository before machine),
  then the more recent `written_at` (or page modification), then the id, so the
  order is the same on every machine and every run.
- **Explainable.** `abcd rules --prompt "<prompt>"` prints, for each
  candidate, its score, each matched term with its field and its contribution,
  the bracket in force, and whether it would come back in full or as one line,
  or not fit the budget. Nothing about the choice is hidden.

Prior art: BM25 is the probabilistic relevance framework's ranking function
(Robertson and Zaragoza, "The Probabilistic Relevance Framework: BM25 and
Beyond", 2009), and BM25F its multi-field extension (Robertson, Zaragoza and
Taylor, "Simple BM25 Extension to Multiple Weighted Fields", 2004). It is the
default similarity in Lucene since version 6 and the ranking SQLite's FTS5
`bm25()` exposes, with per-column weights. The fit challenge the prefer-sota
principle asks for set aside the two stronger-sounding options: dense
embeddings need a model or a network call inside a hook that runs on every
prompt, against the host-delegated and minimal-dependency stances and the
hook's fail-closed, never-blocking contract; a learned re-ranker needs
training data abcd does not have. A raw count of matching words, the order
`library ask` uses today, is what the ruling rejected: it lets a common word
outrank a rare, telling one. `library ask` keeps its order; changing it is not
in this bundle.

### Context brackets

The facilitator ruled that memory recall shares the rules loader's context
brackets (itd-3) with no thresholds of its own, and then that the brackets gate
rules too, with the same thresholds. The shipped loader has no brackets: it has
a fixed per-turn byte budget, and nothing in it reads how full the session is.
The brackets exist only in itd-39's design (the brief's
`05-internals/07-memory.md` § 9). So this bundle builds one bracket table in
`internal/core/rules`, beside the byte budget, and the rules injection and the
recall both read it from there, so no payload can grow thresholds of its own.

The table starts from itd-39's figures, read as the fraction of the context
window still free. There are three brackets of fill and no fourth in which
recall sends nothing: the facilitator ruled that recall never sends nothing,
because a compaction or a new session
resets recall anyway, so the one-line forms cost little and a session never
loses sight of what matches.

| Bracket | Free | Rules | Notes and pages |
|---|---|---|---|
| Fresh | 70% or more | Every matched domain in full, as today. | Every candidate in full, in ranked order, within the budget. |
| Moderate | 40% to 70% | Each matched domain as its heading and first rule, then a line saying how many rules it holds and that `abcd rules <DOMAIN>` renders the rest. | The top-ranked candidates in full within 8 KiB, the rest as one line each. |
| Depleted | below 40%, to the end of the session | As in moderate. | One line each (a note's title and id, a page's index line), the top-ranked lines within 2 KiB, and always at least the top-ranked one. |
| Unknown | no source tells (How full the session is, below) | As in fresh. | As in depleted. |

The unknown row is not a bracket of fill but the technical
facilitator's ruling of 2026-10-11 on what to do without one: rules keep the
form they have today, and notes and pages come back as one line each.

- A shrunk domain is never a heading alone: the loader already skips a domain
  with no rules, because a heading-only block reads as a domain that says
  nothing, and the first rule plus the pointer line keep that true. Rules are
  not reordered to choose the first. In a domain written in a `rules.json`
  layer, the first rule is the one its author put first. SHELL's and GRILL's
  rules are generated, so for them no author chooses: SHELL's first rule is
  the first hazard-registry entry in id order (`internal/core/rules/shell.go`),
  and GRILL's the first rule `question.AskingRules` returns
  (`internal/core/rules/grill.go`). A shrunk domain appears only under a known
  fill in the moderate or depleted bracket; an unknown fill keeps every domain
  in full.
- An item, rule domain or note or page, is sent once per session in whatever
  form its bracket gave it, and is not sent again in a larger or smaller form
  when the bracket changes: the ledgers key on content, not on form. The next
  reset (a compaction or a new session) clears the ledgers, and the item comes
  back in the form the bracket then in force gives.
- The 8 KiB and 2 KiB figures are this spec's starting points, set beside the
  thresholds in one place.

### How full the session is

The prompt hook's payload carries no measure of the context window. The
facilitator ruled for both sources, the status line's first (2026-10-11):

1. **The status line's fill file.** The `statusline` verb parses five values
   from the host's status payload today (`internal/core/statusline/payload.go`):
   the model, the context percentage (`context_window.used_percentage`), the
   two rate-limit percentages, and the working directory. It does not parse
   the session id. Step 5 adds the payload's `session_id` to that parse, kept
   out of every rendered row and JSON envelope as the working directory is,
   and used only to name the fill file. When the verb renders abcd's own row
   (never when it passes through to the person's previous status command) and
   the payload carries both the session id and the context percentage, it
   writes `{"used_percentage": …, "at": …}` to
   `~/.abcd.noindex/fill/<sha256(session)>.json`, mode 0600, atomically,
   through the home scope's guarded write (`fsutil.OpenHomeScope`, so never
   behind a symlinked `~/.abcd.noindex`). The file lives in the user-level abcd
   home, never in the host's configuration folder and never in a working
   tree. The writer and the file name live in `internal/core/rules`, beside the
   fill reader, so one package owns the file.

   This is an exception the product thinker granted on 2026-10-11 ("Allow one
   fill file") to the ruling of 2026-10-05 that the status line writes nothing
   (iss-2610050556383525). It covers exactly that one figure, in one file per
   session, and nothing else: no cache, lock, log or ledger, and no directory.
   The loader creates `~/.abcd.noindex/fill/` (0700) on its session-start
   reset, through `fsutil.EnsureHomeScope` rather than `os.MkdirAll`, so a
   symlinked `~/.abcd.noindex` is refused quietly and no `fill/` lands under
   its target; the status line writes only into a directory that is already
   there.
   The two read-only tests narrow to that one file and still refuse every
   other write: `TestStatuslineWritesNothing` (`internal/surface/cli`) allows
   one changed entry across its snapshot, the session's fill file, holding only
   those two fields, and still requires every other case, the pass-through
   path among them, to leave the snapshot unchanged;
   `TestStatusVerbReachesNoWritePrimitive` (`internal/core/statusline`) admits
   exactly one call, the fill writer, from one function in
   `internal/surface/cli/statusline.go`, and refuses every other write
   primitive and any second call site by name, as it refuses `mode.Set`. The
   verb's help text, which says "It writes nothing", and the doc comment above
   `newStatuslineCommand` change to say it writes only the session's fill file
   and where. An absent directory (the session-start hook not installed, or the folder
   swept) is a skipped write with no notice, since a stateless verb cannot say
   it once; any other failed write is named on stderr, and the row still
   renders either way. The
   status line runs only where the person consented to it at install, so this
   source is present only there.
2. **The transcript's tail.** Without a fill file for the session, the hook
   reads the transcript its payload names (`transcript_path`), at most its last
   256 KiB, through the guarded read (a regular file this account owns, never
   followed through a symlink). It takes the last assistant entry's usage, in
   the token-count shape `internal/core/history` already parses (input,
   cache-creation and cache-read input tokens), and divides it by the context
   window a per-model table in `internal/core/rules` declares for that entry's
   model, beside the bracket table. Where one model is offered with more than
   one window size, the table holds the smaller, so a doubt errs towards
   shrinking. Reading the transcript the host hands over has precedent in the
   transcript capture. The comment on `hookInput.TranscriptPath` in
   `internal/surface/cli/cli.go`, which says the field is supplied by the Stop
   hook and read by `hook session-end` only, changes to name the prompt
   router as its second reader.
3. **Unknown fill.** No fill file, no transcript, a transcript that fails the
   guarded read or holds no usage, or a model the table does not name: the
   fill is unknown. Rules then inject in the fresh form, exactly as they do
   today, and notes and pages come back as one line each (the technical
   facilitator's ruling of 2026-10-11, "Rules full, notes short"). Grounds:
   rules on a host where the fill is never known do not regress from today,
   and notes and pages, which are new, cannot flood a session that may be
   nearly full, while every match still shows as a line carrying its id and
   `rules --prompt` shows everything in full. The hook says the fill is
   unknown: the `--json` envelope's `fill` names the source as unknown on
   every prompt, and one line on stderr says it on the first prompt of each
   session (the ledger records that it was said).

The reset triggers delete the session's fill file with its ledgers, so a
compaction does not leave the hook reading the full session's figure until the
status line next refreshes, and the loader's existing sweep of stale session
ledgers sweeps the fill directory by the same age.

### The recall diagnostic: `rules --prompt`

The facilitator placed the diagnostic on the existing `rules` verb, which the
verb split put with the agents (`groupAgents`, page `commands/ahoy.md`).
`abcd rules --prompt "<text>"` shows what that one prompt would bring back:

- the bracket in force and how it was chosen (`--fill <percent-used>` sets
  it; without the flag the diagnostic has no session, so the fill is unknown
  and it says it is rendering the unknown-fill form: rules in full, notes and
  pages as one line each);
- each rule domain the prompt matches, with the recall words that hit and the
  form the bracket gives it;
- each candidate note and page, with its score, each matched term with its
  field and contribution, and its form: full, one line, or not fitting the
  budget.

It reads against an empty ledger, so it shows what a fresh session would get,
and writes nothing. `--prompt` with a positional domain is refused, exit 2,
naming the two forms. `--json` carries the same facts. The verb's help text and
`commands/ahoy.md` document it.

### The `/abcd:memory` agents' command

`/abcd:memory` is an agents' page under the verb split's rules
(itd-2610090831227812): `block: agents`, `user-invocable: false`, kept in the
flat `commands/` directory, named on an agents-block line of
`abcd --help --agent`, and held there by `TestCommandPagesMatchTheMenu`. The
binary verb is `abcd memory`, placed in `groupAgents` naming
`commands/memory.md`. Every sub-verb writes only through the core in
`internal/core/memnote`; the page carries the judgement half.

| Sub-verb | What it does | Writes |
|---|---|---|
| (bare) | Counts personal notes for this repository and everywhere, and notes in the project's file; names any layer that could not be read and why. | nothing |
| `add` | Writes one note to the machine layer: `--title`, `--recall` (repeatable), the body on stdin, `--by <Vendor>:<model>`, optional `--session <id>`, `--everywhere` and `--moved-from-host`. Prints the minted id; without `--session`, also prints that the session is recorded as unknown; with `--everywhere`, also prints that only this checkout's private names were checked. | the machine layer |
| `list` | Lists notes from both layers, each with its title, body, recall words, stamps, and whether it is tied to this repository or recalled everywhere: enough to review them by. | nothing |
| `remove <mem-id>` | Removes any personal note, whoever wrote it and for whatever reason, run by a person or by an agent at a person's request. A note in the project's file is removed by editing that file in a reviewed change, never by this verb. | the machine layer |

`list` and `remove` are the review until the dashboard ships (the product
thinker's ruling of 2026-10-11, "Ship, list and remove"): a person reads the
notes with `list` and removes any they do not want, or asks an agent to.

The page tells the agent when to write a note (a lesson it would otherwise
relearn: a flag the tests need, a preference the person stated, a trap in the
tooling), to choose recall words a later prompt would actually use, to keep one
lesson per note, to add `--everywhere` only for a lesson that holds in every
project, and never to put a secret, a private name or a network address in
one, since the binary refuses it. It says that an `--everywhere` note has been
checked against the writing checkout's private names only, so a name another
project bans is the agent's to keep out. It tells the agent to run `remove`
only when the person asks. It passes `--by` with the agent's own vendor
and model, and `--session` with the host's own substitution of its session id
written into the page's text, so the host fills it in and the agent never
guesses it (the facilitator's ruling of 2026-10-11). Step 1's live trial
confirms the substitution on the first host. Where a host offers no
substitution, the page leaves `--session` out, and the note is recorded as
session unknown, said on every write.

### The manual move from the host's memory files

The person points at a lesson in the host's own memory files, or pastes it.
The agent, at that word and only then, reads the passage the person named with
the host's own tools, and files it with
`abcd memory add --moved-from-host`, the text on stdin. The binary stamps
`origin: host-memory-move` and judges it through the same gate. The binary
takes no path operand on `add`, so it never opens the host's files at all, on
this verb or any other; the page tells the agent never to scan those files for
candidates, and never to edit or delete the original. Removing it there is the
person's choice, in the host. abcd's ruling of 2026-10-05, that abcd never
touches the person's host configuration folder, stands unchanged.

### Review and promotion: on the dashboard

The product thinker moved the review and promotion to a later dashboard where
the product thinker and the technical facilitator click the notes they want to
promote (2026-10-11). The two criteria and the two open questions on the
maintainer count and the agreement are carried, verbatim, by the draft
itd-2610111655362931, which builds on the notes intent and the dashboard
intent (itd-2610032150577708).

Notes ship before that review (the product thinker's ruling of 2026-10-11,
"Ship, list and remove"). Until the dashboard ships, the review is `memory
list` and `memory remove`, for any personal note, run by a person or by an
agent at a person's request; the dashboard draft is the review's later home,
as adr-2610091918443997's Consequences record.

This bundle keeps no promote operation, neither on the verb nor in the store
for the dashboard to call later: a store operation with no caller until the
dashboard ships is unwired code, which the wired-or-it-isn't-done boundary
refuses. With no promote operation there is nothing for an agent to promote
with, so this bundle adds no guard entry; the guard entry and terminal check
the earlier draft of this spec designed (after the source ledger's flip,
adr-41) go to the promotion intent as its starting design. What remains here
is the repository layer's read, so a note a person puts in the project's file
is recalled, and the schema the dashboard will extend.

### Provenance

Every note answers who, when and in which session, in the file, in `list` and
in the `rules --prompt` output. `written_by` and `session` are the writer's
stamps, and `written_at` the clock's. The stamps are never rewritten after the
fact. The session id is the host's identifier for the session, never a link to
it, so it carries no session URL; where the host supplies none, the note says
"session unknown" rather than guessing.

Design choices this spec makes inside those rulings, each with its grounds and
each open to the facilitator's veto at review:

- **A shrunk rule domain ends with a pointer line** naming how many rules it
  holds and `abcd rules <DOMAIN>`. Grounds: a guardrail domain shrunk to its
  first rule must still say where the rest is, and the loader already skips a
  domain that would render as a heading alone.
- **The ledgers key on content, not on rendered form.** Grounds: a bracket
  change would otherwise send again, in a smaller form, an item already in the
  context in full.
- **The fill file lives under `~/.abcd.noindex/fill/`, created by the
  loader.** Grounds: the question behind ruling 10 offered the local tier or the
  user-level abcd home, and this location is the facilitator's choice, recorded
  in the notes intent's Decisions as the ruling's place; a session is not bound to one checkout, so the user-level home keeps
  one file per session wherever its working directory is, and no status
  refresh writes into a working tree. The loader creates the directory so the
  status line's one write stays one file.
- **`--everywhere` notes are judged against the writing checkout's private
  names only, and say so.** Grounds: the reviewer offered judging them against
  a machine-wide banlist layer as well, if cheap; no such layer exists (the
  private layer is per checkout, a linked worktree inheriting its primary's),
  so building one is a banlist change outside this bundle. The gate reads the
  primary checkout's store in a linked worktree, which is cheap, and `add
  --everywhere` and the command page say which names were checked.
- **Survivors are taken in id order until the ranking lands.** Grounds: step
  2 must choose when only some candidates fit before step 4 builds the
  ranking; id order is deterministic and is replaced, not kept beside it.
- **Where a model has more than one window size, the smaller.** Grounds: a
  doubt about the window should shrink recall, not flood the context.
- **No promote operation, and so no guard entry, in this bundle.** Grounds: a
  store operation with no caller until the dashboard ships is unwired code.
- **BM25F with recall words weighted three, title two, body one.** Grounds: the
  prior art above; standard library only; deterministic and explainable.
- **The gate refuses rather than redacts a note.** Grounds: a lesson with a span
  cut out of it may say something wrong, and the agent can always rewrite it.
- **The bracket table and the window table live in `internal/core/rules`.**
  Grounds: the ruling's "share the brackets" read literally, so no payload can
  grow a second set.
- **Rules and memory share the 64 KiB per-turn budget, rules first.** Grounds:
  the budget is the loader's flood guard, and a second budget would double it.
- **A separate `recalled` ledger.** Grounds: the rules ledger is pruned to
  active domains every turn.
- **The figures** (120-character titles, 2 KiB bodies, twelve recall words,
  the 8 KiB and 2 KiB bracket budgets, the 256 KiB transcript tail) are
  starting points, each set in one place.
- **Step 1's own limits, chosen while building it (2026-10-11).** A recall
  word is at most 64 characters, holds a letter or digit, and is unique
  ignoring case; the body is trimmed and must not be empty; a session id is
  letters, digits, `-` and `_` (`[A-Za-z0-9_-]`, starting with a letter or
  digit), at most 128 characters; the no-root-commit refusal points at
  `--everywhere`; `memory list` shows a note tied to another repository as
  "another repository"; and `mem` joins `recordid.handleInTextRe` in step 2,
  where notes first come back in running text, not in step 1. Grounds: each
  bounds what a note can carry or how it is named without a ruling of its own,
  and is open to the facilitator's veto at review like the choices above.

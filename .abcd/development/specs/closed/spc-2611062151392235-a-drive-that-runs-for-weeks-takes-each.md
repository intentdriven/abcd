# a-drive-that-runs-for-weeks-takes-each

## Summary

`abcd drain --drive` takes each newer stable release of abcd at a lane boundary: it checks the release origin at most about once an hour, fetches the platform binary into a staging file through the verification `abcd update` makes, runs the staged binary read-only against the checkout's drain, proves it in the drive's own live launch before the installed binary is touched, swaps atomically keeping the previous binary, and re-executes itself to resume from the drain's state. A re-executed start that keeps failing before its first move restores the kept copy and carries on with it. `--no-self-update` turns it off. A source build, a plugin root's binary, a package manager's and the track-latest shim never self-update. The trust rule is adr-2611062149324491 (proposed).

This spec is written against the wall work on the branches that land before it (`wall-init-1106`, `wall-reprove-1106`): `WriteWallSettings` renders the hooks and the harness's attribution, `renderedByAbcd` accepts the previous rendering, `ProveWall` takes `bin` as the approver, the harness is pinned to one file for the run, and `checkStageFiles` compares abcd's binary by content before every stage. Nothing here depends on the branches' tests.

The builder reads first: `internal/surface/cli/drain_drive.go` (the drive's preconditions, consent, walls and loop start), `internal/core/runner/wall.go` (`WriteWallSettings`, `writeStageFiles`, `checkStageFiles`, `ProveWall`, `SelfBinary`), `internal/core/update/update.go` (`Plan`, `Apply`, `verifyRelease`, `stageVerified`, `runsFromTarget`), `internal/core/update/fetch.go` (`FetchVerified`), `internal/core/ahoy/update_target.go` and `foreign_entry.go` (`releaseOfBuild`), `internal/core/ahoy/release_mark.go` (`ReleaseOlder`), `internal/core/implement/loop/terminal.go` (`run`, `driveLane`, `wallHeld`, `TerminalOptions`), and `internal/surface/cli/update.go` (what the verb does after a swap).

## What the verification proves, and what it does not

The staged bytes pass `Updater.FetchVerified`: the release's `checksums.txt` names their digest (the download arrived intact; the manifest sits on the release page, so it proves no more); a build provenance for exactly those bytes verifies in process against the Sigstore trusted root (anchored on the root built into the binary, fetched through TUF), its certificate chaining to Fulcio, its entry in Rekor, its signer abcd's release workflow on the default branch run on a GitHub-hosted runner, and both the certificate's source digest and the provenance's source commit the commit the tag resolves to (so an older release's genuine build re-uploaded under a newer tag is refused); and the bytes' own Go build metadata names the tag (`ahoy.CheckReleaseClaim`). It proves the bytes are the release the publisher cut. It does not prove the release is free of defects, that it works on this machine, this harness or this repository, that the publisher's latest-release answer is the newest release that exists, or that the staging file is unchanged after it is written. The live proof covers the walls; the re-read digest covers the staging file; nothing covers the rest, by design.

## The decision's inputs

The decision to swap reads, and reads only:

1. `--no-self-update`, from the drive's own arguments, in memory.
2. The clock: the time of the last check, in memory.
3. The running binary's own build metadata: `debug.ReadBuildInfo()` of this process, read once at the start, through `ahoy.releaseOfBuild` (export a reader; a build claiming no release tag disables self-update for the run).
4. The installed binary's kind, read once at the start: `os.Executable()` resolved, a regular file, not under a plugin root (`ahoy.PluginRootContaining`), not under a Homebrew Cellar (`update.brewCellarPrefixes`), not the track-latest shim; `update.Plan`-shaped refusals, computed for the running file rather than for the first `abcd` on PATH.
5. The release origin, over `urlguard` on its override-free roots, with no proxy read: the latest-release redirect (`vintage.ReleaseFetcher.LatestTag`), `checksums.txt`, the asset, GitHub's attestations API and the Sigstore TUF repository. The client is `update.NewSelfUpdater`, and not `newUpdater`, whose `scrubEnv` unsets the proxy and certificate variables for the whole process: that fits a verb that exits, and in a drive would take the person's proxy away from git, the forge and every agent.

None of the files on the account that a drive writes is an input above. The installed binary and the settings are compared with the start before every stage (`checkStageFiles`), so a difference ends the run as today (`TerminalWall`), and no update runs after a failed comparison. The staging file is held to its verified digest and to being a regular file, a link refused, immediately before each run of it (both of the rehearsal's and the proof's launch) and before the swap, and the installed file likewise immediately before the re-execution; a check that fails runs and swaps nothing, and is no verdict on the release. The release mark and the install record are written after a swap, as `abcd update` writes them, and never read. The rehearsal reads the checkout and its ledger, so a failed rehearsal keeps that version out and never brings one in: the candidate comes from the origin and passes the verification and the proof whatever the rehearsal reads. The one fact that crosses a re-execution about a refused release, its tag, travels in the arguments (`--update-refused`) rather than in a file. The drain's state is read at a resume: with no drain in progress `--after-update` refuses, exit 2, and the run ends on the new binary with nothing to resume.

## What a stage's hooks and settings name, and the plugin root

The profile's `settings.json` names the drive's binary by absolute path (`wallSettings(bin)`, `SelfBinary()`). The path does not change; its contents do. The re-executed drive runs `WriteWallSettings(p, SelfBinary())` at its start as every drive does, which writes a byte-identical file when the rendering is unchanged, and `writeStageFiles` records the new binary's content as the baseline `checkStageFiles` compares against. So the comparison never refuses because of the swap itself. The one way it would say something is a release that changes the rendering: `WriteWallSettings` then reports the file as edited and replaced, a line and not a refusal, unless `renderedByAbcd` accepts the previous release's rendering; the branch's `wallSettingsHooksOnly` is the pattern, and the rule for every later release is in the ADR's consequences. The approver is `c.approver = selfBinary()` at launch and so is the new binary after the re-execution.

The plugin root's binary and the plugin's pages are never touched. A drive's stages load no plugin (`ProveWall` refuses one that is not the harness's own), and `update.Plan` refuses a plugin root's binary as a target, so a drive started from one never self-updates and says so. The person's own host sessions keep the plugin's vintage until they take a plugin update in the host, which `abcd ahoy` then lists. One place a drive reads the plugin root is `agentPrompt` (`internal/surface/cli/dispatch.go`), the reviewer prompts for the remote review route (`oracle.ReviewRP`), read from `agents/` under the plugin root the install record names; after a self-update those pages stay at the plugin's vintage, which a new release must keep reading. The default route reads none.

## Design

**Core, `internal/core/update`.** Add `selfupdate.go` (a new file in the package, not the dependency's name) with:

- `type SelfTarget struct { Path string; Version string; Refusal *Refusal }` and `func ResolveSelfTarget() SelfTarget`: `osExecutable()` resolved through symlinks, its kind judged as above, and the running build's release tag; a `Refusal` names why the binary never self-updates, in the shapes `Plan` uses (`plugin-root`, `package-manager`, `dev-shim`) plus `source-build` (the build claims no release tag). Nothing on the network.
- `func (u *Updater) Candidate(current string) (tag string, newer bool, err error)`: `ResolveTag("")`, then `newer` is `ahoy.ReleaseOlder(current, tag)` and the tag carries no pre-release suffix. One request.
- `func (u *Updater) StageRelease(target, tag string, progress io.Writer) (Staged, error)`: `FetchVerified(tag, progress)` then `stageVerified(target, r.Bytes)`; `Staged{Path, SHA256, Signer}`. The staging name stays `.<name>.new` beside the target, which `selfupdate.CommitBinary` renames into place.
- `func NewSelfUpdater() *Updater`: the release client above. `func KeptPath(target string) string` and `func RestoreKept(target, keepAs string) (digest string, err error)`: the kept name, and the kept copy renamed back over the target with its digest read for the install record.
- `func CommitStaged(target string, st Staged, keepAs string) error`: reads the staging file's digest again and refuses with the file removed when it differs from `st.SHA256`; then `selfupdate.CommitBinary(selfupdate.Options{TargetPath: target, OldSavePath: keepAs})`, with the same rollback handling `Apply` has. `keepAs` is `.<name>.previous` beside the target; whatever stands there first is removed.
- `Apply` is untouched: `abcd update` keeps its receipt and removes the old file as it does.

**Core, `internal/core/runner`.** In `wall.go`:

- `func ProveCandidate(ctx context.Context, p Profile, candidate string) error`: writes the profile's `settings.json` as `wallSettings(candidate)` (the settings file only; `stagesWritten` is not touched, so the running drive's baseline stands), runs `ProveWall(ctx, p, candidate)`, and restores the file to `wallSettings(SelfBinary())` on every path out, returning the proof's error. The caller runs `CheckWallSettings(p, SelfBinary())` before it, as before any stage, and the restore is byte-identical to what that check compares against. The staging file is `0o755` (`stageVerified`), so the hooks and the approver run it from its dotted name.
- `func SelfBinaryContent() [sha256.Size]byte` is not needed: `checkStageFiles` already compares `binaries[SelfBinary()]`.

**Surface, `internal/surface/cli`.** In `drain.go`: the flag `--no-self-update` (bool, drive only, refused without `--drive` in the same shape as `--until`), and two hidden flags the re-execution passes: `--after-update <from>=<to>`, refused when the running build's release tag is not `<to>` or when no drain is in progress (`loop.ReadDrainProgress(...).Live` false), and `--update-refused <tag>`, repeatable, which the kept copy starts with so the tag stays tried, refused on the same state. Both refuse on a build that never self-updates and with a session's marker set, naming the flag, before anything is read or renamed. What the flags change is checked in turn: `--after-update` is honoured only for the release this build claims and leaves out the live launch on a first attempt, an attempt after a failed one proves itself, and what guards a restore is the kept copy's verification, and the kept copy then proves itself live. `--until` is read without its past check at a resume: a bound that passed during the step ends the run in the loop, and a refusal there would read as a bad release. `driveFlags` gains `noSelfUpdate`, `afterUpdate`, `refused`, `self` and `reached`.

In `drain_drive.go`:

- `driveConsent`: one more line, labelled `releases:` since the screen's `updates:` line is the harness's. On a target `ResolveSelfTarget` admits: `releases: asks the release origin about once an hour, at a lane boundary, and takes a newer stable release after the update verb's verification and the live check, going on from the drain's state (--no-self-update turns it off)`; the line names the request because the ADR rests the yes on it. On that target one more line follows: `others:   any other drive on this account ends when this one moves to a new release, whatever flags it has`. With the flag: `releases: none (--no-self-update)`. On a refused target: `releases: none: <refusal detail>` (for a source build: `this abcd is a source build, which never self-updates`). With `--after-update`, the consent screen is not shown; one line prints instead, through `say`, in `update.UpdatedFormat`'s wording, `abcd updated from <from> to <to>`, prefixed `abcd drain --drive:`, and the drive goes straight to the static walls and the loop. The yes was given once; `--after-update` implies it.
- `driveSelfUpdate(ctx, p, f, say) (reexec bool)`: the step, run at a lane boundary (below). It returns at once when the flag is set, the target is refused, or less than an hour has passed since the last check. Otherwise, in order: `driveWalls.settings(p)` (a failure is the loop's to end, so return); `Candidate(current)`; `runner.HarnessMoved`, which resolves the harness as a start would, marks another file the run's signing team admits as unproved, marks nothing for one it does not admit or with no team, and either way leaves the release for a later check, fetching and rehearsing nothing, said once a release for the second case; `StageRelease`; the rehearsal below; `ProveCandidate`; `runner.HarnessOwed` or `HarnessMoved` again, which on true leaves the swap and the tag alone and the next check to try again, since the re-executed drive proves no wall live and this drive's next wall check proves the harness; `driveWalls.settings(p)` again, with the settings put back by then, since a re-executed start pins what stands, so a difference at the harness's own path, in a program or in a declaration swaps nothing and is the loop's own check to end; `CommitStaged`; `ahoy.RefreshPathEntryDigest(target, digest)`; `ahoy.RecordReleaseMark(tag, false)`; then the re-execution. A verdict on the release before the commit is said once with `say` (`abcd drain --drive: a newer release <tag> was not taken: <why>; going on with <current>`), records `tag` as tried so the same tag is not fetched again, and returns false: a provenance or digest mismatch, a failed proof. A failed rehearsal is said once per reason and tried again at later checks, since it reads the checkout as it stands. A fault that says nothing about the release does not record the tag and the next check tries it again, with one line each attempt: `update.NoVerdictError` marks a transport fault, any status but not-found, a body cut short, a trusted root not fetched and a staging file not written, and a limit or a launch with no verdict at the proof is the same. The interval's clock is set before the request, so a retry waits its hour, and the check is one request under its own short bound with no fetch behind it when it fails, so a dead network does not hold a lane boundary. A stop signalled before the commit cancels the step with nothing swapped; a stop that arrives after the commit ends the run as asked, with the new binary installed for the next start. The seams `driveSelfUpdateSteps` (a struct of funcs, as `driveWallChecks` is) and `driveReexec` are package variables the tests replace.
- The rehearsal, `driveRehearse(ctx, repoRoot, staged, args)`: the wall proof exercises `guard approve`, `guard hook` and the session hooks but no drain verb, so before the proof the staged binary runs in this checkout, in the sealed environment a stage's shell has rather than the drive's own, as a process group of its own, killed whole at the two-minute bound. It takes the arguments its re-execution would be given with `--help` added, so a release that dropped a flag this drive passes is refused here; then `drain --dry-run --json`, which writes nothing and fetches nothing, must exit 0 with `dry_run: true`. Anything else leaves the installed binary as it was and the drive goes on; a later check tries that version again.
- The re-execution: `syscall.Exec` of the installed name read before the swap, the one just held to the digest, so a drive started through a link runs what it checked, with `os.Args` holding `--after-update <from>=<to>` in place of any earlier one, `--yes` added when absent, and `--profile <name>` added when absent, so a second directory appearing under the profiles since the start is no reason to stop. `--max`, `--pace`, `--sub-agents`, `--fix-rounds`, `--skip`, `--reason` and `--unskip` are left out: the boundary runs only after a move, so the drain's state holds what they gave. Given again, a cap set over a live drain with none would refuse its own start, and a pace or a skip would undo what a person changed since. Nothing is closed first: the drive's lock and log are close-on-exec, a caught signal goes back to its default across exec, and a refused exec therefore leaves the drive as it was, with its lock. The re-executed drive takes the lock again under `driveLockWait`. An `Exec` that returns is a failure: the kept copy goes back over the target only when it matches the digest the run holds for its own binary (`runner.PinnedBinary`), which needs no request; say so once, and return false. The process group, the terminal and the standard streams carry over, so the person's terminal shows the new drive's lines.
- A resuming start that fails, on the new release or the kept copy, is tried again: a passing failure is no verdict on the release. `driveStartRetries` waits 15 seconds, 45 seconds and two minutes before each further attempt, one line each, under a signal context, so a stop ends the wait with the killed exit and nothing restored. What a failed try would say, the end of the run and under `--json` its one refusal document, waits until no attempt follows it, so a try that will be tried again says only that, and a kept copy that goes on answers for the run. A limit at a resuming start's proof waits with no bound given, as a limit in the loop does, up to its eight hours, and ends with exit 3; a person's start with no bound still refuses at once. A stop asked for during a try does the same, whatever that try then does, the window before the drive's own signal handling starts included: no further try runs, no proof launches, and the kept copy does not start. Another drive's hold, a stop, a limit and a comparison that ended the loop are not tried again, and a first start a person typed answers at once. Each attempt after the first holds the installed file to its digest as the process began, the person's machine declarations and the programs beside the harness to `runner.StartPins`, taken as that process begins and after `PinPrograms`, and any pin to `runner.CheckPinnedBinaries`, before `writeStageFiles` pins anything, since the likeliest failed attempt pinned nothing, and a difference ends the run naming the way back; a harness that changed in the wait is held to the signing team the run pinned, or where no attempt has pinned one to the team `runner.PinStart` verified as the process began, rather than read afresh, and one carrying another team stops the run as a new file does between stages while one with no identity to read has the file's tries; it then proves itself live, so a harness that changed in the wait is proved.
- A re-executed start that fails: `runDrive` wraps the start, and a failure of the re-executed drive before its first move (exit 2 or an uncoded error, a panic in the drive's own goroutine read as one) that repeats through those attempts goes to `driveGoBack`. `TerminalOptions.Moved` says the first move was made, so a release whose first move refuses goes back too. A code 3 before that move, a stop, a limit or a wait, goes back to nothing. Under the checkout's drive lock it verifies the kept copy, its own build claim naming `<from>` and `update.VerifyReleaseProvenance(<from>, digest)` passing, and on anything else renames nothing and exits 2 naming the copy and `abcd update <from>`. A verification that came to no answer (`update.NoVerdictError`) is no verdict on the copy, so `driveVerifyRetries` asks again after 5 seconds, 15 seconds, 30 seconds and a minute, one line each, with the lock free between tries and a stop ending the wait with nothing restored; only the last no-answer counts as not verifying, and a verdict refuses at once. It restores the bytes it verified over the target and refreshes the install record's digest, says one line naming both versions, and execs the kept copy with `--after-update` taken out and `--update-refused <to>` added, in place of a refusal. The kept copy proves itself in one live launch, since it is rare and costs one launch. A lock it cannot have, or a start that lost the lock to another drive, or a stop, goes back to nothing: another drive holds this checkout, or the stop was asked for. A restore or an exec that fails ends with exit 2 naming the kept copy and `abcd update <from>`, or that the kept copy is back and the way to start it. A run that has made a move and then fails does not come back: it ends as any drive does, with one line naming the kept copy, and a panic past that move stays a panic.
- `driveRun`: hand the step to the loop as `TerminalOptions.AtBoundary func(ctx) (stop bool)`.

**Core, `internal/core/implement/loop`.** In `terminal.go`: `TerminalOptions.AtBoundary func(ctx context.Context) bool`, called in `run` after `wallHeld` and before `Drain`, once after each drain move, that is, when nothing is in hand (a lane has ended, or a wait ended before the next opens), and never during a stage. A refused step comes back with its lane still in progress and reserved, and a judgement holds its issue, so the call stays due until the next move has settled them, for `TerminalOptions.BoundaryCeiling` at most, which the drive sets to its check interval: a stuck one must not keep a release out for the whole run. The first wait that holds a due call says once, on its line, that a new release may be waiting. Past the ceiling the call runs beside them, what the run holds is renewed while it does, and a re-execution takes the lane up from the drain's state. Only a skip the run gave and the next move has yet to take holds the call absolutely. `TerminalOptions.Resumed` says this process goes on from another, whose held-back issues the drain's skip list holds, so their lines and the run's exit 3 survive the move. The run's first pass has no boundary: no drain move has written the state a resume reads, so its `Live` check would refuse and end the drive. The callback returns whether it took time, the exec never returning on success, so the loop needs no new end state; when it took time the loop goes round its checks again before anything starts. Nothing else in the loop changes; `BeforeStage` keeps its meaning.

| the run's own name | a system whose report of a process's name follows its file to the kept copy, a refused re-execution; a run with `--no-self-update` or on a build that never self-updates | the name read at the start is what the comparison goes on holding, so the drive goes on; no boundary and no ceiling are set, so no wait line speaks of a release |
| what stands before the swap | new bytes at the harness's own path or a changed declaration during a check's proof; a proof that passes and changes nothing; a link moved to a file of another team or with no team held, the old file standing and a release waiting | neither the swap nor the re-execution comes, and the loop's own check ends the run; the passing proof swaps; the moved link marks nothing, the run carries on with no re-proof, one line says so and the release waits |

## Order of work

1. `internal/core/update`: `ResolveSelfTarget`, `Candidate`, `StageRelease`, `CommitStaged`, with their tests; `Apply` untouched.
2. `internal/core/runner`: `ProveCandidate`, writing and restoring the settings file around `ProveWall`; its test on the fake harness.
3. `internal/core/implement/loop`: `AtBoundary` in `TerminalOptions` and `run`; the boundary test.
4. `internal/surface/cli`: the two flags, the consent line, `driveSelfUpdate`, the re-execution, the resume; the rows above.
5. The docs and the generated appendix; `make precheck`, then `make preflight`.

Steps 1 to 3 are independent of one another and land together or in that order; 4 needs all three.

## What it must not change

- `checkStageFiles` and `CheckWallSettings` keep refusing a changed binary and changed settings before every stage; the self-update never relaxes them, and runs only when they hold.
- `abcd update`'s `Apply`, receipt, refusal shapes and the removal of the old file.
- The consent screen's existing lines, the yes, and `--yes`'s meaning.
- `ProveWall`'s checks: the candidate is proved by the same function with a different `bin`, and no wall is skipped for it.
- The loop's end states, `BeforeStage`, and `driveLane`; no network request inside a lane.
- The plugin root, its binary and its pages; `ahoy install` and `ahoy`'s detection.
- The drain's state files: the resume reads them; nothing new is written to them for the update.
- No configuration key, environment variable or repository file is read to decide the update.

## Risks the builder watches

- `os.Executable()` on macOS reports the path abcd was invoked through; resolve it (`filepath.EvalSymlinks`) before judging its kind, and keep `SelfBinary()` as the path the hooks name.
- The settings file written for the proof names the staging path; a crash between the proof and the restore leaves it so, and the next drive's start replaces it and says so. Acceptable: a drive rewrites the settings at every start.
- The re-executed drive's `WriteWallSettings` must see the previous release's rendering as abcd's, or the start prints a false "edited" line; keep the previous rendering as a fixture and the compatibility row above.
- A reviewer route reading the plugin root's pages after a self-update reads the plugin's vintage of them.
- Every later release must keep answering what an earlier one starts it with: `--after-update`, `--update-refused`, `--no-self-update`, and `drain --dry-run --json` with `dry_run: true`. A release that drops one is refused at the rehearsal, which leaves every drive on the release before it for good.
- One drive's swap ends any other on the account at its next comparison, whatever flags that other has, as a changed binary does, and on one profile one drive's proof rewrites settings the other compares. One drive to an account is the supported shape (dcn-2611070019463013); a second is not refused, a start that may take a release says so in a line, and a second such run ends with the lane let go, naming the file, and the next start runs the new binary.

## What the two start checks cannot cover

The rehearsal and the fall-back cover a release that refuses a drain's arguments or preconditions. They do not cover a binary that panics or fails to load before `runDrive` is reached, one that hangs at its start (no process outlives the exec to watch it), a failure resolving the checkout or a refusal of the hidden flags before the wrapper is entered (a resume with no drain in progress among them), or a fault that shows only after the first move, which ends the run naming the kept copy, as a comparison that fails does at any point. A kept copy that itself cannot start ends the run: there is no chain of copies. The re-executed start pins what stands at the installed name when it starts. An attempt after a failed one holds the installed file, the person's machine declarations and the programs beside the harness to what the process began on, and to any pin it made, before it pins anything, and a difference ends the run; a harness that changed is held to the signing team that pin or that beginning holds, with another team ending the run and no identity to read having the file's tries; it then proves itself in one live launch. A signal in the milliseconds before the new process's watcher takes it ends that process with the signal's default.

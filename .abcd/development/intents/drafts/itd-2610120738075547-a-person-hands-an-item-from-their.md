# Work handed to a cloud session comes back, or says why not

Typed links: `builds_on` [itd-2609091034175565](../planned/itd-2609091034175565-nothing-tells-an-agent-that-a-record-it.md) (reservations on the shared remote, being built now: a cloud session reserves the item it takes, which is how every other session, local or cloud, sees that it is held; this record adds nothing to the reservation itself); `related_issues`, the six findings of 2026-10-12 this record answers, each listed under Why This Matters. `related_intents`, prose relations no typed field carries: [itd-2609150819440345](itd-2609150819440345-which-session-holds-which-worktree.md) (the wider register of running sessions, kept for later; this record's list covers only the cloud sessions abcd briefed, read from the remote), [itd-152](../shipped/itd-152-autonomous-cloud-runs-in-sibling-repos.md) (shipped: tool footers and session links leaking from cloud runs into public text; a report this record posts publicly is held to that same outbound check, nothing more), [itd-107](itd-107-autonomous-routines-assemble-from-one.md) (routine prompts assembled from one versioned template; the cloud brief here is a one-off brief for one item, and may later become one of that template's archetypes) and [itd-22](itd-22-harness-portability.md) (the host-profile seam: the host connector this record's first rung writes for one host, decision 1, is a piece of that seam, not a second one).

## Press Release

> A person hands any item that is ready to build, from a small fix to a planned feature, to a cloud agent session as easily as to a session on their own computer: abcd starts the session itself, and the work comes back, or the session says why it could not. The cloud session runs with the same abcd tools the person has, on a machine abcd prepares with the same checks, run as an ordinary user rather than as the machine's all-powerful one, and checked before any work starts, so a session never finds out halfway through that it cannot pass the project's checks. It gives the session a brief that says what to work on, whose name the work goes out under, and how to stop and report. Every session, finished or stopped, posts its report where abcd can read it, and one list shows each cloud session's item, branch and report, so nobody copies a report out of a transcript by hand. Nothing from the cloud lands until it has passed the checks again on the person's own computer. When the cloud cannot be reached, or the login abcd starts sessions with has run out, abcd says so before anything starts, instead of quietly running the work on the person's own computer. It starts with one host's cloud sessions; other agent hosts plug into the same place later.
>
> "On the day I moved three fixes to the cloud, two things went wrong at once," said Maya, an autonomous-development practitioner. "The sessions I meant for the cloud started on my laptop without telling me, and the ones that did reach the cloud finished their work, failed checks their machine could not pass, and kept everything to themselves. I copied one report out of a transcript by hand and redid its fix locally. Now I tell abcd which item to send, the session checks its own machine first, I read every session's report from one list, and what comes back passes my own checks before it lands."

## Why This Matters

On 2026-10-12 three issues that needed no decision were moved to cloud agent sessions, and every step of it was done by hand or went wrong quietly:

- **The work started in the wrong place, silently.** The requesting session's sub-agents could not reach the cloud and started on the person's own computer instead, in worktrees under the checkout (`.claude/worktrees/`), and other sessions learned of it only when the requesting session corrected its own announcement ([iss-2610120729076366](../../../work/issues/open/iss-2610120729076366-cloud-dispatch-falls-back-to-local.md)).
- **The real cloud sessions were started by hand.** The person launched them in the browser with briefs a local session wrote; nothing in abcd composes such a brief, lists the running sessions or collects their results ([iss-2610120729071657](../../../work/issues/open/iss-2610120729071657-abcd-cannot-launch-or-manage-cloud.md)).
- **The cloud machine could not pass the project's checks.** The container ran everything as root and had no gitleaks, so tests that prove abcd refuses a path other accounts can write, and gitleaks-backed checks, failed on work that did not touch them; one failure reproduced on an unchanged copy of the default branch there ([iss-2610120724251698](../../../work/issues/open/iss-2610120724251698-cloud-sessions-fail-preflight-and.md)). Nothing prepares or checks a cloud machine the way the person's own computer is prepared ([iss-2610120729094755](../../../work/issues/open/iss-2610120729094755-no-cloud-environment-setup-for-abcd.md)).
- **Finished work was trapped.** Without a passing preflight there is no receipt, the push hook refuses the push, and skipping the hook is forbidden, so a finished fix (two commits and a resolved record) stayed in the container and was redone locally ([iss-2610120729087253](../../../work/issues/open/iss-2610120729087253-cloud-session-work-trapped-without.md)).
- **The reports stayed in transcripts.** The person copied one session's stop report into a local session by hand; the other two were still unread when the findings were filed ([iss-2610120729083126](../../../work/issues/open/iss-2610120729083126-cloud-session-reports-only-in-transcript.md)).

A second person now works on the project from another computer, and a cloud session has no machine-local state in common with either of them: it shares only the remote. Whatever lets the person send work out and get it back has to live where the cloud session can reach it, which is the same ground the reservation record ([itd-2609091034175565](../planned/itd-2609091034175565-nothing-tells-an-agent-that-a-record-it.md)) stands on.

### What the host offers today (evidence, 2026-10-12)

Read from the host's documentation on 2026-10-12 (code.claude.com: claude-code-on-the-web, cloud-environments, routines, self-hosted-environments, settings-reference) and GitHub's rulesets documentation; a coordinator's research, not yet re-verified in a live session:

- **Launch.** A cloud session can be started from a terminal with `claude -p "<prompt>" --environment <env-id> --ref <branch> --output-format json`, which returns the session's id and link; a follow-up is sent with `--cloud <id>`. It needs a claude.ai login whose refresh lasts at most 30 days. Routines have a REST fire endpoint, in beta.
- **No way to list or read sessions.** There is no documented interface to list cloud sessions or read their results: what a session produces comes back only through what it pushes. A local sub-agent cannot run in the cloud; it runs where its session runs, which is how the 2026-10-12 lanes ended up on the person's computer.
- **The machine.** Hosted sessions run as root on Ubuntu, and the base image cannot be replaced. A setup script stored with the claude.ai environment (not in the repository, cached for about five minutes), or a repository session-start hook gated on `CLAUDE_CODE_REMOTE=true`, can install a pinned gitleaks and the toolchain. Creating a non-root user and running preflight as that user is untested. Self-hosted environments (Team and Enterprise plans, beta) allow a non-root image. A shell command times out after two minutes by default and ten at most (longer in the background, adjustable by environment variables); the machine has about 4 CPUs and 16 GB.
- **Branches.** Sessions push to `claude/`-prefixed branches. The forge proxy refuses any ref that is not a branch, so a custom namespace such as `refs/abcd/wip/*` cannot work; it refuses deletions; and it blocks the forge's GraphQL interface, so `gh pr` and `gh issue` fail while `gh api` over REST works. Keeping such branches off the default branch takes a ruleset plus a CI check that fails on a source branch matching `claude/**`.
- **Attribution.** The host adds an AI co-author trailer and a session link to commits by default; the repository's `.claude/settings.json` (`attribution.commit`, `attribution.sessionUrl`) switches them off, though one report says the link can survive, so abcd's attribution gate stays the check. The git author inside the machine is not documented and has to be set explicitly.

## Scope Conditions

- Holds for the hosted cloud sessions of claude.ai, started through abcd's plugin for that host (decision 1). Another host (opencode, for example) is out of scope until a connector for it is written; nothing outside the connector may assume the first host.
- Holds on abcd's own repository first. A managed repository is a later rung, and its version must leave that repository's own git settings, hooks and tools as they are.
- Hypothesis until the first rung proves it: the hosted machine lets the setup step create a normal (non-root) user and run every check as that user (decision 8). Untested on 2026-10-12; if it cannot be done, C1 fails and the runner is re-decided.
- Holds while the person renews the host login by hand at most every 30 days (decision 11). A run that meets an expired login stops and says so; it never keeps going on a stored credential.
- Holds while the plan's own limits are the only cap on concurrent cloud sessions the person wants (decision 6); abcd counts sessions and refuses none for their number.
- Holds while the hosted machine's forge proxy accepts branch pushes and the forge's REST interface, which the provisional report channel (decision 4) needs from inside the session; the GraphQL route is blocked there.
- Holds while the person's own computer can run the full preflight: every cloud result is re-checked there before it lands (decision 9), so a cloud session never lands work on its own.

## Acceptance Criteria

> _Agent-seeded, unconfirmed: proposals for the planning interview, never approvals, revised on 2026-10-12 to the product thinker's answers (Decisions). They cover the **first rung only**: built first as scripts under [`script-first-mvp`](../../principles/script-first-mvp.md), on abcd's own repository, the smallest version that removes the hand work of 2026-10-12. Hosted sessions push to `claude/*` branches by default, and the forge proxy accepts only branches; whether abcd's work-in-progress branches keep that prefix is Q3b, deferred with Q3. A criterion marked "waiting on Qn" stands as written until that question is answered, and changes or is struck with the answer._

- **C1, the machine is prepared, and nothing runs as root.** **Given** a fresh hosted cloud container for this repository, running as root with no gitleaks, **when** the session starts and the repository's cloud-only setup step (C11) runs before anything else, **then** a normal (non-root) user exists and owns the checkout, gitleaks, the toolchain `go.mod` declares, the committed git hooks and the person's author identity are in place for that user, and `make preflight` on an unchanged copy of the default branch, run as that user so that no command time limit cuts it short, either passes and mints a receipt or fails only on the gates the check (C2) named in advance; no check of this criterion or of C2 runs as root, and the whole is proved once in a real cloud session, because running as a non-root user there is untested (decision 8).
- **C2, the machine is checked before work, and stops only for what the final checks need.** **Given** a container in which one prerequisite is missing (gitleaks, for example), **when** the session runs the environment check, **then** the check names each missing prerequisite, the setup step that supplies it and the final checks that need it, and changes no file in the checkout; if any of preflight's gates needs the missing tool, the session stops before any work and reports why (C6), and otherwise it warns and carries on. Which tool each gate needs is read from one list abcd keeps beside the gates (decision 5).
- **C3, a brief started in the wrong place stops.** **Given** a brief written for a cloud session, **when** it is started on the person's own computer instead (for the first host, `CLAUDE_CODE_REMOTE` unset, a test the host connector owns), **then** its first step reports that it is not running in the environment the brief was written for, and the session starts no work.
- **C4, one brief per item.** **Given** an item that is ready to build, either an open ledger item or a planned intent whose readiness gate passes (decision 7), **when** abcd composes the cloud brief for it, **then** abcd produces one brief naming the item, the author identity to commit under, the setup and check step to run first, the rule that no hook is skipped, the branch the work goes to (its prefix waits on Q3b) and the tracking issue the report is posted to, and the brief carries no session link, no path on the person's computer and no secret.
- **C5, no quiet fallback, and an expired login stops the run.** **Given** a request to send an item to a cloud session, **when** the cloud cannot be reached (no login, an expired login, an unknown environment, a launch the host refuses), **then** the person is told the cloud cannot be reached and why, and nothing is started on their own computer in its place: no local session, sub-agent or worktree; an unattended run that meets an expired login stops there and says that the person must renew the login by hand (decision 11).
- **C6, every session reports.** **Given** a cloud session that ends, having handed back its work or having stopped because a check failed, **when** it stops, **then** it posts its report (what it did, what failed, what it needs from the person) as a comment on the project's one tracking issue for cloud sessions, through the forge's REST interface, before it exits, and the comment passes abcd's outbound check, carrying no session link and no tool footer (decision 4, provisional until Q3 is answered).
- **C7, finished work is not trapped, and never reaches the default branch on its own.** **Given** a cloud session whose commits cannot earn a preflight receipt there, **when** it pushes them to its work-in-progress branch, **then** the push hook admits that push without a receipt and admits no other branch without one, and a pull request from any branch under that prefix into the default branch is refused by a required check. Waiting on Q3 (deferred on 2026-10-12) and the trust rule held behind it: not struck; its prefix follows Q3b; it is struck only if Q3 is answered no.
- **C8, one list of cloud sessions.** **Given** three cloud sessions abcd started, one that handed back its work, one that stopped with a report and one still working, **when** the person asks abcd for the list of cloud sessions, **then** it shows each one's item, branch, state and report, read from the shared remote and the tracking issue alone (there is no interface to list cloud sessions), with the session still working shown from its live reservation, and no transcript is opened.
- **C9, handed-back work lands through the person's own checks.** **Given** a branch a cloud session pushed, **when** the person collects it, **then** abcd runs preflight on a copy of it on the person's computer and, only if it passes, offers it for landing as a branch whose commits name the person as author, carry an `Assisted-by:` trailer and no AI co-author trailer or session link, with the receipt minted locally; a failing copy is reported with its failures and nothing is pushed; and no receipt minted in the cloud is trusted in place of this check, even one that passed there (decision 9).
- **C10, abcd starts the session.** **Given** an item that is ready to build and a valid host login, **when** the person asks abcd to send the item to a cloud session, **then** abcd starts one cloud session through the host connector with that item's brief (C4) and reports the session's id and link to the person, who takes no step in the host's own interface; a start the host refuses is C5's case (decision 2).
- **C11, the cloud session runs the full abcd toolchain.** **Given** a fresh hosted cloud session for this repository, **when** it starts, **then** the repository's committed Claude settings file has enabled the abcd plugin from this repository's own marketplace, switched off the host's AI co-author line and session link, and run the setup step (C1) because `CLAUDE_CODE_REMOTE` is set; the same file on the person's own computer runs no setup step; and a commit the session makes carries neither the co-author trailer nor the session link, with abcd's attribution gate still the check (decision 10).
- **C12, everything host-specific sits behind the host connector.** **Given** the first rung's scripts, brief template and the files they add, **when** everything outside the host connector is searched for the first host's markers (its name, its command-line tool, `CLAUDE_CODE_REMOTE`, its environment ids, its branch prefix if Q3b keeps it), **then** none is found; the host's own files that it reads at fixed paths (its settings file) belong to the connector though they sit where the host reads them; and a test proves the search, so a second host is added by writing a connector and changing nothing outside it (decision 1).

## Left out of the first rung

- **The Go verbs.** The first rung is scripts and a brief template; the core absorbs the contract they prove, as `script-first-mvp` requires, in a later rung. A coordinator's sketch of that later shape is a `dispatch` verb (launch, keep the session id with the record) and a `collect` verb (C9).
- **Repositories abcd manages other than its own.** The setup and check are proved on abcd's own repository first; a managed repository's version must leave that repository's own git settings, hooks and tools as they are (principle abcd-fixes-what-it-adds, adopted on the default branch on 2026-10-11).
- **Hosts other than claude.ai's hosted cloud sessions** (opencode, for example), and the other runners Q1 weighed (a self-hosted environment, a machine the person runs, GitHub Actions). Other hosts follow later through their own connector (decision 1).
- **A cap on concurrent cloud sessions enforced by abcd.** There is none beyond the plan's own (decision 6); the first rung counts at most.
- **A login kept for abcd in a credential store.** The person renews the host login by hand (decision 11).
- **Merging handed-back work automatically.** C9 offers a passing copy for landing; the person, or a local session under the usual rules, opens and merges it.
- **Messages between cloud and local sessions** while they run; reports are read after the fact. The session mailbox is [itd-2609151838312703](itd-2609151838312703-sessions-on-one-machine-or-one-local.md)'s, and it never leaves the local network.
- **The wider register of running sessions** ([itd-2609150819440345](itd-2609150819440345-which-session-holds-which-worktree.md)).
- **Recurring cloud routines** and their template ([itd-107](itd-107-autonomous-routines-assemble-from-one.md)).
- **Deleting spent `claude/*` branches.** The proxy refuses deletions; a sweep from an ordinary machine is the reservation record's tidy-up route ([itd-118](itd-118-merged-work-leaves-no-residue-abcd.md)).

## Decisions

Ruled by the product thinker on 2026-10-12, answering the draft's open questions (numbered by the question each answers):

1. **Q1, the runner: "Anthropic's hosted cloud sessions first, through the Claude plugin."** With it, a constraint: other hosts (opencode, for example) follow later, so the runner sits behind a host connector, and nothing outside that connector names one host. Reason: it is what was used on 2026-10-12 and can be started from a terminal, and the connector keeps abcd's core host-agnostic ([adr-39](../../decisions/adrs/0039-host-tier-policy.md), [itd-22](itd-22-harness-portability.md)). Criteria C10 to C12.
2. **Q2, who starts the session: abcd starts it.** Settled without a question by the product thinker's own statement, "I'd like abcd local to orchestrate this in future", which leaves one defensible answer. Criterion C10.
3. **Q3 and Q3b, work-in-progress branches and their prefix: deferred.** Reason: the product thinker chose to decide them later. C7 waits on Q3 and is not struck; the trust rule (an ADR and a brief invariant) stays held and is not minted.
4. **Q4, where reports go: "A comment on one tracking issue", provisionally.** Reason: it is the only channel that works when nothing can be pushed, which is the case while Q3 is deferred; it is revisited when Q3 is answered, since a report file on the work branch becomes possible only if Q3 is yes. Criterion C6.
5. **Q5, a missing tool: "Stop only for what the final checks need, warn for the rest."** abcd keeps the list of which tool each final check needs. Reason: a session stops only where its hand-back would fail; the accepted cost is a list that can go stale. Criterion C2.
6. **Q6, concurrency: "No limit beyond the plan's own."** Reason: nothing to build or keep; the accepted cost is that a burst of sessions can spend limits the person's own sessions also need.
7. **Q7, which items: "Any item ready to build, planned intents included."** Reason: more work can leave the person's computer; the accepted cost is that a longer run is likelier to stop on a question, which only its report carries back. Criterion C4.
8. **Q8, root: no; "the setup creates a normal (non-root) user on the hosted machine and every check runs as it."** Reason: the cloud runs the same gates as the person's computer, including the tests that prove abcd refuses a path other accounts can write; it is untested, so the first rung proves it. Criterion C1.
9. **Q9, trust: "Every cloud result is re-checked on the person's computer."** No receipt minted in the cloud is trusted. Reason: every commit that lands has passed the gates on a computer the person controls; the accepted cost is that every cloud result waits for a local collect. Criterion C9.
10. **Q10, the host's files: "Cloud sessions use the full abcd toolchain."** The project keeps a Claude settings file that enables the abcd plugin from this repository's own marketplace, switches off the host's co-author line and session link, and runs the setup step on cloud start only (gated on `CLAUDE_CODE_REMOTE`); other hosts get their equivalent through the same connector. Reason: the setup is versioned and reviewed with the code and attribution is off before the first commit, and the file belongs to the host connector (decision 1), so the host is named in one place. Criterion C11. Agent note for the planning interview: the marketplace serves abcd's last published release, so in a cloud session on this repository abcd's verbs still run as `go run ./cmd/abcd`, as AGENTS.md requires of any source checkout.
11. **Q11, the login: "The person renews the claude.ai login by hand, at most monthly."** Reason: nothing new is stored; an unattended run that meets an expired login stops and says so. Criterion C5.

Decided without a question, each the one defensible answer on the record (moved here from the open questions' preamble):

12. **The work goes out under the person's own author identity, set explicitly in the brief**, because every commit names a human author and an AI co-author trailer is never used (AGENTS.md, attribution).
13. **A cloud session hands work back only as a branch**, because the forge proxy accepts nothing else.

Left for the planning interview, because none of these answers settles them: the Mechanism claim, the grounds, the impact class, the confirmation of the scope conditions written from these answers, and the walk of every criterion.

## Open Questions

For the product thinker. Q1, Q2 and Q5 to Q11 were answered on 2026-10-12 and are recorded under Decisions; what remains is deferred or answered provisionally.

1. **Q3. May work that could not pass the checks go to the shared remote on a `claude/*` branch?** **Deferred** by the product thinker on 2026-10-12 (decision 3). C7 waits on it, not struck, and the trust rule stays held.
   - Yes: the push hook admits `claude/*` without a preflight receipt, and a ruleset plus a required check keep any `claude/**` branch from reaching the default branch; trapped work reaches the remote and can be collected (C9). But it is a new exception in the push gate, which needs its own rule (an ADR and a brief invariant, not minted until this answer) and a test proving the branch can never reach the default branch; and on a public repository unfinished work is public.
   - No: a session pushes only work that passed preflight, and otherwise its report describes the change; the push gate stays as it is. But work that cannot pass in the cloud is redone locally, as on 2026-10-12, and C7 is struck.
   - Decide later.
2. **Q3b. If yes, is the prefix the host's `claude/`, or one abcd names?** (depends on Q3) **Deferred** with Q3 (decision 3).
   - `claude/`: what hosted sessions push to already, so the brief changes nothing about how they name branches; but the name is one host's, in a project whose user-facing side is meant to stay host-agnostic, and a person using the host by hand also pushes `claude/` branches the hook would then admit without a receipt.
   - An abcd-named prefix such as `abcd-wip/`: plainly abcd's, beside `abcd-reserved/`, the same on any runner; but every brief must tell the session to push there rather than to its default, and a session that ignores the brief pushes to `claude/` and is refused.
   - Decide later.
3. **Q4. Where does a session's report go?** **Resolved provisionally** on 2026-10-12 (decision 4): a comment on one tracking issue, to be revisited when Q3 is answered. The options as they were put:
   - A draft pull request: visible on the forge, with notifications, where the person already reads work; but the proxy blocks the command-line tool's usual route (only the REST interface works), it needs a pushed branch, opens one pull request per session, its body is public text, and from a `claude/*` branch it is exactly what the Q3 rule must keep from merging.
   - A report file committed on the session's `claude/<item-id>` branch: it travels with the work, a plain fetch reads it, and it needs no forge access from the cloud; but it exists only if Q3 is yes, and nobody is notified, so only abcd's list shows it.
   - A comment on one tracking issue: it works even when nothing can be pushed, and every session reports in one place; but it needs the forge's REST interface from the cloud session, the text is public, and abcd reads a comment back less reliably than a file.
   - Decide later.

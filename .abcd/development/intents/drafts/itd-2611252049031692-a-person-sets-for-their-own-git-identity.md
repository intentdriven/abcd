# The facilitator's mode is each person's own setting

## Press Release

> Who plays the technical facilitator, a person or abcd, can now be each person's own setting. Jack, a consultant, works in two clients' repositories whose main branches both say `auto`. In the first they type one command at their own terminal and make `auto` theirs; in the second they type `human`, and their work waits for a person there. Every row in the first reads `facilitator: auto (yours, here)`, and every row in the second `facilitator: human (yours, here)`. Their colleague Carol, a tech lead in the first repository, typed nothing: their work goes on exactly as it did, their row says that the setting is the repository's, and nothing Jack typed changed it. A repository can still say `human`, and then it is human for everyone who works in it.

## Why This Matters

The product thinker ruled on 2026-11-25 that the technical facilitator's mode is a personal setting, held for each repository for a person's git identity, and that the status line must say which it is; they called it critical and to be built without delay (dcn-2611252040395990). Today one setting speaks for everyone who works in a repository: the committed line on its default branch, beside the computer's file. A colleague who joins takes the repository's choice, and one who wants the other for themselves has only a setting for every repository on their computer. This gives each person a setting of their own, and changes nothing for a person until they use it. The other half of the ruling, that the row says which it is, is itd-2611252117557299 and comes first. A second ruling reads this setting: abcd may install a newer release unasked only where the facilitator is on auto (dcn-2611252038565989). That is the installing intent's to take up (iss-2611252038564722), with adr-2611251808065076, whose third point keeps every repository file out of it; this intent only lets that one tell a person's own setting from a repository's.

## Mechanism

We expect a person to be on the mode they chose wherever they chose one, because the choice is kept in their account's home, is selected by who they recorded themselves to be and which repository they stand in, and is on the row with whose it is. We expect nobody to find their work changed by an update, because a person with no entry is read as they are today. Shown wrong if a person who set `human` has a pull request of theirs armed by abcd on that computer with nobody's approval; if one person's setting decides another's pull request; if two readers give two answers for one reading of the default branch; or if a person who typed nothing finds a merge of theirs decided otherwise than before.

## Scope Conditions

- Holds on one computer and one operating-system account. The setting lives in that account's home; on a second computer a person has no entry until they make one there, and a hosted session is question 3.
- Holds for the person an identity record names (itd-2610240918547728). The record selects which entry of the account's is read; it is not evidence of who is typing, and two people who share an account share its entries.
- Holds for a repository with a root commit and a name on the forge.
- Holds for what abcd decides and starts: its own merges, the shell commands its guard judges where its hooks run, and its questions. A person merging on the forge's page, and a program that calls the forge itself, are outside it.
- Holds as a setting a person makes and a check against mistakes, as [adr-42](../../decisions/adrs/0042-guard-parse-layer-is-a-mistake-filter.md) has it for the guard. Rules on the forge are the place for a limit that abcd is not asked to keep.
- Holds for the two modes there are, `human` and `auto`, and for what `auto` already covers. It widens neither.

## The trust this rests on

Auto lets abcd merge a pull request whose head a recorded review pair passed, with no person asked. So who may set it, and what it does not reach, are stated here.

**What keeps the setting the person's.** The forge's own rules: where the default branch needs an approval the acting account cannot give itself, no setting of abcd's merges without it. Another operating-system account: an agent run under one has no write to this one's home; abcd does not arrange that.

**What binds abcd's own merge paths.** A repository's `human`, committed on its default branch: abcd's own merge paths do not pass it, and it changes only by a merge, or by a push where the forge lets one reach that branch. The review pair's receipt, which every merge abcd arms in `auto` waits for, and the approval a contributor's pull request waits for in either mode. No personal setting changes any of them.

**What is a filter for mistakes.** The terminal and host-session checks on the command, the guard's refusals, and the checks on the file. They serve against the ordinary failure, an agent that sets `auto` because a task seemed to need it, and are presented as that and no more.

**What selects and does not prove.** The identity record, and the time written beside an entry. A word in a chat that an agent relays sets nothing.

**What shows it afterwards.** The mode and whose it is, on every row; the time it was set, in the command's answer; and each merge abcd armed with nobody asked, in this checkout's record of the gate's decisions (itd-2610301750162657).

## What's In Scope

One file under abcd's home on the computer, never in a checkout, holding for each identity a setting of their own for every repository and a variation for each repository they chose to vary. A variation is kept under the repository's root commit and its name on the forge. One command sets it and shows it. Every reader of `facilitator.mode` then asks one resolver, which answers in this order:

1. `human` committed on the default branch, or in the computer's file, holds for everyone it covers.
2. Else the entry of the person, where they have one that covers this repository: the variation, else their own setting. `human` is human. `auto` is auto where the repository permits it, which as built here means that its default branch commits `auto` (question 1).
3. Else, with no entry that covers this repository, the reading there is today, unchanged, named as whose it is: the committed line, else the computer's file, else human (question 2).

| Reader | Asks for | The default branch it reads |
|---|---|---|
| The merge gate, when `abcd land` or the build loop would arm | the resolved mode of the person running it, when the gate is asked | asked of origin |
| A withdrawn merge re-armed, or admitted after a release's hold | the same | as last fetched, as it is today |
| The guard's judgement of a merge command | the same | asked of origin |
| The line each prompt carries, which decides who answers a technical question | the same | as last fetched |
| The drain and the build, on whether a records commit takes a review round | the same, for the person whose account runs them, asked again at each decision | as last fetched; the arming after it asks origin |
| The bare board | the same, with whose it is | as last fetched |
| The row | the same, with whose it is, the person's and the computer's files read at each refresh | kept (itd-2611252117557299) |
| The listing of past landings | the mode the gate recorded for that merge | none |

## What's Out of Scope

- Finer grants (pushing, opening a pull request, deciding as a role, until a time) are itd-2610240850336695's. That grant and this mode stand side by side, and neither is read as the other.
- Naming the mode on the row and the board, in both modes, is itd-2611252117557299's. The table, the widths and the badges of the row are itd-2611031342000215's, which is a draft.
- The change that ends the reading in step 3 for a person with no entry. It is an intent of its own, later and separately ruled, and is not filed (question 2).
- Installing a release, and which of a person's settings it follows: the installing intent's (iss-2611252038564722), put to the product thinker with the second and third points of adr-2611251808065076.
- Any change to a forge's rules, rulesets or queue, and proving who a person is.

## Acceptance Criteria

A criterion that changes with an open question ends by naming it; it is written as the cautious reading has it.

- **Given** a person at their own terminal in a checkout whose identity record names them, **when** they run the command with `auto` or `human`, **then** it writes their variation for this repository, or with one flag their own setting for every repository, says the mode now in force and whose it is, has the kept reading the row shows taken again, and writes nothing in the checkout, nothing committed, and nothing on the network; a setting that a repository or the computer holds to human, or that the repository does not permit, is written and said to be held, naming what holds it. **Changes with question 1**: under the second reading nothing is held for want of a permit, and under the third the flag takes `human` alone.
- **Given** anyone, an agent included, **when** they run the command bare, **then** it shows the resolved mode, each place that has a say and what it says, and when the person's was set, and writes nothing.
- **Given** every combination of the default branch, the computer's file, the person's own setting, and their variation (each `human`, `auto`, or absent), **when** the mode resolves, **then** it is what the three numbered steps in What's In Scope give, with whose it is: the variation decides over the person's own setting, and `human` on either side of a person and a repository wins. Table-tested over all of them. **Changes with questions 1 and 2.**
- **Given** a person with no entry that covers this repository, **when** any reader in the table asks, **then** the mode is the one it was before this intent in each pairing of the default branch and the computer's file, and it is named as the repository's, this computer's, or not set; a landing arms what it armed before (a `HOME` that is not the account's aside, decision 4). A variation for one repository is no entry for another. **Changes with question 2.**
- **Given** a repository whose default branch commits `auto`, **when** a person with an entry of `human` lands, **then** the mode is human, their own, and their pull request waits for an approval; **when** their entry is `auto`, **then** it is auto, their own. The committed line is kept, is not an error, and abcd neither edits nor removes it.
- **Given** a person whose entry is `auto` and a default branch that declares nothing, **when** the mode resolves, **then** it is human, and the row, the board, and the command say that this repository does not permit auto; each landing that arms nothing for this reason says so and names the committed line that would permit it. **Changes with question 1**: under the second reading, and under the third in a repository the person named, the mode is auto, their own, and nothing is said of the repository.
- **Given** an identity record, for this repository or else for the account (itd-2610240918547728, adr-2610241022541063), that names a person with an entry, **when** git would author and commit in the checkout as that person, **then** the entry is read; **when** git would author or commit as another, **then** the mode is human and the reader names the difference. An account that holds an entry for anyone and has no identity record, or one that is refused, reads human and is told how to record one; an account that holds none reads as the criterion on a person with no entry says, whatever git is set to. An entry is selected by the record alone, never by git's configuration or a command's environment. Table-tested over the record, the entries, and git's identity.
- **Given** any flag or environment variable on any command of abcd's, **when** the mode resolves, **then** none sets `auto` or selects an entry. The person's file and the computer's file are read from one home, the one the account's own record names; with a `HOME` that is not the account's, every reader in the table reads human and says that that is why.
- **Given** the command asked to set `auto`, **when** it runs with no terminal, under a host session, or where that could not be told, **then** it is refused with exit 2, nothing is written, and the line says to type it in a terminal of one's own; **when** it is asked to set `human`, **then** only the first two are refused, since a refusal there would hold a person to auto.
- **Given** a host with abcd's hooks, **when** an agent runs the command to set either mode under any program name, or writes, moves, or removes its file with the shell or the host's own file tools, **then** the guard refuses and says it is the person's to type. The page calls this and the terminal check filters for mistakes, in the words of The trust this rests on.
- **Given** the person's file, **when** it is missing, **then** the person has no entry and nothing is said; **when** it is a link, is owned by or writable by another account, is over its size, is not valid, or holds a value that is neither mode, **then** it is refused naming the file in its tilde form, the mode counts as human, and nothing is armed. A file of its name inside a checkout is never read.
- **Given** a variation, **when** the gate resolves it, **then** it is matched on the root commit of the default branch the gate has just fetched and on the repository's name as the forge answers it; a reader that asks no network matches the root of the default branch it reads and the name origin's address spells. A fork, which carries the same root under another name, takes a variation of `auto` from no other repository; a variation of `human` is matched on the root alone and so holds in the fork too. A repository that is renamed keeps its `human` and is asked for its `auto` again.
- **Given** one reading of the default branch, **when** every reader in the table that asks for the mode is asked over it, across the cases of the criteria on combinations and on identity, **then** they give one answer for that reading, through one resolver, and a test that adds a reader of `facilitator.mode` beside that resolver fails. Two readers that hold different readings of the default branch may differ until each has read the same one, and the pages say so.
- **Given** a branch that commits either mode, or a working tree that holds one, **when** the mode resolves in that checkout, **then** it changes nothing: the repository's say is the default branch's.
- **Given** `facilitator.mode: auto` in the computer's file, **when** the person has no entry that covers the repository, **then** it counts as it does today; **when** they have one, **then** it turns nothing on and permits nothing, and each landing that arms nothing for this reason says so and what to type. `human` there holds every repository on the computer. **Changes with questions 1 and 2.**
- **Given** a person whose own entry gives `auto`, and a ready pull request that another maintainer's account opened, or one whose opener or whose own account cannot be read, **when** the gate is asked, **then** it answers as for human and says whose pull request it is; one their own account opened is armed on the terms `auto` has today. Where the repository's or the computer's setting gives `auto` to a person with no entry, the ruling of 2026-10-29 stands as it is: a maintainer's pull request goes through in `auto`.
- **Given** the resolved mode, **when** a session is prompted, **then** the line telling it that a technical question is decided and not asked is sent under `auto` and not under `human`, and says whose setting it is; two people's sessions in one repository, one on each mode, each get their own.
- **Given** a drain or a build begun under `auto`, **when** the person sets `human` while it runs, **then** the next decision it takes reads human and arms nothing more; a merge already armed or queued is not taken back by the command, and the command says so and names the act that does. A drive that is running on the binary it began with, from before this intent, goes on reading the settings that binary knows, and the command names each such drive it finds and how to stop it.
- **Given** a hosted session, or any session with no home of the person's, **when** it reads the mode, **then** the person has no entry there, the criterion on a person with no entry decides, and the row says whose setting it is. **Changes with question 3.**
- **Given** a merge the gate armed, **when** the past landings are listed, **then** the mode is the one this checkout's record of that decision holds, whatever the committed line said; a merge with no such record reads `unread` unless the first parent committed `human`, is counted neither as automatic nor as a person's, and is listed among the unattended, as every row the evidence cannot place with a person is. The spot-check's groups take a row that reads `unread` as their own rule says. Refines itd-2610301850454860 and itd-2610301750162657.
- **Given** any act above, **when** what it writes is read back, **then** nothing this intent writes adds to a commit, branch, pull request, announcement, spot-check record, or receipt the person's identity, the file's entries, or whether it was theirs or another's: a record that names a mode names `human` or `auto` and no more.
- **Given** any case above, **when** the row or the board renders, **then** whose it is stands where itd-2611252117557299 puts it, with two answers more than that intent has: the person's own for this repository (`yours, here`) and their own for every repository (`yours`). Nothing that intent shipped is withdrawn.

## Open Questions

1. Must a repository permit auto, or is the person's own setting enough? Three readings, for the product thinker to choose between; the criteria that change name this question. The first is built, as the cautious one: it can be widened without taking anything back. **First reading, both agree.** Auto is possible only where the team has said, on the main branch, that work may merge there with no person asked; inside that, each person chooses for themselves. It costs a step in each repository, and the permitting line is the same key that a copy of abcd from before this intent reads as auto for everyone, as it is read for a person with no entry until question 2 is ruled. It buys a second, visible step, in the history with who merged it; where anyone with write access may push to the main branch it buys the history and not the limit. It keeps the promise shipped with itd-2610150602547271, that in a team that keeps the default nothing merges until one of them has read it. **Second reading, the person's setting is enough unless the repository says human.** A person says auto once and has it wherever they may merge and nobody has objected. It reaches only pull requests their own account opened, which they could merge on the forge's page already, and each still waits for its review pair. It costs that shipped promise: a team that keeps the default, and wants it kept, commits `human`. It also reaches a fork of any repository, whose main branch says nothing. **Third reading, the person's setting is enough in the repositories they named.** As the second, but `auto` is never a setting for every repository: a person says it in each one, and nowhere is it true that they did not name. It costs that promise only where a colleague named the repository, and a step in each repository on each computer; it asks no committed line of a team and does not reach a fork nobody named.
2. When does a committed `auto` stop counting for a person who has set nothing? Until they have an entry it counts as it does today, which is what is built, and nothing ends it but a later intent the product thinker rules on. **First reading, at once**: the change that lets a person choose also ends it. From that day nobody is on auto they did not choose. Everyone who has typed nothing goes to human when they update, in abcd's own repository too, and their merges wait until they type. **Second reading, later**: it counts until the person has an entry, and a later release ends it for those who still have none, after the row and the board have named whose setting it is for as long as the product thinker wants. Nobody's work stops on the day this lands, and until that release a person who joins takes the repository's choice. Never is the second reading with no such release: the committed line then stays a team's default, and the mode is personal only for those who choose.
3. What does a hosted session do? It holds no home of the person's and so no entry. **First reading, as a person with no entry**: the repository's line counts, as today, which is what is built, whatever that person chose on their own computer. **Second reading, always human**: hosted work waits for a person, wherever they are, and an unattended hosted run merges nothing by itself. **Third reading, its own word**: the person says, where they set up their hosted sessions, which mode those have; abcd has no such place today, and no environment variable may be it. itd-2610241015120503 holds this question too, with brief invariant 23, under which cloud work reaches the default branch only through the person's own collect; one answer settles both.

## Decisions

3. The same: the change is additive. A person with no entry is read as today and the row says whose it is; an entry rules once there is one; both sides must permit, and human from either wins. To reverse: rule the cut-over in the same change.
4. The session's, for review: one narrowing reaches a person who has typed nothing. With a `HOME` that is not the account's, every reader reads human. To reverse: limit that to an account that holds an entry.
5. The session's, for review: one person's own `auto` never arms another maintainer's pull request. It changes the ruling of 2026-10-29 in itd-2610150602547271 ("a maintainer's goes through in `auto`") for a person whose own entry gives the auto, and leaves it where the repository's or the computer's setting does; a person confirms it. To reverse: let the setting of whoever runs the landing decide.
6. The session's, for review: `auto` in the computer's file counts only for a person with no entry. It names no person and no repository, so it is neither a person's choice nor a repository's permit. To reverse: read it as the account's own setting.
7. The session's, for review: an agent sets neither mode, `human` included, where the command or the guard can tell. To reverse: let an agent set `human`.
8. The session's, for review: nothing public says whose setting it was, only which mode. To reverse: name it in the landing's record.
9. The session's, for review: a fork shares a person's `human` and not their `auto`. A variation of `auto` holds under the root commit and the forge's name together, a `human` under the root alone, so a mistake of matching ends at human. To reverse: match both on the root.
10. The session's, for review: one flag makes the setting for every repository, kept beside the variations; under the third reading of question 1 it takes `human` alone. To reverse: variations only.
11. The session's, for review: an entry is selected by the identity record and not by git's configuration, and a difference between the two reads human. To reverse: select by what git would author as.
12. The session's, for review: the permitting line is the key there is, `facilitator.mode: auto`, and no new key. A copy of abcd from before this intent reads it as auto for everyone, which a new key would not. To reverse: a key of its own.
13. The session's, no question put: the command's name, the file's name and shape, and the short words in the row are the spec's. It is not `abcd mode facilitator`, which already sets whose answer is owed.

# Work handed to a cloud session comes back, or says why not

Typed links: `builds_on` [itd-2609091034175565](itd-2609091034175565-nothing-tells-an-agent-that-a-record-it.md) (reservations on the shared remote, being built now: a cloud session reserves the item it takes, which is how every other session, local or cloud, sees that it is held; this record adds nothing to the reservation itself); `related_issues`, the six findings of 2026-10-12 this record answers, each listed under Why This Matters. `related_intents`, prose relations no typed field carries: [itd-2609150819440345](../drafts/itd-2609150819440345-which-session-holds-which-worktree.md) (the wider register of running sessions, kept for later; this record's list covers only the cloud sessions abcd briefed, read from the remote), [itd-152](../shipped/itd-152-autonomous-cloud-runs-in-sibling-repos.md) (shipped: tool footers and session links leaking from cloud runs into public text; a report this record posts publicly is held to that same outbound check, nothing more), [itd-107](../drafts/itd-107-autonomous-routines-assemble-from-one.md) (routine prompts assembled from one versioned template; the cloud brief here is a one-off brief for one item, and may later become one of that template's archetypes) and [itd-22](../drafts/itd-22-harness-portability.md) (the host-profile seam: the host connector this record's first rung writes for one host, decision 1, is a piece of that seam, not a second one). `related_adrs`: [adr-2610120937435856](../../decisions/adrs/2610120937435856-a-cloud-session-s-unchecked-work-goes.md) (the trust rule this record's work-in-progress branches need, decision 3; brief invariant 23).

## Press Release

> A person hands any item that is ready to build, from a small fix to a planned feature, to a cloud agent session as easily as to a session on their own computer: abcd starts the session itself, and the work comes back, or the session says why it could not. The cloud session runs with the same abcd tools the person has, on a machine abcd prepares with the same checks, run as an ordinary user rather than as the machine's all-powerful one, and checked before any work starts, so a session never finds out halfway through that it cannot pass the project's checks. It gives the session a brief that says what to work on, whose name the work goes out under, and how to stop and report. Every session, finished or stopped, pushes its work and its report to a work-in-progress branch, even when the cloud machine could not pass the checks, so nothing is left behind in the cloud, and one list shows each cloud session's item, branch and report, so nobody copies a report out of a transcript by hand. A work-in-progress branch never reaches the main branch on its own: nothing from the cloud lands until it has passed the checks again on the person's own computer. Because pushed work is public, abcd never hands a cloud session an item that is not public yet, such as a private security report. When the cloud cannot be reached, or the login abcd starts sessions with has run out, abcd says so before anything starts, instead of quietly running the work on the person's own computer. It starts with one host's cloud sessions; other agent hosts plug into the same place later.
>
> "On the day I moved three fixes to the cloud, two things went wrong at once," said Maya, an autonomous-development practitioner. "The sessions I meant for the cloud started on my laptop without telling me, and the ones that did reach the cloud finished their work, failed checks their machine could not pass, and kept everything to themselves. I copied one report out of a transcript by hand and redid its fix locally. Now I tell abcd which item to send, the session checks its own machine first, its work and its report come back on a branch even when its checks failed, I read every session's report from one list, and what comes back passes my own checks before it lands."

## Why This Matters

On 2026-10-12 three issues that needed no decision were moved to cloud agent sessions, and every step of it was done by hand or went wrong quietly:

- **The work started in the wrong place, silently.** The requesting session's sub-agents could not reach the cloud and started on the person's own computer instead, in worktrees under the checkout (`.claude/worktrees/`), and other sessions learned of it only when the requesting session corrected its own announcement ([iss-2610120729076366](../../../work/issues/open/iss-2610120729076366-cloud-dispatch-falls-back-to-local.md)).
- **The real cloud sessions were started by hand.** The person launched them in the browser with briefs a local session wrote; nothing in abcd composes such a brief, lists the running sessions or collects their results ([iss-2610120729071657](../../../work/issues/open/iss-2610120729071657-abcd-cannot-launch-or-manage-cloud.md)).
- **The cloud machine could not pass the project's checks.** The container ran everything as root and had no gitleaks, so tests that prove abcd refuses a path other accounts can write, and gitleaks-backed checks, failed on work that did not touch them; one failure reproduced on an unchanged copy of the default branch there ([iss-2610120724251698](../../../work/issues/open/iss-2610120724251698-cloud-sessions-fail-preflight-and.md)). Nothing prepares or checks a cloud machine the way the person's own computer is prepared ([iss-2610120729094755](../../../work/issues/open/iss-2610120729094755-no-cloud-environment-setup-for-abcd.md)).
- **Finished work was trapped.** Without a passing preflight there is no receipt, the push hook refuses the push, and skipping the hook is forbidden, so a finished fix (two commits and a resolved record) stayed in the container and was redone locally ([iss-2610120729087253](../../../work/issues/open/iss-2610120729087253-cloud-session-work-trapped-without.md)).
- **The reports stayed in transcripts.** The person copied one session's stop report into a local session by hand; the other two were still unread when the findings were filed ([iss-2610120729083126](../../../work/issues/open/iss-2610120729083126-cloud-session-reports-only-in-transcript.md)).

A second person now works on the project from another computer, and a cloud session has no machine-local state in common with either of them: it shares only the remote. Whatever lets the person send work out and get it back has to live where the cloud session can reach it, which is the same ground the reservation record ([itd-2609091034175565](itd-2609091034175565-nothing-tells-an-agent-that-a-record-it.md)) stands on.

### What the host offers today (evidence, 2026-10-12)

Read from the host's documentation on 2026-10-12 (code.claude.com: claude-code-on-the-web, cloud-environments, routines, self-hosted-environments, settings-reference) and GitHub's rulesets documentation; a coordinator's research, not yet re-verified in a live session:

- **Launch.** A cloud session can be started from a terminal with `claude -p "<prompt>" --environment <env-id> --ref <branch> --output-format json`, which returns the session's id and link; a follow-up is sent with `--cloud <id>`. It needs a claude.ai login whose refresh lasts at most 30 days. Routines have a REST fire endpoint, in beta.
- **No way to list or read sessions.** There is no documented interface to list cloud sessions or read their results: what a session produces comes back only through what it pushes. A local sub-agent cannot run in the cloud; it runs where its session runs, which is how the 2026-10-12 lanes ended up on the person's computer.
- **The machine.** Hosted sessions run as root on Ubuntu, and the base image cannot be replaced. A setup script stored with the claude.ai environment (not in the repository, cached for about five minutes), or a repository session-start hook gated on `CLAUDE_CODE_REMOTE=true`, can install a pinned gitleaks and the toolchain. Creating a non-root user and running preflight as that user is untested. Self-hosted environments (Team and Enterprise plans, beta) allow a non-root image. A shell command times out after two minutes by default and ten at most (longer in the background, adjustable by environment variables); the machine has about 4 CPUs and 16 GB.
- **Branches.** Sessions push to `claude/`-prefixed branches. The forge proxy refuses any ref that is not a branch, so a custom namespace such as `refs/abcd/wip/*` cannot work; it refuses deletions; and it blocks the forge's GraphQL interface, so `gh pr` and `gh issue` fail while `gh api` over REST works. Keeping such branches off the default branch takes a ruleset plus a CI check that fails on a source branch matching `claude/**`.
- **Attribution.** The host adds an AI co-author trailer and a session link to commits by default; the repository's `.claude/settings.json` (`attribution.commit`, `attribution.sessionUrl`) switches them off, though one report says the link can survive, so abcd's attribution gate stays the check. The git author inside the machine is not documented and has to be set explicitly.

## Mechanism

_The technical facilitator's proposal of 2026-10-12, written on delegation because the draft left it open; for the product thinker's review on return._

We expect work handed to a cloud session to come back, or say why not, without any step done by hand, because the only thing a cloud session and the person's computer share is the remote, and this design puts every piece of hand-back on it: who holds the item (the reservation), the work itself, checked or not (the work-in-progress branch), and what happened (the report file committed on that branch). Every failure of 2026-10-12 was a step that depended on something not on the remote: a transcript, a receipt the cloud could not mint, a sub-agent that ran locally instead. Trust does not move to the cloud, because the person's own collect re-runs the checks (decision 9), so admitting unchecked work to the remote widens nothing that lands.

This would be shown wrong if, on the proof rung or on the first three items handed off after it, a result still has to be copied out of a transcript or redone on the person's computer for any reason other than a check that genuinely fails: for example, the hosted proxy refusing the work-in-progress name, the non-root user unable to run preflight there, or a report that reaches neither the branch nor the tracking issue.

## Acceptance Criteria

> _Agent-seeded, revised on 2026-10-12 to the product thinker's answers and the facilitator's delegated decisions (Decisions). They cover the **first rung only**: built first as scripts under [`script-first-mvp`](../../principles/script-first-mvp.md), on abcd's own repository, the smallest version that removes the hand work of 2026-10-12. Hosted sessions push to `claude/*` branches by default, and the forge proxy accepts only branches; the first host's connector declares the work-in-progress prefix `claude/abcd-wip/` (decision 3). Planned by the technical facilitator on delegation on 2026-10-12; the product thinker reviews them on return._

- **C1, the machine is prepared, and nothing runs as root.** **Given** a fresh hosted cloud container for this repository, running as root with no gitleaks, **when** the session starts and the repository's cloud-only setup step (C11) runs before anything else, **then** a normal (non-root) user exists and owns the checkout, gitleaks, the toolchain `go.mod` declares, the committed git hooks and the person's author identity (taken from the environment's forge token, decision 18) are in place for that user, and `make preflight` on an unchanged copy of the default branch, run as that user so that no command time limit cuts it short, either passes and mints a receipt or fails only on the gates the check (C2) named in advance; no check of this criterion or of C2 runs as root, and the whole is proved once in a real cloud session, because running as a non-root user there is untested (decision 8).
- **C2, the machine is checked before work, and stops only for what the final checks need.** **Given** a container in which one prerequisite is missing (gitleaks, for example), **when** the session runs the environment check, **then** the check names each missing prerequisite, the setup step that supplies it and the final checks that need it, and changes no file in the checkout; if any of preflight's gates needs the missing tool, the session stops before any work and reports why (C6), and otherwise it warns and carries on. Which tool each gate needs is read from one list abcd keeps beside the gates (decision 5).
- **C3, a brief started in the wrong place stops.** **Given** a brief written for a cloud session, **when** it is started on the person's own computer instead (for the first host, `CLAUDE_CODE_REMOTE` unset, a test the host connector owns), **then** its first step reports that it is not running in the environment the brief was written for, and the session starts no work.
- **C4, one brief per item.** **Given** an item that is ready to build, either an open ledger item or a planned intent whose readiness gate passes (decision 7), **when** abcd composes the cloud brief for it, **then** abcd produces one brief naming the item, the rule that every commit is authored under the identity the setup took from the forge token (decision 18), the setup and check step to run first, the rule that no hook is skipped, the branch the work goes to (the host connector's work-in-progress prefix followed by the item id, `claude/abcd-wip/<item-id>` for the first host), where the report goes (a report file on that branch, and the tracking issue only when the push fails, C6), and the brief carries no session link, no path on the person's computer and no secret.
- **C5, no quiet fallback, and an expired login stops the run.** **Given** a request to send an item to a cloud session, **when** the cloud cannot be reached (no login, an expired login, an unknown environment, a launch the host refuses), **then** the person is told the cloud cannot be reached and why, and nothing is started on their own computer in its place: no local session, sub-agent or worktree; an unattended run that meets an expired login stops there and says that the person must renew the login by hand (decision 11).
- **C6, every session reports, on its branch.** **Given** a cloud session that ends, having handed back its work or having stopped because a check failed, **when** it stops, **then** it commits its report (what it did, what failed, what it needs from the person, and which channel it used) as `.abcd/work/cloud-reports/<item-id>.md` in a final commit of its own on its work-in-progress branch and pushes it with the work; only when that push fails does it post the same report, saying the push failed and why, as a comment on the project's one tracking issue for cloud sessions through the forge's REST interface, before it exits; and either form passes abcd's outbound check, carrying no session link and no tool footer (decision 4).
- **C7, finished work is not trapped, and never reaches the default branch on its own.** **Given** a cloud session whose commits cannot earn a preflight receipt there, **when** it pushes them to `<wip-prefix><item-id>`, **then** the push hook admits that push without a receipt as one entry of its declared list of receipt-less prefixes, with the prefix read from the host connector's declaration and the entry ruled by [adr-2610120937435856](../../decisions/adrs/2610120937435856-a-cloud-session-s-unchecked-work-goes.md); it refuses without a receipt every other branch, including any other branch in the host's own namespace, a work-in-progress branch whose name is not the prefix followed by one valid record id, and one whose pushed commits fail the attribution gate; it refuses a declaration whose prefix does not end in the segment `abcd-wip/` or holds more than one segment before it; and a pull request or merge-queue entry into the default branch from a source branch holding the segment `abcd-wip`, or whose diff adds a file under `.abcd/work/cloud-reports/`, fails a required check the default branch's ruleset names (decision 3, invariant 23).
- **C8, one list of cloud sessions.** **Given** three cloud sessions abcd started, one that handed back its work, one that stopped with a report and one still working, **when** the person asks abcd for the list of cloud sessions, **then** it shows each one's item, branch, state and report, read from the shared remote alone (the work-in-progress branches, the report file on each and the reservations), plus the tracking issue's comments for a session whose push failed (there is no interface to list cloud sessions), with the session still working shown from its live reservation, and no transcript is opened.
- **C9, handed-back work lands through the person's own checks.** **Given** a branch a cloud session pushed, **when** the person collects it, **then** abcd runs preflight on a copy of it on the person's computer and, only if it passes, offers it for landing as a branch whose commits name the person as author, carry an `Assisted-by:` trailer and no AI co-author trailer or session link, with the receipt minted locally and the report's own commit left out of it; a failing copy is reported with its failures and nothing is pushed; and no receipt minted in the cloud is trusted in place of this check, even one that passed there (decision 9).
- **C10, abcd starts the session.** **Given** an item that is ready to build and a valid host login, **when** the person asks abcd to send the item to a cloud session, **then** abcd starts one cloud session through the host connector with that item's brief (C4) and reports the session's id and link to the person, who takes no step in the host's own interface; a start the host refuses is C5's case (decision 2).
- **C11, the cloud session runs the full abcd toolchain.** **Given** a fresh hosted cloud session for this repository, **when** it starts, **then** the repository's committed Claude settings file has enabled the abcd plugin from this repository's own marketplace, switched off the host's AI co-author line and session link, and run the setup step (C1) because `CLAUDE_CODE_REMOTE` is set; the same file on the person's own computer runs no setup step; and a commit the session makes carries neither the co-author trailer nor the session link, with abcd's attribution gate still the check (decision 10).
- **C12, everything host-specific sits behind the host connector.** **Given** the first rung's scripts, brief template and the files they add, **when** everything outside the host connector is searched for the first host's markers (its name, its command-line tool, `CLAUDE_CODE_REMOTE`, its environment ids, its work-in-progress prefix `claude/abcd-wip/`), **then** none is found, the push hook and the required check match only the connector's declaration and the host-agnostic segment `abcd-wip`; the host's own files that it reads at fixed paths (its settings file) belong to the connector though they sit where the host reads them; and a test proves the search, so a second host is added by writing a connector and changing nothing outside it (decision 1).
- **C13, nothing private goes to the cloud.** **Given** an item that is not public yet (its record is absent from the remote's default branch: a draft never pushed, a record only on a local branch, or a private record in the embargo store) or one the embargo store on this machine holds, **when** the person asks abcd to send it to a cloud session, **then** abcd refuses before composing a brief or starting anything, names which of the two reasons applies, and starts nothing on the person's computer in its place; when an embargo store exists on the machine, the composed brief for a public item is passed through `abcd embargo check` first, and a store that exists while that check cannot run is a refusal, never a pass; and a test proves each refusal (decision 14, from the security rule).

- **Repositories abcd manages other than its own.** The setup and check are proved on abcd's own repository first; a managed repository's version must leave that repository's own git settings, hooks and tools as they are (principle abcd-fixes-what-it-adds, adopted on the default branch on 2026-10-11).

- **A login kept for abcd in a credential store.** The person renews the host login by hand (decision 11).
- **Merging handed-back work automatically.** C9 offers a passing copy for landing; the person, or a local session under the usual rules, opens and merges it.
- **Messages between cloud and local sessions** while they run; reports are read after the fact. The session mailbox is [itd-2609151838312703](itd-2609151838312703-sessions-announce-what-they-are-doing.md)'s, and it never leaves the local network.

- **Recurring cloud routines** and their template ([itd-107](../drafts/itd-107-autonomous-routines-assemble-from-one.md)).
- **Deleting spent work-in-progress branches.** The proxy refuses deletions; a sweep from an ordinary machine is the reservation record's tidy-up route ([itd-118](../drafts/itd-118-merged-work-leaves-no-residue-abcd.md)).

## Decisions

Ruled by the product thinker on 2026-10-12, answering the draft's open questions (numbered by the question each answers):

1. **Q1, the runner: "Anthropic's hosted cloud sessions first, through the Claude plugin."** With it, a constraint: other hosts (opencode, for example) follow later, so the runner sits behind a host connector, and nothing outside that connector names one host. Reason: it is what was used on 2026-10-12 and can be started from a terminal, and the connector keeps abcd's core host-agnostic ([adr-39](../../decisions/adrs/0039-host-tier-policy.md), [itd-22](../drafts/itd-22-harness-portability.md)). Criteria C10 to C12.
2. **Q2, who starts the session: abcd starts it.** Settled without a question by the product thinker's own statement, "I'd like abcd local to orchestrate this in future", which leaves one defensible answer. Criterion C10.
3. **Q3 and Q3b, work-in-progress branches and their prefix: yes, and the connector owns the prefix.** Decided on 2026-10-12 by the technical facilitator on the product thinker's explicit delegation that day: "decide the deferred item so that you can plan the intent. I want it ready to be build in a few days (while I'm away)". A cloud session that cannot pass the checks still pushes its work to a work-in-progress branch, so nothing is trapped; the push hook admits such a branch without a preflight receipt as one entry of its declared list of receipt-less prefixes (the list the reservation build introduces), and a ruleset plus a required check that fails on a work-in-progress source branch keep it from ever reaching the default branch. Reason: decision 9 already re-checks every cloud result on the person's computer, so the receipt was never what made cloud work trusted; the risk the receipt guarded, unchecked work landing, is held by the ruleset, the required check and the local collect. Cost accepted: on a public repository unfinished work is public. Q3b: the host connector owns the prefix and the host-agnostic core never names it; for Anthropic's hosted sessions it is `claude/abcd-wip/<item-id>`, inside the host's own branch namespace in case its proxy admits only that, and narrow enough that a person's own hand-pushed `claude/` branches still need a receipt. That the proxy accepts a push to that name is a scope condition the first rung proves.

# ADR-2611062149324491: An unattended process replaces its own binary only after verification and a passing proof

## Context

`abcd drain --drive` runs for weeks with nobody at the terminal (adr-2610222222326104). It compares abcd's binary with the one it started on before every stage and ends the run on a difference, so a release cut while it runs cannot reach it, and the technical facilitator has ruled that a long run has no stops and no restarts (dcn-2611062149362998). A binary left behind also falls behind the records newer binaries write.

Two records already bind what may replace abcd's binary. adr-38 keeps every implicit operation off the network and says that checking for updates is a verb the person runs, and that ambient update discovery needs a record in the open. `abcd update` (itd-130) swaps a release binary only after the release's checksums, the build provenance the release workflow signed for exactly those bytes, bound to the commit the tag names, and the release the bytes' own build metadata claims all agree, and only over a file it can prove is abcd's. A drive proves the walls it runs behind in one live launch before its first move, with its own binary serving the approver and the hooks.

A drive's stages run on the same account as the drive. A profile is a login boundary, not an isolation boundary: a stage's shell can reach the installed binary, the profile's settings, the install record and the release mark. Whatever decides a swap must read none of them.

## Decision

We will let an unattended process of abcd's replace its own binary, and only under these rules.

**Only the drive, only at a lane boundary, only on the person's yes.** The one process that takes a release itself is `abcd drain --drive`. It checks when a lane has ended and the next is not yet opened, or on waking from a wait before opening one, or when a lane or a judgement has held the check for that long, at most about once an hour, and never from a stage. The consent screen names the check in one line, so the yes is the explicit ask adr-38's second tier requires; `--no-self-update` turns it off, and nothing else turns it on or off: no configuration key, no environment variable, no repository file. Every other operation of abcd's stays off the network as adr-38 says, and `abcd update` stays the person's verb.

**Only a newer stable release the origin itself names.** The candidate is the tag the release origin's latest-release answer names, read by the drive; a tag a file, a stage or a repository names is never one. A tag not newer than the running version, or carrying a pre-release suffix, is not taken.

**Only after the update verb's verification, into a private staging file.** The bytes are held to the three checks `abcd update` holds a swap to, in one place: the release's checksums, the signed build provenance for exactly those bytes from the release workflow on the default branch at the commit the tag names, and the release the bytes' own build metadata claims. They are written to a staging file beside the installed binary that nothing else names. This proves the bytes are the release the publisher cut and that the download arrived intact. It does not prove the release is free of defects, that it works on this machine, this harness or this repository, or that the staging file is unchanged afterwards.

**Only after the new binary answers for the drain verbs, read-only.** The live proof below exercises the approver and the hooks and no drain verb, so first the staged binary runs in the checkout, with a bound: it accepts the arguments its re-execution would be given and answers a read-only drain with a plan. Anything else leaves the installed binary as it was; the drive says so once per reason, carries on, and tries that version again at later checks, since this run reads the checkout as it stands.

**Only after the new binary passes the live proof from the staging file.** Before the installed binary is touched, the staged binary serves as the approver and the hooks of the same live launch the drive proves itself with: the tools, the one server connected, no plugin but the harness's own, no key, the guard refusing what it is meant to refuse, the approver answering for the shell step, the home and the variables, and a settings file in the working tree having no effect. A wall that does not hold leaves the installed binary and the settings as they were; the drive says which wall once and carries on, and the release is tried again only when a later one is published. The file is held to the verified digest and to being a regular file immediately before each run of it, before the swap, and at the installed name before the re-execution.

**The swap is atomic, the previous binary is kept, and the process re-executes itself.** The swap is the update verb's, the previous binary stays beside the installed one, and the drive re-executes itself with no new question, since the yes covered the run, and with none of the arguments the drain's state already holds. The re-executed drive writes the profile's settings afresh for the same path, pins the new binary as its baseline, and resumes from the drain's own state. On a first attempt it runs no live proof of its own: that file passed the proof moments before the swap and was held to the verified digest immediately before the exec, and a second launch at every move would spend the subscription on what was just shown. An attempt after a failed one proves itself live, since time has passed. The kept copy, started after a refused start, does run the proof: it is rare, costs one launch, and that file has not been proved in this run's present state. A re-execution the system refuses is restored from the kept copy and said. A new binary that starts and keeps failing before its first move, a panic in its start or its loop included, verifies the kept copy as the release it replaced, its own build claim and its build provenance, restores those bytes, says so, and executes it with that version named as refused in its arguments, where no stage can write, so the drive carries on and does not try it again. A copy found not to be that release is not restored, and neither is one whose verification still has no answer after about two minutes of asking. A restore or an execution that fails ends naming the way back, as does a fault that first shows after the first move; restoring it then is the person's act. A binary that fails to load, panics before that code or on another goroutine, or hangs at its start, is out of reach: nothing outlives the exec to see it.

**A source build never self-updates.** A binary whose own build metadata claims no release tag, and a binary a plugin root, a package manager or the track-latest shim owns, is never replaced by a drive, and the consent screen says so.

**Nothing a stage writes brings a swap about.** The decision reads the flag, the clock, the running binary's own build metadata, the installed binary's kind as read at the start, and the release origin over the transport the update verb uses, with proxy and certificate overrides scrubbed. The release mark and the install record are written after a swap, as the update verb writes them, and never read to decide one. A failed read-only run keeps that version out and never brings one in. The comparison of the installed binary and the settings with the start stands before every stage; a stage that writes either ends the run as it does today. An attempt at a start after a failed one holds the binaries to what the process began on before it pins anything, and a difference ends the run.

## Alternatives Considered

- **Keep the rule as it is: a changed binary ends the run, and a person restarts it on a new release.** Rejected by the ruling: a long run has no stops and no restarts, and a binary left behind stalls on records it cannot read.
- **Swap the installed binary on verification alone, as the update verb does.** Rejected: the update verb runs for a person who sees its receipt and can act on it; a drive has nobody there. The live proof is what shows the release holds every wall on this machine before anything depends on it.
- **Run the new binary from a versioned store and leave the installed binary alone.** Rejected for now: the hooks and the approver name one absolute path, `abcd ahoy` and `abcd update` reason about one installed copy, and two copies of abcd on one account would be a second install shape to classify. The swap keeps one copy, and the kept previous binary gives the recovery a second copy would have given.
- **A supervisor that keeps the old process alive to restart the new one if it fails.** Rejected: no process must stay alive beyond the run (dcn-2610180720366282), and the proof already ran the new binary as the approver and the hooks of a live launch. A start that fails restores the kept copy itself, and what it cannot see is the person's.
- **A setting in the repository or the machine configuration to turn it on.** Rejected: a repository's configuration can never start or widen an unattended run (adr-2610222222326104, condition 1), and a stage can write the machine's files. A flag on the command the person typed is the one input a stage cannot reach.
- **This rule, on the person's yes, with the proof before the swap (chosen).** It takes releases unattended without trusting anything new, and every failure leaves the drive on the version it has.

## Consequences

- adr-38's second tier gains one verb whose documented meaning includes a release check the person consents to at its start; its first tier and its consequence that update discovery never rides in as an implementation detail stand. This record states the refinement in the open; a person confirms it is a refinement and not a reversal when accepting this record.
- A release's rendering of the profile's settings must accept the previous release's rendering as abcd's, or the re-executed drive's start says the settings were edited when they were not; the drive's hooks name one absolute path whose contents change.
- Every later release must keep answering what an earlier one starts it with: the drive's two resume flags, its off switch, and the read-only drain's plan. A release that drops one is refused at the rehearsal, and every drive on the release before it stays there.
- Drives on one account share the installed binary and, on one profile, the settings: one drive's swap ends another at its next comparison, whatever flags that other has, and one drive's proof rewrites settings the other compares. The comparison is what ends it, so nothing unproved runs. One drive to an account is the supported shape (dcn-2611070019463013), and a start that may take a release says so.
- The plugin root's binary and the plugin's pages are not the drive's and are never touched: a drive's stages load no plugin, and the person's own sessions keep the plugin's vintage until they take a plugin update in the host, which `abcd ahoy` then lists as a gap.
- Accepted: a first attempt that names a move goes on with no live proof of its own, because that file passed the proof moments before the swap. The comparison before every stage and the proof on any later attempt stand.
- Accepted: a go-back keeps that one release out for the rest of the run. The person gets a line, and the next release reopens the check.
- The staging file and the kept previous binary are two files beside the installed one, in a directory the account can write, each named for what it is.
- A brief invariant states this rule once this record is accepted, which is a person's act. Its wording: **An unattended process replaces its own binary only after the update verb's verification and a live proof the new binary passes, on the person's yes, and nothing a stage writes brings a swap about** — the drive alone takes a release, at a lane boundary, from the origin's own latest-release answer; the bytes pass the checks `abcd update` makes, then answer a read-only drain and serve the drive's live proof from a staging file before the installed binary is touched; a failure leaves the version running; the previous binary is kept, and a start that fails its own preconditions goes back to it; a source build never self-updates; and the decision reads the flag, the clock, the running binary's own build metadata and the origin, never a file on the account.
